SYSTEM DESIGN PRIMER · UNIT 14

Asynchronism

Some work is too slow to do while the user waits. An asynchronous workflow moves it out of the request: the application hands the job to a message queue or task queue, a worker does it in the background, and the user gets an answer straight away. This unit covers how queues hand out work and what they promise when things fail, the tools the primer names (Redis, RabbitMQ, Amazon SQS and Celery), and back pressure: what to do when work arrives faster than the workers can finish it.[1]

14.0Why go asynchronous

Asynchronous workflows help reduce request times for expensive operations that would otherwise be performed in-line. They can also do time-consuming work in advance, such as periodic aggregation of data.[1] Figure 14.1, which the primer takes from Larson, shows the shape. The web server still talks to the database directly for quick work, but hands slow work to a message queue; a separate queue consumer takes it from there and writes the result to the database.[1][2]

Synchronous vs asynchronous

In a synchronous (in-line) request, the server finishes all of the work before it replies, so the user waits for the slowest step. In an asynchronous one, the server does only the part the reply needs, records the rest as a job, and replies; the job runs later, outside the request, and the user is not blocked.[1] Figure 14.2 plays both versions of the primer’s example, posting a tweet that has to reach every follower.[1]

The same contrast holds inside a single program. In his talk, Thompson compares a thread waiting on a lock with a thread handing work to a queue. Threads that fail to get a lock are parked by the operating system and woken later, at a large cost: their caches are polluted and they may be rescheduled on a different core, and meanwhile they make no progress. A thread that hands its work to a queue instead stays busy and useful, while a thread on the other side of the queue does the work.[5]

Offline processing

Larson calls this off-line processing and gives two reasons for work to leave the request. Either it would add unacceptable latency (his example is spreading one user’s action across a social graph), or it has to run on a schedule, such as daily analytics rollups.[2] Putting it behind a queue also lets it run on its own pool of machines, so you can add capacity only to the part that has become the bottleneck instead of scaling everything together.[2]

For scheduled work, Larson observed in 2011 that nearly every large system needs recurring jobs, yet no widely accepted tool ran them with redundancy, so cron (the Unix job scheduler) was the usual fallback. His advice is to have the cron job only publish a message: the cron machine then just schedules the work, and the queue’s consumers do it.[2]

14.1Message queues

Message queues receive, hold, and deliver messages. If an operation is too slow to perform inline, the primer’s workflow is:[1]

  1. An application publishes a job to the queue, then notifies the user of the job’s status.
  2. A worker picks up the job from the queue, processes it, then signals that the job is complete.

The application that writes messages is the producer (or publisher), the worker that reads them is the consumer, and the software that holds the queue in between is the message broker.[10] Brokers can deliver messages by push, sending them to consumers that have subscribed, or by pull, where consumers keep asking for new messages; RabbitMQ recommends push and calls polling inefficient.[10]

The workflow, step by step

The last step, signalling completion, is what makes a queue safe. The broker keeps a job until a worker confirms it, so a worker that dies halfway through does not take the job with it. Step through Figure 14.3, then switch to Worker crashes to see the job come back; the next sections explain the cost of that safety.

Making it look done

While the job runs, the client might do a small amount of processing to make the task seem complete. If you post a tweet, it can appear on your own timeline instantly, even though delivering it to all your followers takes longer.[1] Larson treats this as a choice about the interface you show users:[2]

Do the minimum inline

  • The request only schedules the job and tells the user it will happen offline.
  • The interface updates later, usually by polling (asking “is it done yet?” again and again).
  • Larson’s example: provisioning a new virtual machine at Slicehost.

Do enough inline to look complete

  • The request finishes the part the user sees; the rest happens afterwards.
  • Larson’s example: posting on Twitter or Facebook. Your timeline updates in the request; followers’ timelines update out of band.
  • Updating every follower of a prominent account in real time is not feasible.

Delivery guarantees

The primer warns that Redis messages can be lost and SQS messages can be delivered twice.[1] Both are statements about delivery semantics: what a broker promises when a consumer or server fails.

At-most-onceA message is delivered once if at all and is never sent again, so it can be lost. Redis Pub/Sub works this way: if a subscriber cannot handle a message, because of an error or a network disconnect, it is gone for good.[8]
At-least-onceA message is not lost, but it may arrive more than once. SQS standard queues guarantee this,[13] and RabbitMQ gives the same effect with explicit acknowledgements.[10]
Acknowledgement (ack)The consumer tells the broker it has finished. With automatic acks the broker removes a message as soon as it is delivered; with explicit acks it waits for the consumer, and redelivers to another consumer if the first one dies first.[10]
Visibility timeoutSQS’s version of an ack. A received message stays in the queue but is hidden from other consumers, for 30 seconds by default. The consumer must delete it before then, or it becomes visible again for another attempt.[15]
IdempotentProcessing the same message twice does no extra harm. AWS’s advice for at-least-once delivery is to design applications this way.[14]
DurabilityWhether a stored message survives a server failure. SQS stores each message redundantly across several availability zones before acknowledging the send.[13]

Why would SQS deliver a message twice? It keeps copies of each message on several servers. On rare occasions one of them is unavailable when you receive or delete the message, so its copy is not deleted and can come back on a later receive.[14] For stronger guarantees in Redis, its documentation points to Redis Streams, which persist messages and support both at-most-once and at-least-once delivery.[8]

Inside RabbitMQ: the AMQP model

AMQP (Advanced Message Queuing Protocol) is the protocol the primer says RabbitMQ users must adapt to.[1][10] In its 0-9-1 version, publishers do not write to queues directly. They send messages to an exchange, which routes copies into queues according to bindings: rules that link an exchange to a queue, often using a routing key carried by the message. Consumers then read from the queues.[10] The exchange type decides how the routing key is used:[10]

  • Direct: to every queue whose binding key exactly equals the routing key.
  • Fanout: a copy to every bound queue; the routing key is ignored.
  • Topic: to queues whose binding pattern matches the routing key. Keys are words separated by dots; in a pattern, * stands for exactly one word and # for zero or more.[11]
  • Headers: by matching message header values instead of the routing key.

Figure 14.4 routes one message through the first three types. A related setting, prefetch, caps how many unacknowledged messages one consumer may hold at a time, which spreads work across consumers.[10]

14.2Task queues

Task queues receive tasks and their related data, run them, then deliver their results. They can support scheduling and can be used to run computationally intensive jobs in the background.[1] The primer’s example is Celery, which supports scheduling and is primarily for Python.[1]

Celery

In Celery a client (your application) adds a task to a queue as a message, a broker delivers it, and a dedicated worker process performs it; several workers and brokers can run together for availability and horizontal scaling.[16] The pieces in Figure 14.5 are:

  • Broker: required. RabbitMQ and Redis transports are feature-complete; Amazon SQS is supported but marked experimental.[16]
  • Result backend: optional, and off by default. When set, it stores return values; options include Redis, SQLAlchemy, the Django ORM and MongoDB.[16][17]
  • Scheduling: a task can run at a given time, or periodically on an interval or a crontab expression.[16] celery beat is the scheduler that kicks off periodic tasks, and only one should run per schedule, or tasks are duplicated.[18]
  • Languages: Celery is written in Python, but its protocol can be implemented in any language, and community clients exist for Node.js, PHP, Go and Rust.[16]

Listing 14.1 is Celery’s own minimal example. Calling delay() sends the task and returns at once with an AsyncResult; the work happens in the worker.[17]

Message queue vs task queue

The primer’s two definitions differ in what the queue is responsible for.[1] A message queue moves messages and leaves the work to whoever consumes them. A task queue takes a task with its data, runs it, and hands back the result. Celery shows why a task queue usually sits on top of a message broker: the task itself travels as a message, and the broker is what delivers it to a worker, so Celery cannot run without one.[16]

The top-voted answer on the Quora thread the primer links argues the two names are close to interchangeable: what matters is the asynchronous hand-off, where one party asks for something and moves on, and another follows up on it later. It splits the system into roles rather than products:[6]

The task or messageThe unit of work being handed over.[6]
The queueA largely passive data structure, kept by a managing process, that stores tasks and hands them out in order when asked.[6]
The workersProcesses that take tasks from the queue and execute them. If they all remove tasks from the queue directly, they run into race conditions, such as two workers grabbing the same task.[6]
The message brokerDistributes tasks to workers, even on other machines, and looks after completion: retrying tasks when a worker fails and giving faster workers more tasks.[6] These match RabbitMQ’s redelivery of unacknowledged messages and its prefetch limit (14.1).[10]

The answer adds that the roles overlap in real products, which is why the terms get confused. Redis is mainly a fast data store but also acts as a broker, and RabbitMQ keeps tasks in queues of its own.[6] Both points agree with the brokers’ documentation.[8][10]

14.3Back pressure

If queues start to grow significantly, the queue can become larger than memory, resulting in cache misses, disk reads, and even slower performance. Back pressure helps by limiting the queue size, which maintains a high throughput rate and good response times for jobs already in the queue. Once the queue fills up, clients get a server busy or HTTP 503 status code telling them to try again later, perhaps with exponential backoff.[1]

Two terms from Unit 3 matter here: throughput is how many jobs finish per second, and response time (latency) is how long each one takes from arrival to completion, including any time spent waiting in a queue.

Queues are everywhere

Thompson’s talk opens by framing scale as a cost problem: as volume grows, cost should stay reasonable, which means knowing how many units of work each extra node buys you.[5] He calls contention, many threads or requests competing for one shared resource, the biggest killer of scalability, in the small (a contended lock) and in the large (one database or one load balancer everything passes through). Wherever there is a contention point, a queue builds up behind it.[5]

His advice is to embrace queues because they exist whether you model them or not. Writing to or reading from the network queues, submitting jobs to a thread pool queues, and, as 14.0 showed, a lock is a queue run by the operating system.[5] His blog post lists the same hidden queues in synchronous designs: lock and semaphore wait queues, and the run queue when a thread is created per request, while thread creation, context switches and condition variables add significant cost.[3] Bring the queues out where you can see them, and you can start managing them.[5]

Example: logging behind a lock

Thompson calls logging one of the biggest limits he meets when scaling systems, and the common Java logging frameworks a perfect example of ignoring Little’s law and Amdahl’s law.[5] (Amdahl’s law, from Gene Amdahl in 1967, says the part of a task that cannot be parallelized caps the speed-up you get from adding processors.[19]) In his measurements, one uncontended thread logging through the JDK logger took about 16 µs per message on a fast machine with an SSD, two threads about 35 µs, and more threads hundreds of microseconds, all queuing on one lock. The thread that fills the buffer must flush it to disk while everyone else waits behind it, giving a sawtooth of latency, and rolling the log file stalls the queue again.[5]

Why unbounded queues fail

Thompson starts from a system receiving requests faster than it can handle them, for a sustained period. A common failure is to accept everything until response times rise into a “hockey stick” curve and the system crashes. Since something has to give, he argues it should keep working at its maximum sustainable throughput, with acceptable response times, and turn the excess away.[3]

In software, capacity comes from the size of a thread pool and the time each transaction takes on a thread. Pools normally sit behind a queue that absorbs bursts. If that queue is unbounded and arrivals stay above capacity, it grows without limit: latency climbs past anything acceptable, memory eventually runs out, and the system fails.[3] Trouble starts before that. In the talk he compares the out-of-memory crash to dying of pneumonia: it is the final cause, but the disease came first, and the disease is cache overrun.[5] Because the queue is first-in, first-out, the item a consumer picks up next is the one that has waited longest; once the queue outgrows the processor cache, that item has already been evicted, so consumers take cache misses at exactly the moment they are falling behind. They slow down, the queue grows faster, and memory fills.[3][5] On Linux, memory overcommit lets allocations succeed until the memory is actually used, and then the OOM Killer (out-of-memory killer) terminates processes.[3] Figure 14.6 lets you push a queue past capacity both ways.

Little’s law

Thompson’s analogy is an art gallery that can hold 30 viewers. Each viewer browses for 20 minutes on average, and with more than 30 inside, nobody can see the paintings, so they are unlikely to buy or come back. The overflow is sent to a café down the road and invited back later. By Little’s law, the gallery can admit at most 90 people an hour; if 100 arrive between 9:00 and 10:00, ten go to the café.[3] The law itself is:[4]

Little’s law

L = λ × W

L is the long-term average number of items in the system, λ (lambda) the long-term average rate at which items actually enter it, and W the average time an item spends inside.[4]

It needs no assumptions about how arrivals or service times are distributed, or about the order of service. It holds for any stable system over the long run (Wikipedia’s term is ergodic), and for any part of one, such as a single bank teller inside a bank.[4] One detail matters for back pressure: λ is the effective arrival rate. In a system that turns customers away, it is lower than the rate of customers who tried to arrive.[4] Philip Morse published the form L = λW and challenged readers to find a case where it fails; John Little published a proof in 1961 that none exists.[4]

Wikipedia’s examples: a server with 9 jobs queued and 1 in service, completing 50 jobs per second, has a mean response time of 10 ÷ 50 = 0.2 seconds; a store whose customers arrive at 10 an hour and stay half an hour holds 5 on average. If advertising doubles arrivals to 20 an hour, the store must hold about 10 at once or cut the average stay to a quarter of an hour.[4] Figure 14.7 solves the law for any of its three terms.

Thompson’s quick version in the talk: if a worker takes time X on average per item and its queue holds 10 items, the last item waits about 10X before its work completes, so you can predict response times from queue lengths.[5] That is Little’s law rearranged, since one worker finishing an item every X has a throughput of 1/X, and W = L ÷ λ = 10 ÷ (1/X) = 10X.[4]

Sizing a bounded queue

Thompson names three variables that decide response time: the time a transaction takes on a thread, the number of threads working in parallel, and the length of the input queue, which sets the longest a job can wait.[3] From them he derives:[3]

max latency  = (transaction time / number of threads) × queue length
queue length = max latency / (transaction time / number of threads)

With Figure 14.6’s numbers, 40 ms per transaction across 4 threads means the queue drains one job every 10 ms. A 500 ms latency target therefore allows a queue of 500 ÷ 10 = 50 jobs. This is Little’s law in another form: 4 threads finishing a job every 40 ms is a throughput of 100 per second, and 50 jobs ÷ 100 per second is 0.5 seconds. Without a bound there is no maximum latency at all, so a guaranteed response time requires a bounded queue.[3] Thompson adds that cutting per-transaction time is one of the biggest wins, since it improves both the best and the worst case.[3]

The talk applies the same rule to individual units of work. Unbounded queries, such as “every transaction on my account”, can run on and on, and get spectacularly worse when nested. Giving every unit of work an upper bound (for example, at most 100 rows per database request) keeps the work in manageable chunks whose cost you can measure.[5]

How pressure travels upstream

Thompson’s example system (Figure 14.8) has a gateway whose thread pools accept user requests, and an asynchronous transaction service behind it, joined by an input and an output FIFO (first-in, first-out) queue. The gateway only translates protocols and handles border security; a web container running servlets is his example. The transaction service holds the domain model and may use a durable store.[3]

When the transaction service’s bounded input queue is full, the gateway thread trying to add to it blocks. That pushes back on whoever is sending to the gateway; over TCP, the senders’ network buffers fill up, and the pressure can travel all the way back to the customer. For a synchronous protocol such as REST, the gateway can instead answer with HTTP 503 when its incoming queue is full.[3] Each service’s queues should be sized so that together they meet the end-to-end quality-of-service target.[3]

In the talk he walks the chain from the far end: the storage system cannot keep up, so the transaction thread blocks, its input queue backs up, the thread feeding that queue can no longer take network packets, and eventually the system stops reading new work from the network at all. His analogy is a coffee shop that lets in only so many people and asks the rest to come back later, the equivalent of an HTTP 503. Denying new input while still serving up to maximum capacity is a better experience than a crash.[5]

Look at the whole path, too: a slow client reading its response can tie up gateway threads and cut throughput for everyone.[3]

Retrying with exponential backoff

A rejected client should not retry immediately, or every rejected client retries together. Exponential backoff is a feedback algorithm that slows a process down after adverse events, such as failed connections, collisions, error responses or an explicit request to back off, until it finds an acceptable rate.[7]

  • Each further adverse event multiplies the delay by a base b. Binary exponential backoff uses b = 2: retry after 1 s, then 2 s, then 4 s.[7]
  • Truncated backoff caps the number of doublings so the delay stops growing.[7]
  • Randomization: if every sender waits exactly the same time, they retry together and collide again, so the delay is drawn at random from a range that the backoff sets. A wider range means fewer collisions but more average waiting.[7]
  • For web services, the benefit is that clients need no prior knowledge of the limits; the rate adjusts on its own under heavy load.[7]

Ethernet is the classic case. After the c-th collision, a sender waits a random number of slot times from 0 to 2c − 1; IEEE 802.3 truncates the exponent at 10 (Table 14.3).[7] Figure 14.9 replays three senders that collided at the same moment, one retry at a time.

Watching and testing the queues

Thompson recommends monitoring queues and threads and acting when a threshold is crossed, such as raising an alert when a queue reaches 70% full, and sampling transaction times to check they stay in the expected range.[3] In the post’s comments he notes that some input cannot be rejected, such as a market data feed; then latency keeps growing until the system fails, and for trading it is better to drop stale data and work from the latest view.[3]

The talk adds what visible queues buy you:[5]

  • Insight. With queue lengths and average processing times, you can work out the average response time users get and the transactions per second flowing through.
  • Testability. Components joined by queues are decoupled, so each can be load-tested on its own by feeding its input queue and draining its output, which gives faster feedback than a full end-to-end run.
  • Capacity planning. CPU, memory and I/O utilization are useful but not enough. Response times and filling queues, higher up the stack, reveal an underlying problem sooner.
  • Testing to breaking point. Load-test until the system breaks and look at how it breaks. A design with bounded queues and back pressure levels off at maximum capacity, denies new requests and serves the rest at the same rate, instead of falling off a cliff. Test fail-over under heavy load as well, since cascading failures usually happen under stress, not when the system is idle.

14.4Disadvantages of asynchronism

  • Use cases such as inexpensive calculations and realtime workflows might be better suited to synchronous operations, as introducing queues can add delays and complexity.[1]
  • Queues bring failure modes of their own: brokers can lose messages or deliver them twice (14.1), so consumers may need to be idempotent,[14] and a queue that is not bounded can grow until the process runs out of memory (14.3).[3]
  • The user sees a result before the work is done, so the interface has to report progress later, for example by polling.[2]
