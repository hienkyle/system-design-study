SYSTEM DESIGN PRIMER · UNIT 15

Communication

Every request in a system travels through a stack of protocols. This unit starts at the top with HTTP, drops to the two transport protocols beneath it, TCP (reliable, ordered, slower) and UDP (fast, with no guarantees), and then climbs back up to the two main ways of designing an API on top: RPC, which exposes operations, and REST, which exposes resources.[1]

15.0Layers and HTTP

The OSI model

The primer opens the section with the OSI (Open Systems Interconnection) 7-layer model in Figure 15.1. Each layer serves the one above it. From the bottom: the physical layer moves raw bits over cables; the data link layer moves frames between neighbouring nodes using MAC addresses; the network layer routes packets by IP address; the transport layer makes sure messages arrive error-free, in sequence and without losses or duplication; the session layer sets up and ends conversations between processes; the presentation layer converts, compresses and encrypts data; and the application layer is the window through which programs use the network.[1]

This unit lives on two of those layers. HTTP is an application-layer protocol; TCP and UDP are transport-layer protocols, carried over IP at the network layer.[1][6]

The top Quora answer the primer links, on how HTTP differs from TCP, walks the same stack using the simpler five-layer TCP/IP model and explains what each layer adds:[24]

  • Physical: electrical signals, light pulses or radio waves. It has standards for voltages and frequencies rather than protocols.
  • Link: devices that share one medium, using protocols such as Ethernet or Wi-Fi (802.11). This is how your computer reaches your home router.
  • Network: mostly IP. Routers carry traffic between networks, so you can reach a computer on the other side of the world without knowing where it is.
  • Transport: delivers the message to the right program on that computer, usually by port number. TCP reorders packets and resends lost ones; UDP is less reliable but has less overhead.
  • Application: what the programs say to each other. HTTP for the web, SMTP, IMAP and POP3 for email, SSH and RDP for remote administration, and thousands more.

Its short version: TCP is a transport-layer protocol, and HTTP is an application-layer protocol that runs over TCP. The answer adds that the layers are conceptual and some protocols span them.[24] Its example, TLS (the encryption behind HTTPS), indeed fits no single layer, but it runs on top of a reliable transport such as TCP, so it sits above the transport layer, not below it as the answer suggests.[29]

HTTP

HTTP (Hypertext Transfer Protocol) is a method for encoding and transporting data between a client and a server. It is a request/response protocol: clients issue requests, and servers answer with the relevant content plus completion status information about the request.[1] F5’s glossary (the primer’s NGINX link) adds that the name comes from the hypertext documents it was built to exchange, and that clients use it to fetch text, images, video and application data.[2]

Because each request and response is self-contained, it can flow through many intermediate routers and servers that perform load balancing, caching, encryption and compression, such as the load balancers, reverse proxies and caches of Units 9, 10 and 13.[1][2] Headers carry information about state and capabilities between client and server, and F5 notes that they often affect application performance.[2] HTTP relies on lower-level protocols such as TCP and UDP.[1] Today’s HTTP/3, for example, runs over QUIC, a reliable transport built on top of UDP.[7]

Verbs and their guarantees

A basic HTTP request consists of a verb (method) and a resource (endpoint).[1] Table 15.1 lists the common verbs with three properties that matter for system design:

  • Idempotent: can be called many times without different outcomes.[1]
  • Safe: read-only; the client asks for no change to the server’s state. Every safe method is also idempotent, but not every idempotent method is safe: PUT and DELETE change state.[22]
  • Cacheable: the response can be stored and reused by a cache along the way. POST and PATCH responses qualify only if they carry freshness information.[1]

Idempotency is what makes a request safe to retry. A client that timed out does not know whether its request took effect; resending an idempotent request cannot do extra harm, but resending a POST can create a second resource. PUT vs PATCH

Both update a resource, and the Laracasts thread the primer links shows how often they are confused.[3]

PUT · replace

  • Stores the entity at a given URI, replacing what is there or creating it.
  • The payload must be the complete resource; in the best answer’s reading, fields not sent are set to null.
  • Idempotent.
  • Example: a location form that always submits City, Country, Zip and Address together.

PATCH · modify

  • The body holds instructions for changing an existing resource (RFC 5789), not a replacement.
  • Only updates a resource that exists; the change must be atomic.
  • Not idempotent: repeating it can give different results.
  • Example: changing only your name on a profile page.

The thread’s practical advice is that for ordinary web forms the choice is mostly convention, and it matters more for public APIs. One poster reported that a customer’s proxy did not recognise PATCH at all, so he used PUT with a flag for partial updates.[3]

15.1Transmission control protocol (TCP)

TCP is a connection-oriented protocol over an IP network. A connection is established and terminated with a handshake, and all packets sent are guaranteed to reach the destination in the original order and without corruption.[1] IP itself promises none of this: packets are passed from computer to computer with no guarantee of delivery, and they can take different paths, arriving out of order or twice. TCP builds a reliable, ordered stream on top, so a program reads and writes it much like a file.[4]

Opening and closing a connection

A TCP connection has three phases.[6]

  1. Establishment. The server listens on a port (a passive open). The client starts a three-way handshake: it sends SYN with a random sequence number x; the server answers SYN-ACK, acknowledging x + 1 and sending its own random number y; the client sends ACK for y + 1. Both directions are now open, so the connection is full-duplex.
  2. Data transfer. Sequence numbers, acknowledgements, retransmission, flow control and congestion control all work in this phase.
  3. Termination. Each side closes its own half with a FIN, which the other side acknowledges, usually four messages in all. The side that sent the first FIN then waits in TIME-WAIT (commonly 30 seconds, 1 minute or 2 minutes) before its port is freed.

Figure 15.4 steps through one connection. Switch to Segment lost to watch TCP recover a missing segment.

How delivery is guaranteed

The primer names two mechanisms: sequence numbers and checksum fields for each packet, and acknowledgement packets with automatic retransmission.[1] Wikipedia fills in how each works:[6]

Sequence numberA 32-bit number for each byte of the stream, starting from a random value. The receiver uses it to put segments back in order and drop duplicates.
Acknowledgement (ACK) numberThe next byte the receiver expects, which confirms every byte before it. It is cumulative, so a receiver cannot acknowledge past a gap.
Selective ACK (SACK)An option (RFC 2018) that lets the receiver also report blocks it holds beyond a gap, so the sender resends only what is missing.
ChecksumA 16-bit ones’-complement sum over the header, the data and a pseudo-header that includes the IP addresses. It is weak by modern standards and is normally backed by a stronger check (CRC) at layer 2.
Retransmission timeout (RTO)If no ACK arrives in time, the segment is resent and the timeout doubles each time (exponential backoff, as in Unit 14).
Fast retransmitThree duplicate ACKs for the same byte signal a lost segment, so the sender resends it without waiting for the timer. Waiting for three avoids resending for mere reordering.

If the sender does not receive a correct response, it resends. If there are multiple timeouts, the connection is dropped,[1] and the application is told that its data could not be delivered.[6]

Flow and congestion control

TCP also implements flow control and congestion control.[1] The two are easy to mix up because both slow the sender down, but they protect different things.

  • Flow control stops a fast sender from overwhelming a slow receiver.[21] It uses a sliding window: rather than waiting for an ACK after every frame (stop-and-wait), the sender may have a whole window of data in flight, and the window moves forward as ACKs arrive.[21] In TCP the receiver advertises its window in a 16-bit header field. When it advertises a zero window, the sender stops and sends small probes until space opens up.[6]
  • Congestion control protects the network, limiting how much traffic enters it so that it does not collapse.[20] The danger is real: in October 1986 the NSFNET backbone fell from 32 kbit/s to 40 bit/s, a congestive collapse that lasted until hosts adopted Van Jacobson and Sally Floyd’s congestion control in 1987–88.[20] Modern TCP combines four algorithms (slow start, congestion avoidance, fast retransmit and fast recovery) and treats packet loss as a sign of congestion, cutting its sending rate in response.[6] Slow start, for example, keeps a new connection from flooding routers before congestion can be detected.[20]

What the guarantees cost

These guarantees cause delays and generally make TCP less efficient than UDP.[1] Three costs come up in the sources:

  • Head-of-line blocking. Data that arrived after a lost segment waits, unusable, until the lost one is resent and received.[4][6] Figure 15.7 shows what this does to a game.
  • Nagle’s algorithm. TCP may hold small writes for up to 200 ms to bundle them into one packet, which delays small, frequent messages such as keystrokes or player input. The TCP_NODELAY socket option turns this off.[4][6]
  • Open connections. To ensure high throughput, web servers can keep a large number of TCP connections open, which uses a lot of memory. Keeping many connections between web server threads and, say, a memcached server is expensive. Connection pooling helps, as does switching to UDP where applicable.[1] A connection pool is a cache of established connections that the application reuses instead of opening a new one for each request.[18] Section 15.2 shows how Facebook did both.

When to use TCP

TCP is useful for applications that require high reliability but are less time-critical.[1] Examples, with their usual ports, are web servers (HTTP, 80), database info, email (SMTP, 25), file transfer (FTP, 21) and remote shells (SSH, 22).[1][5]

Use TCP over UDP when
  • You need all of the data to arrive intact.
  • You want to automatically make a best-estimate use of the network throughput.[1]

15.2User datagram protocol (UDP)

UDP is connectionless. Datagrams (analogous to packets) are guaranteed only at the datagram level: they might reach their destination out of order or not at all, and UDP does not support congestion control. Without TCP’s guarantees, UDP is generally more efficient.[1]

Designed by David P. Reed in 1980 and defined in RFC 768, UDP needs no handshake and does not track what it has sent. It adds only two things to IP: port numbers for addressing and a checksum for integrity.[7] It also keeps message boundaries. TCP delivers a byte stream, so one read may return parts of several messages; with UDP, one read returns one whole datagram.[5][7]

An 8-byte header

The difference in features shows in the headers (Figure 15.6). A TCP header is at least 20 bytes and up to 60 with options;[6] a UDP header is 8 bytes in four 16-bit fields. The UDP checksum is optional over IPv4 and mandatory in most IPv6 cases. Since the length field is 16 bits, a datagram is at most 65,535 bytes; over IPv4 that leaves at most 65,507 bytes of data.[7]

Broadcast and DHCP

UDP can broadcast, sending datagrams to all devices on the subnet. This is useful with DHCP, because the client has not yet received an IP address, so TCP has no way to stream to it.[1] DHCP is the protocol that hands a device its IP address and other settings when it joins a network. It runs over UDP, with servers on port 67 and clients on port 68, in four steps known as DORA: discover, offer, request, acknowledge. A new client sends its DHCPDISCOVER from the address 0.0.0.0 to the broadcast address 255.255.255.255.[19] Broadcast and multicast are also used for service discovery and by routing protocols such as RIP.[7]

Real-time traffic

UDP is less reliable but works well in real-time use cases such as VoIP, video chat, streaming and real-time multiplayer games.[1] The top Stack Overflow answer on TCP vs UDP, whose wording the primer follows closely, puts it as a trade: UDP is more efficient because it sends no acknowledgements, so it suits real-time communication where losing a small percentage of packets is better than paying for a TCP connection.[28] Glenn Fiedler’s article, the first in his Networking for Game Programmers series, explains why with a game where the client sends input every frame and the server sends back positions every frame.[4]

  • This data only matters while it is recent. When a packet is lost under TCP, the game freezes: newer packets have arrived but are held back, and when the resent packet finally lands it is already stale, and the backlog is delivered all at once.[4]
  • Spotting a loss takes at least one round trip, commonly two, plus a one-way trip for the resend. At a 125 ms ping, Fiedler estimates the wait at about a fifth of a second at best and half a second or more in bad conditions. It is built into TCP’s promise of a reliable, ordered stream and cannot be tuned away.[4]
  • With UDP, the lost update is simply gone, and the next one replaces it. The cost is that UDP adds almost nothing to IP: typical loss is around 1–5%, the 16-bit checksum is too weak to rely on at high rates, and the programmer must handle connections, splitting data, reliability and flow control.[4]

Fiedler’s advice for games is to use UDP for the game protocol alone and to build whatever reliability, ordering or congestion avoidance it needs on top of UDP. Mixing in a TCP connection for “important” messages is a trap: both share IP, and TCP’s own reliability and flow control tend to cause loss in the UDP traffic. Unrelated services, such as calling a REST API over HTTP during play, are fine.[4] QUIC, the transport under HTTP/3, follows the same idea at internet scale: reliable, secure connections built on UDP.[7]

Use UDP over TCP when
  • You need the lowest latency.
  • Late data is worse than loss of data.
  • You want to implement your own error correction.[1]

Both at once: memcache at Facebook

The primer links Facebook’s NSDI 2013 paper Scaling Memcache at Facebook, which picks a protocol per operation.[8] (memcached is the in-memory cache from Unit 13.)

Gets · UDP

Reads use UDP to cut latency and overhead. Because UDP has no connections, each web server thread talks to memcached servers directly, with nothing to set up or keep open. Dropped or out-of-order packets are detected with sequence numbers and treated as errors; the client counts the get as a cache miss and does not retry.[8]

Sets and deletes · TCP

Writes must confirm that state changed, so they go over TCP through mcrouter, a local proxy. TCP removes the need to build retries on top of UDP, and mcrouter coalesces connections, since keeping a TCP connection between every web thread and every memcached server would cost too much memory.[8]

The trade paid off. At peak load 0.25% of get requests are discarded (about 80% from late or dropped packets, the rest from out-of-order delivery), while UDP cut request latency by 20% compared with TCP through mcrouter. In lab tests it also beat TCP by 13% for single gets and 8% for 10-key multigets. Clients still add their own sliding window to cap outstanding requests, so that many responses do not swamp the rack and cluster switches at once, a problem called incast congestion.[8]

15.3Remote procedure call (RPC)

In an RPC, a client causes a procedure to execute in a different address space, usually a remote server. The procedure is coded as if it were a local procedure call, which hides from the client program the details of how to talk to the server. Remote calls are usually slower and less reliable than local ones, so it helps to tell RPC calls apart from local calls. Popular RPC frameworks include Protobuf, Thrift and Avro.[1]

How a call travels

RPC is a request-response protocol, and each part in Figure 15.8 has one job:[1]

  • Client program: calls the client stub procedure. The parameters are pushed onto the stack as for a local call.
  • Client stub procedure: marshals (packs) the procedure id and arguments into a request message.
  • Client communication module: the OS sends the message from the client to the server.
  • Server communication module: the OS passes the incoming packets to the server stub procedure (through the dispatcher in Figure 15.8).
  • Server stub procedure: unmarshals the message, calls the server procedure matching the procedure id, and passes it the arguments.
  • The response repeats these steps in reverse.

A stub is the stand-in that makes the remote procedure look local: the client’s stub looks like the real procedure, and the server’s stub looks like a normal caller. Step through one call in Figure 15.9.

Over HTTP, RPC calls name the operation in the URL (Listing 15.1). RPC is focused on exposing behaviours, and it is often used for performance reasons in internal communication, since you can hand-craft native calls to fit your use cases.[1]

Frameworks and IDLs

The three frameworks the primer names share one idea: you describe your data or service once in a language-neutral definition, and a compiler generates the stub and serialization code for each language. That definition is an IDL (interface definition language) file.[14][15]

  • Protocol Buffers (Protobuf) is Google’s language-neutral, platform-neutral, extensible way to serialize structured data. You define messages in a .proto file and the compiler generates code to read and write them (Listing 15.2). Google’s pitch is “XML, but smaller, faster, and simpler”. Supported languages include C++, C#, Dart, Go, Java, Kotlin, Objective-C, Python, Rust and Ruby.[14]
  • Apache Thrift pairs a software stack with a code-generation engine for cross-language services. You describe types and services in a .thrift file and generate code with the compiler’s --gen option; servers implement the services and clients call them.[15] Facebook created Thrift in 2006 and open-sourced it in 2007. By 2014 it ran more than 100 production services there, and Facebook released its rewrite, fbthrift, which added per-request headers (THeader) and out-of-order responses to avoid head-of-line blocking. Services that moved to the new C++ code saw latency fall by up to 50%.[11]
  • Apache Avro is a serialization format for record data, with strong support for schema evolution, and is a common choice for streaming data pipelines.[16]

When to choose RPC

The primer suggests a native library (an SDK) when:[1]

  • You know your target platform.
  • You want to control how your logic is accessed.
  • You want to control how error control happens off your library.
  • Performance and end-user experience are your main concern.

HTTP APIs following REST tend to be used more often for public APIs.[1]

The top answer to the Software Engineering question the primer links comes from someone who has built business systems with RPC, with REST, and with both at once. It grants that RPC brings problems of scale, error handling and type safety, especially across many hosts and languages, but names three cases where RPC fits better:[25]

Tight couplingThe components are designed to work together, a change to one will likely affect the others, and they are unlikely to talk to other systems later.[25]
Reliable communicationThey run on one host or on a network unlikely to see latency or packet loss. The system must still handle those cases.[25]
Uniform languageAll or nearly all components are in one language, and others are unlikely to be added.[25]

The answer also defends the IDL: a REST system needs code to convert requests and responses into its internal data too, and a well-commented IDL doubles as interface documentation, which a REST API has to write and maintain separately. Such components often need subsystems that fail independently, and it notes that Erlang, built for this, can be a better choice than RPC in another language. Its conclusion is that there is no single answer for inter-process communication; choose for the system at hand.[25]

Disadvantages of RPC

  • RPC clients become tightly coupled to the service implementation.[1] Ethereal Bits explains why: the available operations are fixed when the client is built, so when they change, client and server must be deployed together.[10] The top Stack Overflow answer on REST vs JSON-RPC calls coupling the fundamental problem with RPC, in three forms: clients must know procedure names; the order, types and number of parameters matter, so a signature is hard to change without breaking clients; and RPC exposes only endpoints and arguments, so a client cannot tell what it can do next.[26]
  • A new API must be defined for every new operation or use case.[1]
  • RPC can be difficult to debug.[1]
  • You might not be able to use existing technologies out of the box. For example, it can take extra effort to make sure RPC calls are cached properly on caching servers such as Squid,[1] a caching proxy for HTTP, HTTPS and FTP that serves repeat requests from stored copies.[17] A plain HTTP response has well-defined inputs (query string, headers, body), so a cache can sit in front of it without extra work. An RPC call may span several messages, may pass its inputs in a non-standard way, and may lack the metadata a cache needs.[10]

15.4Representational state transfer (REST)

REST is an architectural style that enforces a client/server model in which the client acts on a set of resources managed by the server. The server provides a representation of resources and actions that can either change them or get a new representation of them. All communication must be stateless and cacheable.[1]

Four qualities

A RESTful interface has four qualities:[1]

Identify resources (URI in HTTP)Use the same URI regardless of the operation.
Change with representations (verbs in HTTP)Use verbs, headers and the body.
Self-descriptive error messages (status codes in HTTP)Use the standard status codes; don’t reinvent the wheel.
HATEOAS (HTML interface for HTTP)Your web service should be fully accessible in a browser.

REST is focused on exposing data. It minimises coupling between client and server and is often used for public HTTP APIs. It exposes resources in a generic, uniform way: resources through URIs, representations through headers, and actions through verbs such as GET, POST, PUT, DELETE and PATCH. Being stateless, REST is well suited to horizontal scaling and partitioning,[1] because any server can handle any request (Unit 9).

HATEOAS

HATEOAS stands for Hypertext As The Engine Of Application State. Responses contain links to the actions available right now, so the client discovers what it can do and where to do it from the response itself, instead of knowing in advance.[12] The REST Cookbook’s example is a bank account: in credit it offers deposit, withdraw, transfer and close; overdrawn, it offers only deposit.[12] Ethereal Bits describes the same idea: the client starts from a single top-level URI and follows the links the server gives it at run time. It notes that this is harder for service-to-service calls, because programs are not naturally good at consuming APIs they discover at run time.[10]

The Stack Overflow answer on REST vs JSON-RPC lists what REST gains by putting this kind of control information into representations and headers:[26]

  • Links carry link relation types that say what each URI means, and the answer calls them mandatory.
  • Clients depend on message formats (media types) rather than procedure names and arguments, so existing libraries for formats such as Atom, HTML, Collection+JSON and HAL can be reused.
  • URIs can change without breaking clients, as long as the clients depend only on registered or domain-specific link relations.
  • Representations can embed form-like structures, which a client can show as a UI when the user is a person.
  • Caching support and standardised status codes come with it.

Representation through headers

The primer links know-your-http-well for how REST uses headers.[1] It groups them into representation headers, which describe the data being sent, plus request and response headers for controls, conditionals, content negotiation, authentication and context.[13] Table 15.3 picks a few that come up in this guide.

Disadvantages of REST

  • Because REST exposes data, it may fit poorly when resources are not naturally organised or accessed in a simple hierarchy. “All records updated in the past hour that match a set of events” is not easily expressed as a path, and is likely to end up as a mix of URI path, query parameters and perhaps a request body.[1]
  • REST typically relies on a few verbs (GET, POST, PUT, DELETE and PATCH), which sometimes do not fit your use case. Moving expired documents to an archive folder, for example, does not map cleanly onto any of them.[1]
  • Fetching complicated resources with nested hierarchies takes multiple round trips to render a single view, such as a blog entry and then its comments. For mobile apps on variable networks these round trips are highly undesirable.[1]
  • Over time, more fields are added to a response, and older clients receive all of them, even those they do not need. This bloats the payload and adds latency.[1]

The first two points come from the top Quora answer the primer links (its example is “records updated in the last 3 hours containing the word cat”). That answer adds a further criticism:[27]

  • Statelessness is often a myth in practice. REST APIs end up relying on headers for state, for example to route follow-up requests to the server that handled the previous update, or for authentication. Using headers this way is clumsy and ties the API to HTTP as its transport.[27]

The answer’s author goes further and calls the reliance on REST an outgrowth of HTTP’s success, arguing that a general request/response approach such as JSON-RPC allows more expressive, less cumbersome APIs.[27] That is one person’s view; 15.5 sets it against the others.

REST, HTTP and RPC are not opposites

Ethereal Bits’ Debunking the myths of RPC & REST, linked by the primer, argues that “RPC vs REST” is partly a false choice.[10]

  • REST is a set of constraints, not a protocol, so a RESTful service can be built on top of any RPC mechanism.
  • HTTP is one implementation of REST, not the same thing; REST does not require HTTP’s particular verbs.
  • Avoid design by fad. The post cites Roy Fielding’s dissertation, where REST was defined, warning against choosing an architecture before knowing whether the requirements call for it.
  • The real decision is whether to expose resources through plain HTTP or through a higher-level layer such as SOAP or XML-RPC. Plain HTTP has benefits of its own, such as cacheability, and they are separate from the benefits of REST.

Which one wins?

Arnaud Lauret’s 2015 post on API Handyman, the source of Table 15.4, scores the two styles on seven criteria (Table 15.5). REST wins one and the rest are draws.[9]

His conclusion is that RPC and REST are different approaches with trade-offs, each valuable in its context, and that they can be mixed within one API. He advises pragmatism over fashion, while personally preferring resources for their predictability and their use of the whole HTTP protocol.[9]

What the linked answers recommend

The community answers the primer links pull in different directions, and each gives its reason. The REST vs JSON-RPC answer favours REST because it keeps clients loosely coupled.[26] The REST-drawbacks answer favours JSON-RPC for more expressive APIs.[27] The Software Engineering answer picks RPC for tightly coupled, single-language components on a reliable network.[25] Read together, they agree with Lauret: the choice depends on who the clients are and how much they must be allowed to change independently.[9]

Three sources on caching

The primer lists caching as an RPC disadvantage.[1] Ethereal Bits explains the cause: non-standard inputs that a cache cannot key on.[10] Lauret adds the fix: send reads as GET requests and RPC caches like REST.[9] The three agree; the cost comes from POST-only calls, not from naming operations.

Key terms · Unit 15
Layers and HTTP
OSI model
Seven layers from physical (1) to application (7).
Frame · packet · datagram
Data link unit · network (IP) unit · UDP unit.
HTTP
Application-layer request/response protocol.
Verb · resource
Method (GET, POST…) · endpoint it acts on.
Idempotent
Repeating it gives the same outcome.
Safe
Read-only; all safe methods are idempotent.
Cacheable
Response can be stored and reused.
PUT · PATCH
Replace whole resource · apply partial change.
TCP/IP model
Five layers: physical, link, network, transport, application.
TLS
Encryption behind HTTPS; runs on top of TCP.
Header
Metadata on a request or response.
TCP
Connection-oriented
Sets up a connection before sending.
Three-way handshake
SYN → SYN-ACK → ACK.
FIN · TIME-WAIT
Close one direction · wait before freeing the port.
Full-duplex
Both sides send at once.
Sequence number
Numbers each byte to restore order.
ACK · cumulative
Next byte expected; confirms all before it.
SACK
Also reports blocks held past a gap.
Checksum
16-bit integrity check; weak.
RTO
Retransmit timer; doubles each retry.
Fast retransmit
Resend after 3 duplicate ACKs.
Flow control
Don’t overwhelm the receiver.
Sliding window · zero window
Data allowed in flight · receiver full, sender pauses.
Congestion control
Don’t overwhelm the network.
Congestive collapse
Useful traffic stalls under overload (1986).
Slow start
New connections ramp up their rate gradually.
Head-of-line blocking
Later data waits for a lost segment.
Nagle · TCP_NODELAY
Bundle small writes (≤200 ms) · turn it off.
Connection pool
Reuse open connections.
UDP
Connectionless
No setup; each datagram stands alone.
Port
16-bit number naming a service on a host.
Broadcast · multicast
To every device on the subnet · to a group.
DHCP · DORA
Assigns IP addresses · discover, offer, request, ack.
QUIC
Reliable transport on UDP; under HTTP/3.
mcrouter · coalescing
Memcache proxy · sharing few TCP connections.
Incast
Many replies swamp a switch at once.
RPC
RPC
Call a remote procedure as if local; exposes behaviours.
Address space
A process’s own memory; RPC crosses it.
Stub
Local stand-in that marshals and unmarshals.
Marshal · unmarshal
Pack arguments into a message · unpack.
Dispatcher
Routes a request to the matching server stub.
IDL
Language-neutral definition compiled into code.
Protobuf · Thrift · Avro
Google’s format · Facebook’s framework · record format with schema evolution.
SDK
Native client library for a service.
Tight coupling
Client must change when the service does.
Squid
Caching proxy server.
REST
REST
Architectural style over resources; exposes data.
Representation
The form a resource is sent in (JSON, XML).
Stateless
Each request carries all it needs.
URI
Identifies a resource whatever the operation.
Status code
Standard result, e.g. 200, 404, 503.
HATEOAS
Responses link to the actions allowed now.
Content-Type · Accept
What this is · what I’ll take.
ETag
Version tag used for conditional requests.
Link relation
Label saying what a link means (e.g. deposit).
Media type
Message format a client relies on (HAL, Atom).
JSON-RPC
RPC with JSON messages; an alternative to REST.
