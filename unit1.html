SYSTEM DESIGN PRIMER · UNIT 1

Scaling fundamentals: from one server to many

Before the individual topics, the primer asks you to build a basic picture of the common principles: what they are, how they are used, and their pros and cons. It does that in two steps: one lecture and one article series.[1] This unit covers vertical vs horizontal scaling, load balancing and sticky sessions, RAID, caching, database replication and partitioning, and high availability and firewall basics, then the clone, database, cache and job-queue recipe from “Scalability for Dummies”.

1.1Scaling a web app, one tier at a time

Based on Harvard CS75 Lecture 9: Scalability (David Malan), Step 1 of the primer.[2] The lecture grows a single web server into a redundant system, fixing one bottleneck at a time.[5]

Vertical scaling

Vertical scaling means handling more load by buying a bigger machine: more or faster CPU cores, more RAM, more or faster disk.[4] A single core works on one task at a time; more cores let a server truly run that many requests in parallel. For disks, server-class SAS drives spin faster than typical desktop SATA drives (15,000 RPM is cited), which is why write-heavy databases often sit on them, and SSDs are faster again because they have no moving parts.[3]

Pros

  • Simplest to reason about: one machine
  • Data stays consistent in one place

Cons

  • Hardware has a ceiling
  • Top-end hardware is expensive
  • The one machine is a single point of failure

Horizontal scaling & load balancing

Horizontal scaling means adding more machines of ordinary capability instead of one exceptional machine, and spreading traffic across them.[4] As soon as there is more than one server, something has to decide where each request goes. That is the job of a load balancer.

  • The domain resolves to the load balancer’s public IP. Back-end servers can use private IP addresses, which saves scarce IPv4 addresses and keeps them unreachable from outside except through the balancer.[3][4]
  • The balancer can send each request to the least busy server, or split work by content type (for example, images from one group of servers and HTML from another).[3]
  • Implementations exist in software (Amazon Elastic Load Balancer, HAProxy, Linux Virtual Server) and in more expensive hardware (Barracuda, Cisco, Citrix, F5).[3]

Round-robin DNS

The cheapest way to balance is in DNS itself: the name server answers each lookup with the next IP address in a list (server 1, server 2, …), so clients talk to the back ends directly without a central balancer.[4] It is not very smart. It ignores how busy each server is, and because DNS answers are cached for their TTL (time to live), one heavy user can keep landing on the same server long after the rotation has moved on.[3]

Sessions & sticky sessions

Horizontal scaling breaks sessions. By default, PHP keeps session data in files on the local disk of the server that handled the request. If the next request is balanced to a different server, that file isn’t there, and the user appears to be logged out.[3] The lecture discusses two families of fixes:

  1. Share the state. Factor sessions out into a service every server can reach, such as a shared file server or a database, so it no longer matters which server answers.[4] This shared store then needs its own redundancy, which is where RAID and replication come in.
  2. Make sessions sticky. Send a returning user to the same back end every time (also called session affinity). The balancer can do this with a cookie: it sets one on the first response and reads it on later requests.[4] Putting a server’s private IP in that cookie leaks internal addressing, so a better design stores a random identifier that only the balancer can map to a server.[3]

RAID

To make a single server (such as the shared session store) survive disk failure, the lecture introduces RAID, a redundant array of independent disks: several drives combined using striping, mirroring or parity.[4][6]

Table 1.1 The RAID levels discussed in the lecture

RAID 1Mirroring: identical copy on each drive2All but one driveRedundancy; replace the dead drive and it rebuilds

Drive counts and fault tolerance are from the standard RAID level definitions.[6] RAID protects against hardware failure only; it does not replace backups.

Caching

The lecture then looks at avoiding work the server has already done, at several levels.

Bytecode caching (“PHP acceleration”)

PHP normally re-parses and compiles each script on every request, then discards the result. An accelerator keeps the compiled form for reuse until the file changes; Python’s .pyc files follow the same idea.[3] Today this is built into PHP as OPcache, which keeps precompiled bytecode in shared memory.[7]

Generating static HTML

A site can render dynamic pages once and save them as .html files, because web servers serve static files extremely fast. Craigslist is the lecture’s example. The costs are disk space, the same markup repeated in thousands of files, and pain when you later want to change the layout of every page.[3][4]

MySQL query cache

MySQL could cache the results of identical queries.[4]

Changed since 2012

The MySQL query cache was deprecated in 5.7.20 and removed in MySQL 8.0, because it scaled poorly on busy multi-core servers.[8] Learn the concept, but don’t plan on this feature.

Memcached

Memcached is a separate in-memory cache server that stores whatever you put in it in RAM. Facebook relied on it heavily because its workload was mostly reads.[3][4] Since RAM is limited, the cache must expire entries; evicting the ones used least recently makes room for new data.[3]

Storage engines

MySQL lets each table choose a storage engine, and the choice affects performance.

Database replication

Replication means automatically keeping copies of the database on more than one server.[4]

  • Master-slave. Every write goes to the master, which replays it on one or more slaves, so each slave holds an identical copy. Reads can be load-balanced across the slaves, which suits read-heavy sites. If the master dies, a slave can be promoted, but until then writes have nowhere to go: the master is a single point of failure for writes.[3][4]
  • Master-master. Two masters each accept writes and replicate to each other, so losing either one still leaves a master.[3][4]

Partitioning & high availability

Partitioning splits data across servers instead of copying it. Early Facebook is the lecture’s example: each school network ran on its own servers, so adding a school meant adding servers, at the cost that users could at first only see their own network. Data can also be split by a property such as last name, with A–L on one database and M–Z on another.[3]

High availability means a pair of machines watch each other through heartbeats (small periodic messages) and one takes over if the other goes quiet.[3] Applied to the load balancer itself, which would otherwise be a new single point of failure:

  • Active-active: both balancers accept traffic; if one stops responding, the other takes over its IP and handles everything.[3][4]
  • Active-passive: one balancer handles traffic while the other waits, and is promoted only if the active one fails.[4]

Repeat the idea at a larger scale and you get global load balancing, which routes users between whole data centres by region and availability.[3]

Security

The lecture ends by asking what traffic should be allowed into the data centre at all. The answer follows the principle of least privilege: a firewall opens only the ports each tier needs.[3]

Table 1.3 Firewall rules discussed in the lecture

TCP 80HTTPFrom the internet to the load balancer
TCP 443HTTPSFrom the internet to the load balancer only. The balancer decrypts (SSL offloading), so internal traffic can be plain HTTP.
TCP 22SSHClosed to the public; administrators come in through a VPN first
TCP 3306MySQLOnly between web servers and the database, never from outside

1.2Clones, databases, caches & async work

Based on Scalability for Dummies, Step 2 of the primer. It is a four-part blog series by Sebastian Kreutzberger, written as his answer to the question of what it takes to make a web service massively scalable.[12][13] Each part fixes the bottleneck that the previous part exposes.

Part 1 · Clones

Public servers sit behind a load balancer that spreads user requests evenly over a cluster of application servers. A user may hit server 2, then server 9, then server 2 again, and must get the same result each time. That leads to the series’ first golden rule:[12]

every server contains exactly the same codebase and does not store any user-related dataScalability for Dummies, Part 1[11]
  • Sessions move to a centralised store reachable by all app servers: an external database or, faster, an external persistent cache such as Redis. “External” means in or near the same data centre, not on the app servers.[12]
  • Deployment must update every server so none keeps serving old code. The article recommends the tool Capistrano, while admitting it takes some learning outside Ruby on Rails.[12]
  • Images. Once servers hold no state, create an image of one (on AWS, an AMI, Amazon Machine Image) and use it as a “super-clone” for every new instance: boot it, deploy the latest code, and it’s ready.[12]

Part 2 · Database

Now the servers scale horizontally and handle thousands of concurrent requests, until the application slows and finally breaks down because of the database (“It’s MySQL, isn’t it?”). The fix is more radical than adding clones, and there are two paths.[12]

  • Path #1 keeps the “beast” running. Each new measure costs more time and money than the last, and the DBA soon starts talking about sharding, denormalization and SQL tuning.[12]
  • Path #2 is easier while the dataset is still small and easy to migrate. The sooner you move joins into application code, the less code you will have to change later.[12]

Part 3 · Cache

With a scalable database, users still wait when pages pull lots of data from it. The answer is a cache, and by “cache” the author always means an in-memory cache such as Memcached or Redis. He warns never to use file-based caching, because it makes cloning and auto-scaling servers painful.[12]

A cache is a simple key-value store sitting as a buffer between the application and the data store. The app asks the cache first and only goes to the main data source on a miss. It is fast because everything lives in RAM: Redis on a standard server can serve several hundred thousand reads per second, and writes, especially increments, are also very fast.[12]

Table 1.4 The two caching patterns in Part 3
#1 Cached database queries#2 Cached objects
KeyA hash of the SQL queryYour own key for an assembled object
ValueThe query’s result setA fully assembled dataset or class instance (e.g. a Product with prices, texts, pictures, reviews)
Main problemExpiration: when one table cell changes, every cached query that might include it has to be found and deletedNone highlighted; delete the object when its underlying data changes
StatusThe older, still most common patternThe author’s strong recommendation
Bonus–Enables asynchronism: workers assemble objects, the app reads the latest one and rarely touches the DB

Suggested objects to cache: user sessions (never in the database), fully rendered blog articles, activity streams, and user-to-friend relationships. The author prefers Redis for its extra database-like features (persistence, built-in lists and sets) but recommends Memcached if you only need caching, because it scales easily.[12]

Part 4 · Asynchronism

Picture a bakery that has no bread and tells you to come back in two hours. Asynchronism is how a web service avoids making its users “please wait a while”. There are two paradigms.[12]

Async #1 · Do the work in advance

“Bake at night, sell in the morning.” Do time-consuming work ahead of time and serve the finished result quickly. A common use is turning dynamic content into static content: pages are pre-rendered to HTML on every change, often by a script run hourly by a cronjob. Uploading those pages to AWS S3, CloudFront or another CDN lets a site handle millions of visitors per hour.[12]

Async #2 · Queue the work

Some requests can’t be foreseen, like a birthday cake with a custom name on it. For those, the work starts when the user asks, and the user is told to check back:[12]

To go deeper, the author points to the first three tutorials on the RabbitMQ website. RabbitMQ is one of many systems for async processing; ActiveMQ or a plain Redis list also work. His closing advice: if you do something time-consuming, try to do it asynchronously, because backends become nearly infinitely scalable and frontends stay snappy.[12]

Key terms · Unit 1
Scaling
Vertical scaling
Bigger machine: more CPU, RAM, disk. Simple, but capped and a single point of failure.
Horizontal scaling
More ordinary machines sharing the load.
Clone
An identical, stateless app server; launched from a machine image (AMI).
Single point of failure (SPOF)
One component whose failure takes the whole system down.
Traffic
Load balancer
Public entry point that spreads requests over back-end servers on private IPs.
Round-robin DNS
DNS hands out server IPs in rotation; ignores load and is skewed by caching.
TTL
How long a cached answer (DNS record, cache entry) stays valid.
Sticky session
Sending a user back to the same server, usually via a balancer cookie. Also “session affinity”.
SSL offloading
The balancer decrypts HTTPS so back ends don’t have to.
Reliability
RAID
Drives combined by striping (0), mirroring (1), parity (5, 6) or both (10).
Heartbeat
Periodic “I’m alive” message; silence triggers fail-over.
Active-active / active-passive
Both nodes serve traffic / one serves while the other stands by.
Least privilege
Open only the ports and access each tier needs.
Data
Replication
Automatic copies of a database on several servers.
Master-slave
Writes to master, reads from slaves; master is a write SPOF.
Master-master
Two masters both take writes and sync with each other.
Partitioning / sharding
Splitting data across servers (by school, by A–L / M–Z…).
Denormalization
Storing data redundantly so queries need no joins.
Storage engine
MySQL per-table engine: InnoDB (transactions), MyISAM, Archive.
Caching
In-memory cache
Key-value store in RAM (Memcached, Redis) between app and DB.
Cached query vs cached object
Key = hashed SQL (hard to expire) vs key = assembled object (preferred).
Bytecode cache
Reuse compiled scripts instead of recompiling (PHP OPcache, .pyc).
LRU eviction
When full, drop the least recently used entries.
Asynchronism
Precomputing
Do work ahead of time (e.g. cron renders static HTML, pushed to a CDN).
Job queue & workers
Frontend queues slow jobs; workers process them and signal completion.
Message broker
System that runs the queue: RabbitMQ, ActiveMQ, Redis list.
Trade-off
Every gain in scale costs something: money, complexity, freshness.
