SYSTEM DESIGN PRIMER · UNIT 16

Security

The primer keeps security short: unless your role needs deep security knowledge, you are expected to know the basics. This unit takes its four basics one at a time, encryption in transit and at rest, input sanitization against XSS, parameterized queries against SQL injection, and least privilege, then works through the three resources the primer links: an API security checklist, a security guide for developers and the OWASP Top Ten.[1]

16.0The four basics

What the primer asks for

The primer calls security a broad topic. Unless you have considerable experience, a security background, or are applying for a role that requires security knowledge, it says you probably won’t need more than these basics:[1]

  1. Encrypt in transit and at rest. Protect data both while it moves over the network and while it sits in storage.
  2. Sanitize all user inputs, and any input parameters exposed to the user, to prevent XSS (cross-site scripting) and SQL injection.
  3. Use parameterized queries to prevent SQL injection.
  4. Use the principle of least privilege.
The primer’s own note

The section opens by saying it could use some updates and invites contributions.[1] Its sources date mostly from 2016–2017, so this guide flags advice that has since changed in Fact check boxes.

Where each basic applies

Each basic guards a different point on a request’s path. Figure 16.1 places them on the kind of architecture built in earlier units: encryption on every hop and on disk, sanitization at the edge where input arrives, parameterized queries where the application talks to the database, and least privilege on every account in between.

16.1Encrypt in transit and at rest

The security guide for developers devotes a chapter to transport security (HTTPS) and explains storage through password hashing.[6][5] Both checklists the primer links start here too: the API checklist asks for encryption on all sensitive data and HTTPS with TLS 1.2 or newer, and the developer checklist opens with HTTPS everywhere and bcrypt for password hashes.[2][4]

The trouble with plain HTTP

Plain HTTP sends and receives data as plain text, so anyone on the same local network can read it: co-workers, or the people around you in a café.[6] The guide lists three ways that happens:

  • ARP poisoning. An attacker on the network poisons the ARP table so the switch delivers your packets to the attacker’s machine instead of yours (Figure 16.2).[6]
  • Owning the hardware. The café owner or your employer has physical access to the hub or switch and can program it, or can tap the wire coming into the building.[6]
  • A fake Wi-Fi network. A network named like the café’s may belong to an attacker. Phones and laptops remember networks and rejoin them automatically, which makes this easy.[5]

How HTTPS works

The S in HTTPS stands for Secure. HTTPS encrypts all data between browser and server with a symmetric key that both sides know, so only scrambled text crosses the network. The process by which the two sides agree on that key is the TLS handshake.[6] Step through the version the guide describes:

Fact check · TLS 1.3

The exchange above is the RSA key exchange of TLS 1.2 and earlier. Wikipedia notes it has no forward secrecy: anyone who later obtains the server’s private key can decrypt recorded traffic. TLS 1.3 (RFC 8446, 2018) removed static RSA key exchange and requires ephemeral (EC)DHE key agreement, so each session’s key is thrown away after use.[17] The goal, a shared symmetric key, is the same.

Certificates and authorities

The handshake alone has a gap: a man in the middle could generate a certificate of its own, pretend to be the server and send malicious content. Browsers close it by checking the certificate’s signature, which must come from one of the trusted certificate authorities (CAs) built into Chrome, Firefox, Safari and others. With no trusted signature, the browser warns the user. A server gets a signed certificate by proving its identity to a CA.[6] So HTTPS does two jobs:[6]

Authenticity

  • The domain shown in the browser is the one you are actually talking to.

Confidentiality

  • All communication between the browser and that domain is encrypted.

The guide describes two ways to get a certificate. The paid route: buy one from a CA, generate a certificate signing request on your server, prove you own the domain, then install the signed certificate. The free route: Let’s Encrypt, which can be free because the whole process of creation, validation and renewal is automated; EFF’s Certbot walks through setup for each server.[6]

Configuring TLS

The guide’s HTTPS chapter lists best practices with nginx examples, and points to Mozilla’s SSL configuration generator for Apache and other servers.[6] Table 16.1 pairs each with the attack it stops and, where the advice has aged, what applies now.

Pinning in mobile apps

HTTPS only helps while the trusted CAs deserve trust. Anyone holding a device can create their own CA, tell Android or iOS to trust it, and then sit between the app and the server, swapping in certificates generated on the fly. They act as the server to the app and as the client to the server, and read every API call.[6]

  • Certificate pinning hard-codes the server’s certificate in the app bundle and checks it before every API call. If the server’s certificate changes, or pinning is done wrong, users must update the app or it stops working.[6]
  • Public key pinning pins the server’s public key instead. Sites such as Google rotate certificates but keep the key, so the app survives rotation without an update.[6]

The guide also warns that a company-issued phone or laptop may have extra CAs installed so the company can read your traffic, and shows where to check them in iOS and Android settings.[6]

Fact check · pinning on the web

The developer checklist links pinning to HTTP Public Key Pinning (HPKP), a header that let websites pin keys. Browsers deprecated HPKP from 2017 and have since removed it (Chrome 72, Firefox 78) in favour of Certificate Transparency.[20] Pinning inside native apps, as described above, is unaffected; OWASP keeps a Pinning Cheat Sheet under its cryptographic-failures category.[8]

At rest: hashing passwords

Encryption in transit does nothing for data once it is stored. The guide uses passwords to explain what “at rest” protection looks like:[5]

HashA garbled representation of the password with almost no way back to the original. At login, the typed password is hashed and compared with the stored hash.
Slow on purposeA fast hash lets an attacker hash every short string and look the leaked hashes up. A slow hash makes building that table expensive.
Rainbow tableThe guide’s name for such a precomputed table of hashes. Strictly, a rainbow table stores hash chains to save space; a full list of hashes is a lookup table.[27]
SaltA small random string added to each password before hashing and stored in plain text beside the hash. The attacker now needs a separate table per salt.
CollisionTwo inputs with the same hash. They exist, but nobody should be able to produce them on purpose. Researchers did so with MD5 to forge an SSL certificate, so browsers phased MD5 out, and later SHA-1.
bcryptThe guide’s one rule: never store plain-text passwords; use bcrypt. The checklist adds that bcrypt salts for you.[4]

Figure 16.4 shows why the salt matters. Two users choose the same password; without salts their stored hashes match, so cracking one cracks both, and one table cracks everyone.

Fact check · which hash?

OWASP’s Password Storage Cheat Sheet, listed under the Top Ten, now ranks Argon2id first, then scrypt, and keeps bcrypt for legacy systems (work factor 10 or more, passwords up to 72 bytes), with PBKDF2 where FIPS-140 compliance is required. It agrees that modern libraries generate and manage salts themselves.[11]

At rest: encrypting data

Passwords are hashed because the system never needs them back. Other stored data must be readable, so it is encrypted instead. OWASP draws the line: hashing is a one-way function, right for checking passwords; encryption is two-way, right for data such as an address that the profile page must display.[11] The guide’s planned chapter “Plaintext != Encoding != Encryption != Hashing” makes the same point in its title.[3]

The guide notes that many apps store emails, addresses, location history and messages in plain text, protected only by the database.[5] Its checklist suggests the cloud features that fix this, and the API checklist sets the rule:

  • Encrypt data in Amazon S3 with server-side encryption, and use encrypted EBS volumes on EC2; even boot volumes can be encrypted.[4]
  • Use encryption on all sensitive data, and use server-side encryption only.[2]
  • Never log sensitive data such as card numbers, passwords or PINs: logs are data at rest too.[2]

16.2Sanitize input: XSS

What XSS is

Cross-site scripting (XSS) lets an attacker inject client-side scripts into pages that other users view. It is a form of code injection, and it can bypass the same-origin policy, which only lets content share permissions when the URI scheme, host name and port match.[14] Microsoft security engineers coined the term in January 2000. XSS has since overtaken buffer overflows as the most commonly reported public vulnerability, and researchers in 2007 estimated that up to 68% of websites were likely open to it.[14]

Injected code can load more scripts, steal cookies and session data, deface the site, or pose as the real site to trick users into giving up secrets.[5] The guide’s example is the Samy worm on MySpace (October 2005): over a million profiles displayed “but most of all, samy is my hero” within 20 hours. MySpace went offline to fix it, and its author was sentenced to three years’ probation with restricted computer use.[5][22]

Markup or text?

Every XSS bug comes down to one question: does the browser treat the user’s input as text or as markup? OWASP puts it as displaying input as data without executing it as code.[12] Type into Figure 16.6, or pick a sample. Nothing you enter runs: the page parses it in an inert document only to report what a browser would build.

Defences

The primer’s instruction is to sanitize input; the developer checklist adds the other half, sanitize outputs before displaying them.[1][4] Wikipedia and OWASP agree that the main defence is contextual output encoding, because browsers parse HTML, JavaScript, CSS and URLs differently and the wrong encoder can leave a hole.[14][12] Start with your framework’s automatic encoding and use an encoding library for the gaps.[12]

Around that core, the sources list further layers:

HTML sanitizationWhen users must submit HTML, run it through a sanitizer such as DOMPurify. Blacklisting tags is error-prone.[14]
Safe sinksWrite untrusted values with textContent or value, which never execute, instead of innerHTML.[12]
HttpOnly cookiesHide session cookies from page scripts, so injected code cannot read them; it can still act in the page.[14]
SameSite cookiesStrict withholds the cookie from all cross-origin requests; Lax from unsafe ones (anything but GET, OPTIONS, TRACE).[14]
Content Security PolicyA header that allow-lists where content may load from. The checklist calls it important; OWASP calls it defence in depth, not the primary fix.[4][12]
Trusted TypesMake DOM sinks reject plain strings unless they passed a vetted policy, so attacker strings cannot reach them.[14][12]
Fact check · X-XSS-Protection

The developer checklist recommends the X-XSS-Protection header.[4] MDN now lists it as deprecated and non-standard, warns that the filter it controls can create XSS holes in otherwise safe sites, and recommends a strong Content Security Policy instead.[21]

16.3Parameterized queries: SQL injection

When data becomes code

SQL injection inserts malicious SQL into an entry field so that the application executes it, for example to dump the database. It exploits input that is not filtered for escape characters or not strongly typed.[15] The guide names the root weakness: SQL cannot tell code from data, so a query built from user input lets an attacker supply code where data was expected.[5] A successful attack can spoof identity, change or destroy data, disclose everything in the database, or make the attacker its administrator.[15]

It was first discussed publicly in a 1998 Phrack article by Jeff Forristal. OWASP ranked it the most critical web vulnerability in 2013; in 2021 its injection category was tested in 94% of applications.[15][9] The guide adds that SQL injection is a common way attackers get the data dumps behind breaches.[5]

Concatenated vs parameterized

The classic vulnerable code builds a query by gluing input into a string:[15]

statement = "SELECT * FROM users WHERE name = '" + userName + "';"

Figure 16.7 runs that query against a three-row users table, next to the parameterized version. Try the samples, or type your own input.

With a parameterized query, the SQL is written first with a placeholder, and the value is sent separately and typed, so it is never parsed as SQL.[15] OWASP’s example: the input tom' or '1'='1 makes the database look for a user whose name is literally that whole string.[13]

// Java, from OWASP's SQL Injection Prevention Cheat Sheet
String query = "SELECT account_balance FROM user_data WHERE user_name = ? ";
PreparedStatement pstmt = connection.prepareStatement(query);
pstmt.setString(1, custname);
ResultSet results = pstmt.executeQuery();

Forms of attack

Table 16.4 Forms of SQL injection described by Wikipedia.[15]
FormHow it works
Tautology' OR '1'='1 makes the WHERE clause always true. Comment markers (--, /*) cut off the rest of the query.
Stacked statementsWhere the API runs several statements at once, '; DROP TABLE users; … adds new commands.
Union-basedAppends a UNION to pull rows from other tables; used in the 2012 Yahoo! Voices breach.
BlindNo data comes back, so the attacker infers it from behaviour: a page that differs for 1=1 and 1=2 is injectable.
Second-orderInput is stored safely, then used unsafely in a later query. Automated scanners often miss it.
Out-of-bandResults leave through a separate HTTP or DNS channel to the attacker’s server.

Defences in order

OWASP ranks four primary defences and recommends two additional ones for defence in depth.[13]

  1. Prepared statements with parameterized queries. The database always tells code from data, whatever the input. This is the primer’s rule.[1][13]
  2. Properly built stored procedures, which have the same effect as parameterized queries when implemented safely.[13] An ORM that builds queries for you is also listed, though ORMs can still be vulnerable through raw SQL.[15]
  3. Allow-list input validation, for the parts of a query that cannot be parameters, such as table names or sort order.[13]
  4. Escaping all user input, strongly discouraged: it is database-specific and fragile, and OWASP cannot guarantee it works.[13]

The additional defences are least privilege for every database account, so a successful injection can do less (section 16.4), and allow-list validation as a second check.[13] The developer checklist adds two habits from the same family: never build JSON by string concatenation, and sanitize input reused in features such as CSV import.[4]

Fact check · two Sony hacks

The guide says LulzSec used SQL injection in “the SONY pictures hack” and, in the same breath, credits it with leaked executive details and a passwords spreadsheet.[5] Those are two different events. LulzSec’s claimed SQL injection was in June 2011.[23] The large leak of emails, films and employee data was the November 2014 hack, claimed by “Guardians of Peace” and attributed by US officials to North Korea.[24] The guide’s link for the LulzSec claim also points to an unrelated Wi-Fi article.

The attack even has a nickname: a 2007 xkcd strip about a student named Robert'); DROP TABLE Students;-- is why SQL injection is nicknamed “Bobby Tables”.[15]

16.4Least privilege

The principle

The principle of least privilege (PoLP), also called minimal privilege or least authority (PoLA), says every module, whether a process, a user or a program, may access only the information and resources it needs for its legitimate purpose. Applied to people it is called least user access.[16]

Every program and every privileged user of the system should operate using the least amount of privilege necessary to complete the job.Jerome Saltzer (1974), quoted by Wikipedia[16]

Wikipedia calls Version 6 Unix’s login program probably the oldest example: it starts with super-user rights and drops them with setuid() once they are no longer needed.[16]

In practice

The sources apply the principle at every layer of a system:

Table 16.6 Least privilege at each layer, gathered from the linked sources.
LayerToo much privilegeLeast privilege
Operating systemWorking day to day as an administrator.Work in a normal account; open a password-protected privileged one only when needed.[16]
Service accountA backup account that can also install software.The account runs only backup applications.[16]
Database serverThe DBMS runs as root or system.Run it under a restricted OS account.[13]
Application’s DB userOne admin account shared by every app.A separate user per app. A login page gets SELECT on the user table; only sign-up gets INSERT. Views can hide columns.[13]
API resources/user/654321/orders, where any ID can be tried./me/orders, scoped to the logged-in user, with UUIDs instead of counting IDs.[2][4]
OAuth appsEvery app gets every permission.Define a default scope and validate the scopes each app asks for.[2]
PeopleEveryone can query the user database.Limit access to user databases to those who need it.[4]

Privilege bracketing

Privileges also have a time dimension. Privilege bracketing takes a privilege at the last possible moment and drops it as soon as it is no longer strictly needed, which shrinks the window in which buggy code can misuse it.[16] Figure 16.8 compares the two approaches for a program like Unix login.

Benefits and limits

Benefits

  • Better security: a vulnerability in one application can’t easily compromise the rest of the machine.
  • Intellectual security: code that can change less is easier to test, and can’t crash the machine or harm other apps.
  • Easier deployment: fewer privileged parts, such as drivers, need special install steps.

Limits

  • There are several competing definitions of “true” least privilege.
  • Programs are too complex to predict every resource they need, so granted privileges exceed the true minimum.
  • Systems rarely control memory, CPU time or I/O that precisely; the practical method is to remove what is clearly unnecessary.

Both lists from Wikipedia.[16] Related ideas it lists include need to know, privilege separation, role-based access control, capability-based security and the confused deputy problem.

16.5Beyond the basics

What can go wrong

The guide’s overview chapter tours how real systems fail. Its theme is that most exploits begin as human errors that a malicious hacker finds and uses.[5] Beyond the café and database scenarios above, it lists:

Open databasesDatabases left on the internet with no or weak passwords. Shodan, a search engine for open ports, finds MongoDB and MySQL instances and even their sizes.
Leaked API keysThird-party keys pushed to public GitHub repositories can be used to read data or even wipe cloud deployments.
Weak second factors2FA by SMS can be beaten with fake cell towers (“Stingray”), the SS7 signalling flaw, or a SIM swap talked out of a telecom provider.
Remote code executionRunning arbitrary code on a target device, the most serious class; such fixes appear in many OS security updates.
Social engineeringLook-alike domains and spoofed email. Missing SPF, DKIM and DMARC records let attackers send mail that appears to come from your domain.
Malware and botnetsRemotely controlled programs on many compromised machines, used together to attack other systems.
DoS and DDoSTraffic far beyond what a system can handle, from one source or, distributed, from a botnet. Mirai built its botnet from IoT devices with default passwords.
Parser bugsThe LangSec view: improper input handling is the root of almost all security issues. Hand-coded parsers make it worse.
UsabilitySecurity that is cumbersome lowers adoption and so protects nobody; measures also need explaining to users.

The guide closes with two warnings: probing a system you don’t own can be a crime even with good intentions, so use public bug bounty programs; and avoid designing your own cryptography or security by obscurity.[5]

Fact check · 2016 details

Three claims in the chapter need care. It says the October 2016 attack on DNS provider Dyn brought down almost half of US internet at 1.2 Tbps; Wikipedia describes outages across Europe and North America, especially the eastern US, attributes it to Mirai, and gives no confirmed size.[25] It says NIST deprecated SMS for 2FA in August 2016; that was a July 2016 draft, and NIST’s current guidance labels phone and SMS one-time passwords restricted: allowed only with a risk assessment and a non-restricted alternative.[26] It says the Samy author got no computer access for three years; Wikipedia records three years’ probation with one monitored computer.[22]

The primer’s first two links are checklists. Shieldfy’s API Security Checklist covers countermeasures for designing, testing and releasing an API.[2] The FallibleInc guide aims at two kinds of developer, those who can’t yet tell MD5 from bcrypt and those who know but forget, and offers its checklist for the second kind.[3] Figure 16.10 condenses both into checklists you can tick while reviewing a design; the items are paraphrased, so open the originals for full wording.

Encryption
In transit · at rest
While moving over the network · while stored.
ARP poisoning
Tricks a switch into sending your packets to an attacker.
HTTPS · TLS
HTTP encrypted by the TLS protocol.
Symmetric key
One shared key both encrypts and decrypts.
TLS handshake
How browser and server agree on that key.
Public · private key
Anyone can encrypt to it · only the owner decrypts.
Pre-master · master secret
Random value sent encrypted · key derived from it.
Forward secrecy
A stolen key can’t decrypt past sessions; TLS 1.3 requires it.
Certificate · CA
Binds a domain to a key · trusted signer of certificates.
Man in the middle
Attacker relaying, reading or changing traffic.
CSR
Certificate signing request sent to a CA.
HSTS · SSL stripping
Forces HTTPS · silent downgrade to HTTP.
Heartbleed · BEAST · POODLE · DROWN · Logjam
Attacks fixed by patching, ciphers, protocols, DH parameters.
Certificate · public key pinning
App trusts only a known certificate · known key.
Hash
One-way digest; compared, never reversed.
Salt
Random per-user value hashed with the password.
Rainbow table
Precomputed hashes for cracking; salts defeat it.
Collision
Two inputs, one hash; broke MD5.
bcrypt · Argon2id
Slow password hashes; OWASP now prefers Argon2id.

XSS
Injected script runs in other users’ browsers.
Same-origin policy
Pages share rights only with the same scheme, host, port.
Reflected · stored · DOM-based
Echoed at once · saved and served · written by page JS.
Output encoding
Convert input so it shows as text, per context.
Sanitization
Strip dangerous parts from user HTML (DOMPurify).
Safe sink
Writes as text: textContent, not innerHTML.
HttpOnly · SameSite
Cookie hidden from scripts · not sent cross-site.
CSP
Header allow-listing where content may load from.
Trusted Types
DOM sinks accept only vetted values.

SQL injection
Input that escapes its data context and runs as SQL.
Parameterized query
SQL with placeholders; values sent separately.
Tautology · stacked · union
Always-true WHERE · extra statements · rows from other tables.
Blind · second-order
Inferred from behaviour · stored, exploited later.
Stored procedure · ORM
Query kept in the DB · library that builds queries.
Allow-list validation
Accept only known-good input.

Only the access a job needs.

Take rights late, drop them early.

Need to know · RBAC
