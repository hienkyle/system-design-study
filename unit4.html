SYSTEM DESIGN PRIMER · UNIT 4

Availability vs consistency

The third of the primer’s high-level trade-offs. Once data lives on more than one machine, the network between them can fail, and when it does you must choose: answer every request, or only ever give correct answers.[1]

Primer section · Availability vs consistencyRobert Greiner · “CAP Theorem: Revisited” (2014)Kaushik Sathupadi · plain-English introHenry Robinson · CAP FAQ (2013)

4.1Why the trade-off exists

Greiner starts from the trend of scaling out: handling more load by adding commodity machines rather than buying a bigger one (Unit 1’s horizontal scaling). Scaling out turns an application into a distributed system, a set of interconnected nodes that share data. That brings new complexity, and the CAP theorem describes it.[2]

Two points from Greiner set up everything below:[2]

  • Distributed programming is not object-oriented programming. Assumptions that hold when code shares memory inside one process stop holding when nodes are separated in space and time.
  • Networks are unreliable. Assuming otherwise is one of the fallacies of distributed computing, a list of false assumptions whose first entry is “the network is reliable”.[9] Network failures will happen to your system, and you don’t get to choose when.

4.2The CAP theorem

Where it came from

Eric Brewer posed the idea, then unproven, in his keynote Towards Robust Distributed Systems at the Principles of Distributed Computing (PODC) conference in 2000. Two years later, MIT researchers Seth Gilbert and Nancy Lynch formalised and proved it, turning “Brewer’s conjecture” into a theorem.[4][6][7]

The three guarantees

The primer’s version: in a distributed computer system, you can only support two of the following guarantees.[1]

  • Consistency (C): every read receives the most recent write or an error.
  • Availability (A): every request receives a response, without a guarantee that it contains the most recent version of the information.
  • Partition tolerance (P): the system continues to operate despite arbitrary partitioning due to network failures.

The three sources word the guarantees slightly differently. The differences matter: they are exactly where most CAP arguments start.

The precise terms

Robinson’s FAQ states the theorem exactly: it is impossible to build an implementation of read-write storage in an asynchronous network that is available, consistent and partition-tolerant all at once. Informally, you can’t build a database that both responds to every request and always returns the results you’d expect.[4] The intermediary terms:

Read-write storage (a register)

CAP is about a register, a data structure with two operations: set(X) stores X, and get() returns the last value set. A key-value store can be modelled as many registers, so this simple object captures what most distributed stores do: write data and read it back.[4]

Atomic (linearizable) consistency

The register must look to every client as if it ran on one machine, answering operations in the order they arrive. The results of all clients’ operations, even concurrent ones, must match a single serial (one-after-another) execution.[4][8] This is very strong. It rules out eventual consistency, which allows a delay before a write becomes visible (Unit 5). It also respects external communication: if I read a value and tell you about it, you must be able to read it too.

Table 4.2 Robinson’s example histories (A: / B: = which client runs the operation)
HistoryAtomic?Why
set(10), set(5), get() = 10✗Allowed under eventual consistency (the newer write isn’t visible yet), not under atomic
B:set(5), A:set(10), A:get() = 10, B:get() = 10✓Everyone sees the last write
B:set(5), A:set(10), A:get() = 10, B:get() = 5✗Matches some serial order, so it is serializable, a weaker guarantee. But if A tells B “it’s 10”, B’s read of 5 makes no sense

All three histories are from the CAP FAQ, §4.[4]

Asynchronous network

A network with no bound on how long a message takes to be delivered or processed. The key consequence: a node cannot tell a machine that has failed from one whose messages are merely delayed. Robinson argues real networks are effectively asynchronous, since clocks drift and retries or garbage-collection pauses can delay any message.[4]

Available (formally)

Every get and set must eventually return a valid response. Errors don’t count, otherwise a system could be “available” by always failing. The requirement is strong (100% of requests, no partial credit) and weak (no time limit, as long as it’s finite) at once.[4]

Partition

The network loses some messages to one or more nodes. Delay is not a partition: a message that eventually arrives was only slow. A total partition is a period in which no messages pass between two groups of nodes. CAP’s proof uses a total partition, and Robinson notes these are realistic, because traffic between two nodes often flows through a single component that can fail.[4]

Why CAP is true

The idea of the proof is a single scenario.[4] A client writes to a node on one side of a partition. A read then arrives at a node on the other side, which cannot possibly know about that write. The second node has two options, and each breaks one guarantee:

  • Answer with what it has: possibly stale, so consistency is lost.
  • Wait (potentially forever) to hear from the other side: availability is lost.

This is a proof by construction: it shows one situation where C and A can’t both hold. Robinson calls that a critical condition. CAP says nothing about how often it happens; until it does, a system can be consistent and available. But both guarantees are all-or-nothing (one stale read or one unanswered write breaks them), and a long-running system serving millions of requests will likely hit the critical condition, so you should know which guarantee yours gives up.[4]

Why “CA” isn’t a choice

The primer’s key line: networks aren’t reliable, so you’ll need to support partition tolerance, and the real decision is a software trade-off between consistency and availability.[1] Greiner makes the same point: you have fewer options than “pick two” suggests, because you can’t opt out of partitions.[2] Robinson explains why “choose two” misleads: partition tolerance isn’t something you build; your system either might experience partitions or it won’t, and every distributed system might. He rewrites the theorem as:[4]

CAP, restated

Possibility of Partitions ⇒ Not (C and A)

If your system may experience partitions, it cannot always be both consistent and available. Systems that truly can’t partition, such as a single-site database, are outside the setting where CAP is useful. Calling a distributed database “CA” signals a misunderstanding.[4]

4.3CP: consistency and partition tolerance

During a partition, a CP system keeps answers correct by refusing to guess. Waiting for a response from the partitioned node might end in a timeout error;[1] depending on the scenario, the system may instead return an error straight away.[2]

Choose CP when

Business needs require atomic reads and writes: a stale answer is worse than no answer.[1][2] Robinson’s example of a real system that relaxes availability because consistency matters most is ZooKeeper.[4]

4.4AP: availability and partition tolerance

During a partition, an AP system keeps answering. Responses return the most readily available version of the data on whichever node is reached, which might not be the latest. Writes are accepted and may take time to propagate once the partition is resolved.[1][2]

Choose AP when

The business can allow for eventual consistency (Unit 5), or the system must keep working despite external errors.[1] Greiner’s example is a shopping cart, which should keep working even when parts of the system fail.[2] Robinson cites Amazon’s Dynamo as a system that relaxes consistency to stay highly available.[4]

4.5CAP in plain English

Kaushik Sathupadi explains CAP through a story about a two-person phone business. The people are the nodes, their notebooks are the replicated data, and the customers are clients.[3]

Remembrance Inc.

The narrator starts a service: customers call to have him remember something (a boss’s phone number, say) and call back later to retrieve it, paying per call. As it grows, one person is too few: callers queue and hang up, and a sick day closes the business. So his wife joins, each has an extension phone, customers dial the same number, and a phone exchange (PBX) routes each call to whoever is free.[3] Each step of the story then exposes one CAP property:

The run-around clerk (eventual consistency)

In a bonus chapter, a run-around clerk copies each new entry into the other person’s notebook in the background. Updates no longer block the phones. Sathupadi notes this is how many NoSQL systems work: one node updates locally and a background process syncs the rest. The cost is a window of inconsistency: a customer who calls back before the clerk arrives may get the old answer, which is acceptable if the window is short (for example, if customers don’t call back within five minutes).[3] This is eventual consistency, the AP-friendly pattern covered in Unit 5.

4.6Common misconceptions

Robinson wrote the FAQ to settle frequent misunderstandings.[4]

  • “CAP means we can’t build useful distributed systems.” No. It is an impossibility result, not a death knell; it tells you which constraints to design within.
  • “C and A are on/off.” Real systems relax one or both from CAP’s strict definitions, and must; the job is knowing when and how yours does. Weaken any assumption of the theorem, though, and its proof no longer applies.
  • “If no messages are lost, we can have both.” Not in an asynchronous network: Gilbert and Lynch showed no atomic register there can be always available and consistent whenever messages aren’t lost, because a node can’t tell a lost message from a slow one. (In a partially synchronous network, with bounded message processing time, this particular result no longer holds.)
  • “CAP is the same as FLP.” The FLP theorem (Fischer, Lynch and Paterson) says consensus, all nodes agreeing on one value, is unsolvable in general in an asynchronous network where one node may fail. Both are impossibility results, but FLP allows one failed node, forbids message loss, and concerns consensus rather than atomic storage.
  • “We beat CAP.” You haven’t. At best you’ve built a system that isn’t heavily affected by it.
In an interview

Don’t call a distributed design “CA”. Assume partitions will happen, then say which of C or A your design gives up during one, and why that suits the business (atomic reads/writes → CP; must keep working, staleness tolerable → AP).[1][4]
