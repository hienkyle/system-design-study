SYSTEM DESIGN PRIMER · UNIT 12

Database

Once the web and application tiers scale out, the database is usually the next bottleneck. This unit covers the relational database and its guarantees (ACID), six ways to scale one (master-slave and master-master replication, federation, sharding, denormalization and SQL tuning), the four families of NoSQL store and their BASE trade-off, and how to choose between SQL and NoSQL.[1]

12.0The database tier

Figure 12.1 is the primer’s opening picture for this section. A group of web instances sends every write to one write master, spreads reads across read replicas, and also reads and writes a cache.[1] Each piece is covered below: replicas in 12.1, caching in Unit 13.

Two ways to scale it

Part 2 of “Scalability for Dummies” (read in full in Unit 1) frames the choice this unit unpacks. Path 1 keeps the relational database: master-slave replication, then a bigger master, then sharding, denormalization and SQL tuning, each step costlier than the last. Path 2 denormalizes early and moves joins into application code, either on MySQL used like a NoSQL store or on a NoSQL database such as MongoDB or CouchDB. Either way, a cache comes next.[2]

Bonér’s deck gives the reason the relational path gets expensive: scaling reads to an RDBMS is hard, and scaling writes to one is, in his words, “impossible”.[5] Replication helps reads; splitting the data (federation, sharding) removes the single master that serializes writes.[1]

12.1Relational databases (RDBMS)

A relational database like SQL is a collection of data items organized in tables.[1] The model comes from Edgar Codd’s 1970 paper at IBM: rows and columns, with constraints such as uniqueness and foreign keys. IBM’s first implementation, SEQUEL, grew into the SQL standard during the 1980s.[31]

Transactions and ACID

A transaction is a unit of work that may contain several operations. It exists for two reasons: reliability, so the database recovers correctly from a crash partway through, and isolation, so programs running at the same time don’t corrupt each other’s results.[4] The flow is BEGIN, run the changes, then COMMIT to keep them all or ROLLBACK to discard them all; a partial transaction is never committed.[4] ACID names the four properties a relational transaction provides:[1]

AtomicityEach transaction is all or nothing.
ConsistencyEach transaction moves the database from one valid state to another.
IsolationRunning transactions concurrently gives the same result as running them one after another.
DurabilityOnce committed, a transaction stays committed.

Isolation comes in levels. The strictest, serializability, makes concurrent transactions behave as if they ran in sequence; looser levels let changes show up sooner in exchange for more concurrency.[4] Carvelli traces these properties to Jim Gray’s work on transactions in the late 1970s.[31] The classic example is a bank transfer: money leaves one account and arrives in another, and both steps must happen or neither.[4] Try it in Figure 12.2.

The primer lists six techniques for scaling a relational database: master-slave replication, master-master replication, federation, sharding, denormalization and SQL tuning.[1] Asked how to scale out an RDBMS, Bonér’s deck answers sharding, which it breaks into partitioning plus replication.[5]

Master-slave replication

The master serves reads and writes and replicates writes to one or more slaves, which serve only reads. Slaves can replicate to further slaves in a tree. If the master goes offline, the system keeps running in read-only mode until a slave is promoted or a new master is provisioned.[1] Unit 6 covers both replication forms in depth; see Unit 6 · Replication.

Disadvantage

  • Extra logic is needed to promote a slave to a master.[1]
  • Plus the shared replication costs below.

Master-master replication

Both masters serve reads and writes and coordinate with each other on writes. If either goes down, the system keeps running with both reads and writes.[1] In Wikipedia’s terms this is multi-master replication: any member can update the data, and the system spreads each change and resolves conflicts between concurrent ones.[6]

Disadvantages

  • You need a load balancer, or changes to application logic, to decide where to write.[1]
  • Most master-master systems are either loosely consistent (violating ACID) or have higher write latency from synchronization.[1] That is the lazy (asynchronous) versus eager (synchronous, often two-phase commit) choice; eager replication avoids conflicts, as in Galera Cluster.[6]
  • Conflict resolution matters more as write nodes are added and latency grows.[1]
  • Plus the shared replication costs below.

Replication: shared costs

These apply to both master-slave and master-master:[1]

  • Data loss if the master fails before newly written data reaches other nodes.
  • Replay load. Writes are replayed on the read replicas; with many writes, replicas get bogged down replaying and serve fewer reads.
  • Replication lag grows with the number of read slaves, since there is more to replicate.
  • Single-threaded replay. On some systems the master writes in parallel threads while replicas apply writes sequentially in one thread.
  • More hardware and complexity.

Federation

Federation (or functional partitioning) splits databases by function. Instead of one monolithic database you might have three, forums, users and products, each getting less read and write traffic and so less replication lag.[1]

  • Smaller databases mean more of the data fits in memory, so more cache hits thanks to better cache locality.[1]
  • With no single central master serializing writes, you can write in parallel and raise throughput.[1]

Disadvantages

  • Not effective if the schema needs huge functions or tables.[1]
  • Application logic must decide which database to read and write.[1]
  • Joining data across two databases is more complex, needing a server link, a connection from one database server to another.[1]
  • More hardware and complexity.[1]

Sharding

Sharding distributes data across databases so that each one manages only a subset of the data. With a users database, more shards join the cluster as users grow.[1] Where federation splits by function, sharding splits one table’s rows: a shard is a horizontal partition (by rows), as opposed to vertical partitioning (by columns, as in normalization).[8]

The advantages mirror federation’s: less read and write traffic, less replication and more cache hits. Index size also shrinks, which generally makes queries faster. If one shard goes down the others keep working, though you’ll want replication inside each shard to avoid data loss. And with no central master, writes run in parallel.[1] Common ways to shard a users table are by last-name initial or by geographic location.[1]

Disadvantages

  • Application logic must work with shards, which can mean complex SQL queries.[1]
  • Data can become lopsided: a set of power users on one shard loads it more than the others. Rebalancing adds complexity; a sharding function based on consistent hashing reduces the data moved.[1]
  • Joining data across shards is more complex.[1]
  • More hardware and complexity.[1]

From the further reading

  • Origins. Todd Hoff’s 2009 article credits the idea to Dathan Pattishall, who used it at Auction Watch and then at Flickr. Users are split into groups, each on its own cheap server; the article reports Flickr handling over a billion transactions a day this way.[7]
  • Data used together lives together. Rather than normalizing and joining at query time, a shard can store a user’s profile as one blob, read with no joins and written in one disk write.[7] That is denormalization (below).
  • Problems Hoff lists: rebalancing a shard that outgrows its server without downtime (Flickr uses a naming service so data can be relocated), cross-shard joins done in the application, hard partitioning choices, and little tooling, so it is largely “roll your own”.[7]
  • Shared-nothing. Shards share no data or resources, so each can sit in a separate server, data center or region.[8]
  • Last resort. Wikipedia notes sharding is generally recommended only after other optimizations prove insufficient,[8] and Hoff’s updates quote a MySQL Performance Blog post making the same case.[7]
  • Why “shard”? The term is thought to come either from a 1988 system called SHARD or from Ultima Online (1997), which split players across separate copies of its world.[8]

Consistent hashing

Plain modulo hashing, shard = hash(key) % N, sends most keys to a new shard whenever N changes.[38][39] Consistent hashing, which originated at Akamai in the late 1990s, avoids that.[9]

  1. The hash space is drawn as a ring. Each server takes a point on it, and owns the range up to the next server’s point.[9]
  2. A key belongs to the first server found moving clockwise from the key’s own hash.[39]
  3. Adding or removing a server moves only the keys next to its points.[24][39]
  4. One random point per server can leave some ranges far larger than others, creating hotspots, so systems give each server many points, called virtual nodes, or split the ring into fixed equal partitions.[9] For Memcached clients, Thijssen suggests roughly 100–200 points per server.[24]

Reading Figure 12.8. The circle is the hash space, from 0 at the top round to just under 1. Each dot is one key, placed at the angle its hash gives it, and coloured by the server that owns it. The short marks outside the ring are the servers’ own points. A key belongs to the first server mark clockwise from it, so each arc of dots takes the colour of the mark at its end. Hashes scatter keys unevenly, so some land almost on top of each other; when that happens the dot is pushed one step inward so both stay visible. Only the angle matters, never the distance from the centre. In hash % N mode the positions stay the same but the ring is ignored, which is why the colours look random.

Meyer’s article adds two notes. Hashing spreads related keys (such as sequential hourly timestamps) evenly, but loses key ordering, which makes range queries harder; Bigtable and HBase keep ranges instead and split them as they grow. And each node can hold replicas of a set of partitions, so with three replicas the data survives losing two nodes.[9] Memcached, Dynamo, Cassandra and Riak all use the technique in some form.[9]

Denormalization

Denormalization improves read performance at the expense of some write performance. Redundant copies of data are written into several tables to avoid expensive joins.[1] It matters because in most systems reads outnumber writes 100:1 or even 1000:1, and a read that needs a complex join can spend a long time on disk operations. Once data is spread by federation and sharding, joins across data centers get even harder, and denormalization can avoid them.[1]

There are two ways to do it.[10]

  • Let the DBMS keep the copies. PostgreSQL and Oracle support materialized views, which store redundant information and keep the copies consistent.[1] A materialized view stores a query’s results as a real table: reads are fast, but the data can go stale until refreshed. PostgreSQL has supported them since version 9.3, refreshed with REFRESH MATERIALIZED VIEW; SQL Server offers indexed views instead, and MySQL has no native support.[11][12]
  • Change the design yourself. The designer adds the redundant columns and must write constraints to keep them consistent, which adds complexity and risk.[10] Other techniques include storing a count of child rows on the parent, star schemas, and precomputed summaries.[10]

Denormalize only from a normalized design (for example third normal form); a denormalized model is not the same as an unnormalized one.[10]

Disadvantages

  • Data is duplicated.[1]
  • Constraints can keep redundant copies in sync, but they make the design more complex.[1]
  • Under heavy write load, a denormalized database might perform worse than its normalized counterpart.[1]

SQL tuning

SQL tuning is a broad topic with many books written on it. The starting point is to benchmark and profile to simulate and uncover bottlenecks.[1]

  • Benchmark: simulate high load with a tool such as Apache’s ab.[1] Its two key options are -n (total requests) and -c (how many run at once); it reports requests per second and time per request.[13] For example, ab -n 1000 -c 10 http://example.com/.
  • Profile: turn on tools such as MySQL’s slow query log to track down slow statements.[1] It is off by default and logs statements slower than long_query_time (default 10 seconds); log_queries_not_using_indexes also catches queries that scan without an index, and mysqldumpslow summarizes the log.[14]

Jesse Farmer’s 2008 list, in the further reading, adds the profiling commands EXPLAIN, SHOW STATUS and SHOW PROCESSLIST, and benchmarking tools such as SysBench.[18] Benchmarking and profiling might point to these fixes:[1]

MySQL dumps to disk in contiguous blocks for fast access.[1] Farmer’s rule of thumb: use the smallest data type that fits.[18]

Use good indices

  • Columns you query with SELECT, GROUP BY, ORDER BY or JOIN can be faster with indices.[1]
  • Indices are usually a self-balancing B-tree, which keeps data sorted and supports search, sequential access, insertion and deletion in logarithmic time.[1]
  • An index can keep data in memory, so it needs more space; writes can be slower because the index must be updated too.[1]
  • For big loads it can be faster to disable indices, load, then rebuild.[1]

Avoid expensive joins · partition tables · tune the query cache

  • Avoid expensive joins: denormalize where performance demands it.[1]
  • Partition tables: put hot spots in a separate table to help keep them in memory.[1] Farmer’s version: split often-read or often-changed columns from the rest.[18]
  • Tune the query cache: in some cases it causes performance issues.[1] MySQL’s query cache returned stored results for identical SELECT statements and was flushed whenever a table changed, so frequent writes made it useless; it was deprecated in 5.7.20 and removed in 8.0.[16] Percona’s 5.7 tuning post notes the cache is already off by default there, which also disables its mutex.[17]

12.2NoSQL

NoSQL is a collection of data items represented in a key-value store, document store, wide column store or graph database. Data is denormalized and joins are generally done in application code. Most NoSQL stores lack true ACID transactions and favour eventual consistency (Unit 5).[1] Bonér’s deck expands the name as Not Only SQL.[5]

The push came from scale. By the late 1990s, growing data volumes made it hard to scale relational systems while keeping ACID and fixed schemas.[31] Google’s Bigtable (2006) and Amazon’s Dynamo (2007) papers then inspired many open-source systems: HBase and Hypertable from Bigtable, Voldemort and Dynomite from Dynamo.[5]

BASE

BASE is often used to describe NoSQL databases. In terms of the CAP theorem (Unit 4), BASE chooses availability over consistency.[1]

Basically availableThe system guarantees availability.
Soft stateThe state of the system may change over time, even without input.
Eventual consistencyThe system becomes consistent over time, given no new input during that period.

Definitions from the primer.[1] Brewer proposed BASE as the alternative to ACID.[31]

Table 12.4 ACID and BASE side by side, with Bonér’s 2010 examples.[1][5]
ACIDBASE
PriorityConsistency of every transactionAvailability; consistency arrives eventually
CAP sideConsistency; a single centralized server faces no partitions, so it keeps availability tooAvailability during partitions (AP)
ExamplesMySQL, Oracle, Postgres; most caching productsCassandra, Riak, Voldemort, Dynomite, SimpleDB

Bonér’s advice is to think about each kind of data separately: when does it need ACID, and when is eventual consistency a better fit?[5] The rest of this section helps pick the type of NoSQL store that fits a use case.[1]

Key-value store

Abstraction: hash table— the primer[1]

A key-value store generally allows O(1) reads and writes and is often backed by memory or SSD. Stores can keep keys in lexicographic order, allowing efficient retrieval of key ranges, and can store metadata with a value.[1] Lexicographic order is dictionary order: compare two keys at the first character where they differ, so car sorts before cat. Keys built in a fixed format sort usefully, for example ISO dates like 2026-10-19 sort chronologically as plain text.[19]

They give high performance and are often used for simple data models or rapidly changing data, such as an in-memory cache layer. Because they offer only a few operations, any extra work shifts to the application.[1] The values are opaque: the store doesn’t interpret them, so it can’t search by their contents or enforce relationships.[21] A key-value store is the basis for more complex systems such as document stores and, in some cases, graph databases.[1]

  • Storage. Some keep data in RAM (Memcached, Redis); others persist it (RocksDB, Berkeley DB, Riak, Voldemort). Consistency ranges from eventual to serializable, and some systems let you choose.[21]
  • Redis persists an in-memory dataset with RDB snapshots, an AOF log of every write, both or neither; the docs suggest both for safety comparable to PostgreSQL.[22] Replication is master-replica and asynchronous by default, and replicas are read-only by default.[23]
  • Memcached claims all its memory at startup and splits it into 1 MB pages, each assigned to a slab class of equal-sized chunks, avoiding fragmentation. An item goes in the smallest chunk that fits. Eviction is LRU within a slab class, and operations are O(1), so there is no way to iterate over all keys.[24] The client, not the server, decides which server holds a key, using consistent hashing.[24]

The primer’s “Redis architecture” link (qnimate.com) no longer loads, so the Redis points above come from Redis’s own documentation instead.[22][23] Its Stack Overflow link on key-value disadvantages could not be read.

Document store

Abstraction: key-value store with documents stored as values— the primer[1]

A document store is centred on documents (XML, JSON, binary, etc.), where one document holds all the information for a given object. It provides APIs or a query language to query on the document’s internal structure. Many key-value stores can also work with a value’s metadata, which blurs the line between the two.[1] That is the key difference: a key-value store treats the value as opaque, while a document store reads inside it.[25]

Depending on the implementation, documents are organized by collections, tags, metadata or directories. Documents in the same group can have entirely different fields.[1] Document stores offer high flexibility and are often used for occasionally changing data.[1]

Two documents, one collection

{ "_id": "u7",
  "name": "Ana",
  "address": { "city": "Hue" },
  "phones": ["090-1111"] }

{ "_id": "u8",
  "name": "Bao",
  "hobby": "chess" }

Query by a field inside the document

// MongoDB-style: find users in Hue
db.users.find({ "address.city": "Hue" })

-- SQL needs a column (or a join)
SELECT * FROM users u
JOIN addresses a ON a.user_id = u.id
WHERE a.city = 'Hue';

Made-up example. Documents with different fields in one collection, and querying by content, are the features Wikipedia describes.[25]

  • MongoDB and CouchDB also provide an SQL-like language for complex queries.[1] MongoDB stores documents as BSON (binary JSON) with replication and sharding.[25] Its architecture page names replica sets, sharding, indexing and transactions as its building blocks.[26]
  • CouchDB 2.0 clusters in the Dynamo style: each database is split into q equal shards (default 8), each stored n times (default 3). Any node can take a request, sends it to all copies and answers after a majority (n/2 + 1) respond. It is designed to stay available and partition-tolerant, trading away consistency.[27]
  • DynamoDB supports both key-values and documents.[1] The primer’s link is to the 2007 Dynamo paper; DynamoDB (2012) is that internal store’s managed successor.[29]
  • Elasticsearch, also in the further reading, stores documents in an inverted index mapping each term to the documents containing it. An index is split into shards, each a full Lucene index made of immutable segments; new documents become searchable on a refresh, every second by default.[30]

Dynamo was built to be “always writeable” for Amazon services such as the shopping cart: an “add to cart” is never rejected, and divergent carts are merged when read, at the cost that deleted items can reappear. A typical setting is N = 3 replicas with R = 2 and W = 2, the quorum idea from Unit 5.[28]

Wide column store

Abstraction: nested map ColumnFamily<RowKey, Columns<ColKey, Value, Timestamp>>— the primer[1]
  • The basic unit is a column (a name/value pair). Columns group into column families (like a SQL table), and super column families group column families.[1]
  • Each column is reached with a row key, and columns sharing a row key form a row.[1]
  • Each value carries a timestamp for versioning and conflict resolution.[1]
  • Bigtable, HBase and Cassandra keep keys in lexicographic order, so selected key ranges are cheap to read. These stores offer high availability and scalability and are often used for very large data sets.[1]

Google introduced Bigtable as the first wide column store; it influenced the open-source HBase, often used in the Hadoop ecosystem, and Cassandra from Facebook.[1]

  • Bigtable (OSDI 2006) is “a sparse, distributed, persistent multidimensional sorted map” indexed by row key, column key and timestamp. Its example Webtable stores pages under reversed hostnames like com.cnn.www, so one domain’s pages sit together, with a contents: family for page versions and anchor: columns for link text. Rows are split into tablets of about 100–200 MB, the unit of load balancing. It is built on GFS, the Chubby lock service and immutable SSTable files, and served over sixty Google products in 2006.[32]
  • HBase splits tables into regions (sorted row ranges) served by RegionServers; an HMaster assigns regions and ZooKeeper tracks which servers are alive. Regions split in two when they grow too large.[33]
  • Cassandra combines Dynamo’s distribution and replication with Bigtable’s data and storage model. Data lives in keyspaces (which set replication) and tables, and the partition key decides which nodes hold a row. It is queried with the SQL-like CQL but has no cross-partition transactions, joins or foreign keys.[34]

Graph database

Abstraction: graph— the primer[1]

In a graph database each node is a record and each arc (edge) is a relationship between two nodes. Graph databases are optimized for complex relationships with many foreign keys or many-to-many relationships, and perform well for data models such as a social network.[1]

  • Index-free adjacency. Nodes hold direct references to their neighbours, so each hop costs about the same however big the graph is; a relational join instead looks up a global index.[35]
  • Property graph vs RDF. The labeled property graph (Figure 12.14) puts properties on nodes and edges; RDF expresses everything as subject–predicate–object statements.[35]
  • Query languages include Cypher (Neo4j), Gremlin, SPARQL (for RDF) and the ISO standard GQL.[35]
  • Caveats. The primer calls them relatively new and not yet widely used, with fewer tools and resources, and notes many can only be reached through REST APIs (Unit 15).[1] Wikipedia adds that relational systems are usually faster for bulk operations on uniform records.[35]

SQL: friends of Alice

SELECT p2.name
FROM people p1
JOIN friends f ON f.person_id = p1.id
JOIN people p2 ON p2.id = f.friend_id
WHERE p1.name = 'Alice';

Cypher: same question

MATCH (:Person {name:'Alice'})
      -[:KNOWS]->(f:Person)
RETURN f.name;

Written for this guide after the friends example in Wikipedia’s article: SQL joins through a link table, while a graph query follows the relationship directly.[35]

  • Neo4j describes itself as a graph database platform storing data as connected nodes and relationships, queried with Cypher.[36]
  • FlockDB (Twitter, 2010) stored the follow graph: over 13 billion edges at peaks of 20k writes and 100k reads per second. It ran on MySQL, partitioned with Twitter’s Gizzard library, and stored every edge twice (forward and backward) so “who follows me” was as cheap as “who do I follow”. It was built for huge adjacency lists and set operations, not multi-hop traversal.[37]

Under the hood: NoSQL patterns

Two pieces in the NoSQL further reading explain what these stores share.

  • Ricky Ho’s “NoSQL Patterns” (2009) models them as a big distributed hash table with get, put and delete, spread over a consistent-hashing ring of virtual nodes. Replicas of the same data go on different physical machines, and a client sees one of five consistency models: strict, read-your-writes, session, monotonic read, or eventual.[39] Replicas stay in step with quorums (W + R > N), vector clocks and gossip, as in Dynamo; deletes are kept as marked versions until every replica has seen them.[39]
  • Gessert et al.’s survey (2016) describes the three non-graph data models,[38] sorts systems by CAP and by PACELC: under a Partition choose A or C; Else choose Latency or Consistency. It then splits the design space into sharding (Table 12.2), replication (Table 12.1), storage management and query processing.[38] On storage, it notes many stores (Bigtable, Cassandra, LevelDB, RocksDB) use log-structured merge (LSM) trees, as in Figure 12.13, paying for fast appends with compaction.[38]

12.3SQL or NoSQL

Reasons for each

Reasons for SQL

  • Structured data
  • Strict schema
  • Relational data
  • Need for complex joins
  • Transactions
  • Clear patterns for scaling
  • More established: developers, community, code, tools
  • Lookups by index are very fast

Reasons for NoSQL

  • Semi-structured data
  • Dynamic or flexible schema
  • Non-relational data
  • No need for complex joins
  • Store many TB (or PB) of data
  • Very data-intensive workload
  • Very high throughput for IOPS

Both lists from the primer.[1]

Sample data well suited to NoSQL:[1]

  • Rapid ingest of clickstream and log data
  • Leaderboard or scoring data
  • Temporary data, such as a shopping cart (Dynamo’s own example, above)
  • Frequently accessed (“hot”) tables
  • Metadata and lookup tables

Side by side

Craig Buckler’s SitePoint comparison, in the further reading, models a bookstore both ways.[42]

His conclusion: choose SQL for related, well-defined data where integrity matters (the bookstore, once it takes orders, needs transactions); choose NoSQL for unrelated, evolving or unclear data, or where speed and horizontal scaling come first.[42] Treat the transactions row as a general rule: MongoDB’s own architecture page lists transactions among its features.[26]

A decision tree

The survey’s point is that choosing a database means choosing which properties to give up.[38]

Moving to NoSQL

In InfoQ’s 2012 interview, Couchbase’s Dipti Borkar describes adopting NoSQL as a transition driven by specific application needs, not a wholesale replacement of SQL. Teams usually start looking when performance drops as users grow, since adding commodity servers is cheaper than buying bigger ones, and because relational schema changes need costly ALTER TABLE operations.[41] Her steps:[41]

  1. Define the key requirements (speed of development, scalability, consistent performance, reliability) and match them to a database type.
  2. Run a proof of concept that tests response time, throughput and scale-out.
  3. Design the document data model.
  4. Stage and monitor the rollout, then train the team in the new skills.

She also warns that complex joins and multi-document transactions may have to be simulated in the application, so some projects are better served by a relational database or a hybrid.[41]

Key terms · Unit 12
Relational basics
RDBMS
Data in tables; queried with SQL.
Transaction
Unit of work: BEGIN, changes, then COMMIT or ROLLBACK.
ACID
Atomic, consistent, isolated, durable transactions.
Isolation level
How much concurrent transactions see; strictest is serializable.
Scaling an RDBMS
Master-slave
Master takes writes; slaves serve reads; read-only if master dies.
Master-master
Two masters both take writes and sync with each other.
Lazy · eager replication
Copy after commit (fast, stale) · before commit (consistent, slow).
Replication lag
Delay before a replica shows the master’s latest write.
Federation
Split databases by function (users, forums, products).
Sharding
Split one table’s rows across databases.
Horizontal · vertical partition
Split by rows · by columns.
Shared-nothing
Shards share no data or resources.
Rebalancing
Moving data when shards become lopsided.
Consistent hashing
Ring placement; adding a server moves only nearby keys.
Virtual node
One of many ring points per server, evening out load.
Denormalization
Redundant copies to skip joins; faster reads, slower writes.
Materialized view
Stored query result kept by the DBMS.
SQL tuning
Benchmark · profile
Simulate load (ab) · find slow queries (slow query log).
Index (B-tree)
Sorted tree; O(log n) lookups; costs space and write speed.
Query cache
Cached SELECT results; flushed on writes; gone in MySQL 8.0.
NoSQL
NoSQL
Key-value, document, wide column or graph; joins in app code.
BASE
Basically available, soft state, eventual consistency.
Key-value store
Hash table; O(1); opaque values.
Lexicographic order
Dictionary order of keys, enabling range reads.
Document store
Values are queryable documents (JSON, XML).
Wide column store
Row key → column families → timestamped columns.
Column family
Group of columns, like a SQL table.
Memtable · SSTable
In-memory write buffer · immutable sorted file on disk.
Graph database
Nodes are records; edges are relationships.
Index-free adjacency
Nodes point straight at neighbours; no join lookup.
Vector clock
Per-replica counters that reveal conflicting versions.
PACELC
Partition: A or C; else: latency or consistency.
