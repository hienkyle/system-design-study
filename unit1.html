SYSTEM DESIGN PRIMER · UNIT 1

Scaling fundamentals: from one server to many

A web app that starts on one server eventually outgrows it. This unit follows that app as it grows: first onto a bigger machine, then onto many identical machines behind a load balancer, then through the database, cache and background-work changes that let those machines keep up, and finally to a layout where no single box can take the site down. Each step fixes one bottleneck and exposes the next.[1, 2, 5]

Bigger machine→ more machines→ shared state→ database→ cache→ background work→ redundancy

1.1One bigger machine

The first response to growing traffic is usually vertical scaling: moving the app to a server with more or faster CPU cores, more RAM and more or faster disk.[2, 4] Cores matter because a core works on one task at a time, so a quad-core server can genuinely handle four requests at once; extra processes or threads on one core only take turns.[3] Disks matter most for the database. Server-class SAS drives spin faster than typical desktop SATA drives (15,000 RPM for fast SAS models), and SSDs, with no moving parts, are faster again.[3]

Pros

  • One machine is simple to run and reason about
  • All data stays in one place, so it stays consistent

Cons

  • Hardware has a ceiling
  • Top-end hardware is expensive
  • The one machine is a single point of failure

All three drawbacks point to the same fix: add machines instead of enlarging one.

1.2Many identical servers

Horizontal scaling adds ordinary machines and spreads the traffic across them.[2, 4] It needs two things: a component that decides which server handles each request, and servers that are interchangeable, so that it never matters which one is chosen.

The load balancer

A load balancer becomes the app’s single public entry point. The domain resolves to the balancer’s public IP address, and the back-end servers sit behind it on private IP addresses. This saves scarce IPv4 addresses and means the servers cannot be reached from outside except through the balancer.[3, 4]

  • The balancer can send each request to the least busy server, or split traffic by content, for example images to one group of servers and HTML to another.[3]
  • Balancers come as software (Amazon Elastic Load Balancer, HAProxy, Linux Virtual Server) or as more expensive hardware appliances (Barracuda, Cisco, Citrix, F5).[3]

Round-robin DNS

A cheaper alternative balances in DNS itself: the name server answers each lookup with the next IP address in a list, so clients connect to the back ends directly.[2, 4] It is not very smart. DNS ignores how busy each server is, and because resolvers and browsers cache an answer for its TTL (time to live), traffic can keep piling onto one server after the rotation has moved on.[3]

Clones: interchangeable servers

Behind a balancer, one user might be served by server 2, then server 9, then server 2 again, and must get the same result every time. That leads to a golden rule for scalable servers:[5, 6]

every server contains exactly the same codebase and does not store any user-related data, like sessions or profile pictures, on local disc or memory[5, 6]
  • Same code everywhere. A deployment must reach every server at once, so none keeps serving old code. Deployment tools such as Capistrano solve this, at the cost of some learning outside Ruby on Rails.[5, 6]
  • A “super-clone” image. Once a server holds no user data, it can be captured as a machine image (on AWS, an AMI, Amazon Machine Image). Every new instance starts from that image and only needs the latest code deployed.[5, 6]

1.3Keeping user state off the servers

Sessions are usually the first thing that breaks. By default, PHP stores session data in files on the local disk of whichever server handled the request. If the next request is balanced to a different server, that file isn’t there, and the user appears to be logged out.[3] There are two ways out.

A shared session store

Move sessions into a store that every server can reach. This can be a file server that every web server writes its sessions to,[2, 4] an external database, or an external persistent cache such as Redis, which performs better than a database for this job.[5, 6] “External” means the store runs on its own machines in or near the same data centre, not on the app servers.[5, 6] With sessions outside, it no longer matters which server answers, and the servers become true clones.

Sticky sessions

Alternatively, keep sessions local but send each returning user to the same server every time. This is called a sticky session or session affinity. The balancer usually achieves it with a cookie: it sets one on the first response and reads it on later requests.[2, 4] Putting a server’s private IP in that cookie would leak internal addressing, so the cookie should carry an opaque identifier that only the balancer can map to a server.[3]

Trade-off

Stickiness is simple, but it ties each user to one machine. If that server crashes or is taken out for maintenance, the sessions it held are lost.[12] A shared store avoids this, but it is now a component that must never lose data.

Protecting the shared store: RAID

A central store needs to survive a dead disk. RAID (redundant array of independent disks) combines several drives using striping, mirroring or parity, so the store keeps working when a drive fails.[2, 4, 7]

Table 1.1 Common RAID levels
LevelHow it worksMin. drivesSurvivesGood for
RAID 0Striping: data split across drives2No failuresSpeed only
RAID 1Mirroring: identical copy on each drive2All but one driveRedundancy; a replaced drive rebuilds from its mirror
RAID 5Striping with distributed parity31 driveRedundancy with one drive’s worth of overhead
RAID 6Striping with two parity blocks42 drivesExtra safety for large arrays
RAID 10Mirrored pairs, then striped (1 + 0)4At least 1; up to one per mirrored pairSpeed and redundancy together

Drive counts and fault tolerance follow the standard RAID definitions.[7] RAID protects against hardware failure only; it does not replace backups.[7]

1.4Scaling the database

With stateless servers, the app can now handle thousands of concurrent requests. Then it slows down and finally breaks down again, and the cause is the database. The fixes here are more radical than adding clones.[5, 6]

Replication

Replication keeps automatic copies of the database on more than one server.[2, 4]

  • Master-slave. Every write goes to the master, which replays it on one or more slaves, so each slave holds an identical copy. Reads can be spread across the slaves, which suits read-heavy sites. If the master dies, a slave can be promoted, but until then writes have nowhere to go: the master is a single point of failure for writes.[2, 3, 4]
  • Master-master. Two masters both accept writes and replicate to each other, so losing either one still leaves a master.[2, 3, 4]

Partitioning

Partitioning splits data across servers instead of copying it. Early Facebook ran each school’s network on its own servers, so adding a school meant adding servers, at the cost that users could at first only see their own school’s network. Data can also be split by a property such as last name, with A–L on one database and M–Z on another.[3]

Two long-term paths

As load keeps growing, there are two broad strategies.[5, 6]

  • Keep MySQL and tune it. Hire a database administrator (DBA), set up master-slave replication (read from slaves, write to the master), and keep adding RAM to the master. Later come sharding, denormalization and SQL tuning, and each new measure costs more time and money than the last.[5, 6]
  • Denormalize from the start. Allow no joins in any database query, using MySQL as if it were NoSQL or switching to a NoSQL database such as MongoDB or CouchDB. Joins move into application code. This is far easier while the dataset is small, and the sooner it is done, the less code has to change later.[5, 6]

Storage engines

Within MySQL, each table chooses a storage engine, and the choice affects both features and performance.[3, 10]

Table 1.2 MySQL storage engines compared
EngineTransactionsLockingTypical use
InnoDBYes (ACID)Row-levelThe default, general-purpose engine
MyISAMNoTable-levelRead-only or read-mostly workloads
ArchiveNoRow-levelCompact, unindexed tables for rarely read history and logs

Whichever path is taken, database requests eventually slow down again. The next step is to stop asking the database the same question twice.[5, 6]

1.5Caching

A cache keeps the result of work that has already been done so it can be reused. Caching can happen at several layers, from compiled code up to fully assembled objects.

Compiled code

PHP normally parses and compiles each script on every request, then throws the result away. A bytecode cache keeps the compiled form until the file changes; Python’s .pyc files apply the same idea.[3] In PHP this is now built in as OPcache, which keeps precompiled bytecode in shared memory.[8]

Pre-rendered pages

A dynamic page can be rendered once and saved as a static .html file, because web servers are extremely fast at serving static files. Craigslist works this way. The costs are disk space, the same markup repeated across thousands of files, and difficulty changing the layout of every page later.[2, 3, 4]

Keep caches off the clones

Caching to files on each server’s own disk undoes the work of §1.2: it makes cloning and auto-scaling painful. Caches belong in a shared, in-memory layer.[5, 6]

The database’s own query cache

MySQL could cache the results of identical queries.[2, 4]

Changed since 2012

The MySQL query cache was deprecated in 5.7.20 and removed in MySQL 8.0, because it scaled poorly on busy multi-core servers.[9] The concept still matters, but the feature is gone.

An in-memory cache layer

An in-memory cache such as Memcached or Redis is a key-value store that sits as a buffer between the application and its data store. The app asks the cache first and only goes to the database on a miss.[5, 6] It is fast because everything lives in RAM: Redis on a standard server can handle several hundred thousand reads per second, and writes, especially increments, are also very fast.[5, 6] Facebook relied heavily on Memcached because its traffic was mostly reads.[2, 3] RAM is limited, so the cache must evict entries; dropping the ones used least recently (LRU) keeps the hot data in memory.[3]

What to cache

There are two common patterns for deciding what goes into the cache.[5, 6]

Table 1.3 Caching query results vs caching objects
Cached database queriesCached objects
KeyA hash of the SQL queryAn identifier for an assembled object
ValueThe query’s result setA fully assembled dataset or class instance, such as a Product with its prices, texts, pictures and reviews
Main problemExpiration: when one table cell changes, every cached query that might include it must be found and deletedLittle: delete the object when its underlying data changes
StatusThe older and still most common patternThe recommended pattern
Bonus–Enables background work: workers assemble objects, and the app reads the latest cached object without touching the database

Good candidates for object caching are user sessions (never kept in the database), fully rendered blog articles, activity streams and user-to-friend relationships. Redis adds database-like features such as persistence and built-in lists and sets, while Memcached is the simpler choice when only caching is needed, because it scales very easily.[5, 6]

1.6Moving slow work out of the request

Picture a bakery that has no bread and asks you to come back in two hours. A web app should not make its users wait like that. Asynchronism keeps slow work out of the request–response path, and there are two ways to do it.[5, 6]

Do the work in advance

Bake the bread at night and sell it in the morning: do time-consuming work ahead of time and serve the finished result quickly.[5, 6] This is the pre-rendered pages idea from §1.5 put on a schedule. Pages are rendered to static HTML on every change, often by a script that a cronjob runs every hour. Uploading those pages to AWS S3, CloudFront or another content delivery network (CDN) lets a site handle millions of visitors per hour.[5, 6]

Queue the work

Some requests can’t be foreseen, like a birthday cake with a customer’s name on it. That work has to start when the user asks, without making the user wait for it to finish:[5, 6]

The queue is constantly checked by a pool of workers, which pick up new jobs, process them and signal when each one is done. RabbitMQ is one system for running such a queue; ActiveMQ or a simple Redis list also work.[5, 6] Combined with object caching (§1.5), workers can also assemble cached objects in the background. The result is a backend that scales almost without limit and a frontend that stays responsive.[5, 6]

1.7Removing single points of failure

Every step so far added a component that the whole site now depends on: the load balancer, the database master, the session store. High availability deals with this by running such components in pairs that watch each other through heartbeats, small periodic messages. If one side goes quiet, the other takes over.[3]

  • Active-active: both load balancers accept traffic. If one stops responding, the other takes over its IP address and handles everything.[3, 4]
  • Active-passive: one load balancer handles traffic while the other stands by, and the standby is promoted only if the active one fails.[4]

The same idea works at a larger scale. Global load balancing routes users between whole data centres by region and availability.[3]

Locking it down

The last question is what traffic should reach the data centre at all. The answer follows the principle of least privilege: a firewall opens only the ports each tier needs.[3]

Table 1.4 Which ports to open, and where
PortProtocolWhere it should be open
TCP 80HTTPFrom the internet to the load balancer
TCP 443HTTPSFrom the internet to the load balancer only. The balancer decrypts traffic (SSL offloading), so internal traffic can be plain HTTP.
TCP 22SSHClosed to the public; administrators connect through a VPN first
TCP 3306MySQLOnly between web servers and the database, never from outside

Key terms · Unit 1
Scaling
Vertical scaling
A bigger machine: more CPU, RAM, disk. Simple, but capped and a single point of failure.
Horizontal scaling
More ordinary machines sharing the load.
Single point of failure (SPOF)
One component whose failure takes the whole system down.
Spreading traffic
Load balancer
Public entry point that spreads requests over back-end servers on private IPs.
Round-robin DNS
DNS hands out server IPs in rotation; ignores load and is skewed by caching.
TTL
How long a cached answer (DNS record, cache entry) stays valid.
Clone
An identical, stateless server, often launched from a machine image (AMI).
User state
Session store
Shared, external place for session data (database or persistent cache such as Redis).
Sticky session
Sending a user back to the same server, usually via a balancer cookie. Also “session affinity”.
RAID
Drives combined by striping (0), mirroring (1), parity (5, 6) or both (10).
Database
Replication
Automatic copies of a database on several servers.
Master-slave
Writes to the master, reads from slaves; the master is a write SPOF.
Master-master
Two masters both take writes and sync with each other.
Partitioning / sharding
Splitting data across servers (by school, by A–L / M–Z…).
Denormalization
Storing data redundantly so queries need no joins.
Storage engine
MySQL’s per-table engine: InnoDB (transactions), MyISAM, Archive.
Caching
Bytecode cache
Reuse compiled scripts instead of recompiling (PHP OPcache, .pyc).
In-memory cache
Key-value store in RAM (Memcached, Redis) between app and database.
Cache-aside
Check the cache first; on a miss read the database and store the result.
Cached query vs cached object
Key = hashed SQL (hard to expire) vs key = assembled object (preferred).
LRU eviction
When the cache is full, drop the least recently used entries.
Background work
Asynchronism
Keeping slow work out of the request–response path.
Precomputing
Doing work ahead of time, e.g. a cronjob renders static pages to a CDN.
Job queue & workers
The frontend queues slow jobs; workers process them and signal completion.
Redundancy & security
Heartbeat
Periodic “I’m alive” message; silence triggers fail-over.
Active-active / active-passive
Both nodes serve traffic / one serves while the other stands by.
SSL offloading
The load balancer decrypts HTTPS so back ends don’t have to.
Least privilege
Open only the ports and access each tier needs.
