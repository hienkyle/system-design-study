SYSTEM DESIGN PRIMER · UNIT 7

Domain name system

Clients reach servers by IP address, but people type names. The Domain Name System (DNS) translates a name such as www.example.com into an IP address.[1] This unit covers how the namespace is organised, how a resolver walks it from the root down, how caching and TTL keep lookups fast (and sometimes stale), the main record types, how managed DNS services route traffic, and DNS’s weak spots.

Primer section · Domain name systemMicrosoft · DNS ArchitectureWikipedia · Domain Name SystemDNSimple · DNS articles

7.0What DNS does

Computers find each other by IP address, much like a street address. DNS sits in between: given a domain name, it returns the matching address. This translation is called DNS resolution.[4] Wikipedia describes DNS as a hierarchical and distributed name service and compares it to a phone book.[3]

Why distributed? Before DNS, every host on the ARPANET was listed in one centrally kept HOSTS file (HOSTS.TXT, maintained by SRI). As the network grew, so did the file and the traffic needed to keep copies updated.[2][3] DNS spreads the database across many servers instead, so it can grow without a central bottleneck and each organisation runs its own part.[2] Paul Mockapetris created it in 1983; the core specifications today are RFC 1034 and RFC 1035 (1987).[3]

7.1The namespace

The primer calls DNS hierarchical, with a few authoritative servers at the top level.[1] The names themselves form a tree called the domain namespace. A name is a series of labels separated by dots, read from right (the top of the tree) to left.[2]

Host nameThe leftmost label, naming one machine or resourcewww.example.com

Levels and definitions from Microsoft’s DNS Architecture.[2] Example names are illustrative; example.com is reserved for documentation.

A fully qualified domain name (FQDN) spells out the full path to the root and so ends in a dot: www.example.com.[2] Each label can be up to 63 characters and a full name up to 253.[3]

Zones and delegation

No server holds the whole tree. It is cut into zones: a zone is a connected part of the namespace whose records are stored together in a zone file. A server that loads a zone is authoritative for the names in it.[2]

  • The first record in every zone is the SOA (start of authority). It names the zone’s primary server and holds timing values used for caching and copying the zone.[2]
  • Delegation hands a subtree to other servers. The parent zone holds NS records that point to the child zone’s name servers; for example, the .com servers hold the NS records for example.com.[2][5] Delegating spreads both the management work and the query load.[2]
  • A primary zone is the only writable copy. Secondary zones are read-only copies kept current by a zone transfer, either full (AXFR) or only the changed records (IXFR). A transfer starts when the primary sends a NOTIFY or when the secondary’s refresh interval (set in the SOA) runs out.[2]
Connection to Unit 6

Primary and secondary zones are master-slave replication applied to DNS data: one writable copy, read-only copies that can still answer queries if the primary is down.

Who runs it

The primer notes that DNS servers are generally managed by governments, ISPs and large companies.[1] Going down the tree:

  • Root servers. There are 13 named root server identities, a.root-servers.net to m.root-servers.net, run by 12 organisations (Verisign runs two), including universities, U.S. government agencies, ICANN, RIPE NCC and Japan’s WIDE Project. Each identity is served from many copies worldwide through anycast, and they all publish the root zone file that ICANN maintains.[10]
  • TLD servers manage domains such as .com and .org and point to each domain’s authoritative servers.[4]
  • Authoritative servers for a domain are run by its owner or a DNS host; you pick the provider at your registrar.[4][5]

7.2Resolving a name

Your router or ISP tells your device which DNS server(s) to contact for lookups.[1] That server then does the work of walking the tree.

Who takes part

  • Stub resolver: the small DNS client on your device. It sends the question and waits for a final answer.[4]
  • Recursive resolver: takes the question and does every lookup needed to return a final answer or an error. Your router, your ISP’s server, 8.8.8.8 and 1.1.1.1 are examples.[4]
  • Root servers point to the right TLD servers; TLD servers point to the domain’s authoritative name servers, which hold the official records.[4]

Each resolver ships with a list of root server addresses, called root hints, so it always knows where to start.[2]

A resolver can also be set up with a forwarder: another DNS server it passes unanswered questions to (as recursive queries) before trying the root itself.[2]

Common mix-up

People often say “my name server” when they mean their ISP’s or Google’s recursive resolver. An authoritative server only answers for the zones it hosts; a recursive resolver answers any question by asking others.[4]

Try it

7.3Caching and TTL

Walking the tree on every request would be slow, so answers are cached at several layers. Lower-level DNS servers cache mappings, and your browser and OS can cache results too.[1] A hit at any layer ends the lookup early. Some browsers keep their own short cache, typically around a minute.[3]

Time to live

How long an answer may be cached is set by its time to live (TTL), given in seconds and chosen by the zone’s owner for each record.[1][6][7]

  • The resolver notes when it received a record and counts down. While the remaining TTL is above zero it answers from cache; at zero it drops the record and the next request goes back to the authoritative server.[6]
  • When a cached answer is passed on, it carries the remaining TTL, not the original, so copies further down expire on time too.[2][6]
  • Negative caching: “this name doesn’t exist” answers are cached as well, for a time taken from the zone’s SOA record.[3][7]

Stale answers

Because of caching, a change to a record doesn’t reach everyone at once: copies cached before the change keep being served until their TTL runs out. The primer calls this DNS propagation delay, and it is why cached mappings can become stale.[1][3] DNS is the primer’s example of eventual consistency from Unit 5 for this reason.

Choosing a TTL

Low TTL (e.g. 300 s)

  • Changes spread quickly.[6][7]
  • Used for key records in disaster-recovery set-ups.[7]
  • Cost: more queries to the authoritative server and slower lookups for clients.[6]

High TTL (e.g. 86 400 s)

  • Efficient caching, less load and traffic.[2][6]
  • A day was once a common default.[7]
  • Cost: old answers linger longer after a change.[2][7]

The usual practice: lower the TTL ahead of a planned change (such as moving a web server or MX record), make the change, then raise it again, to at least an hour per DNSimple.[6][7] Microsoft advises against a TTL of 0: it barely improves freshness over 60 seconds but forces constant re-queries.[2] Note that some caching servers apply their own TTLs, so updates may not land exactly on time.[7]

CNAME rules

  • The target must be a name, not an IP. The resolver follows the alias, then looks up the target’s address.[5]
  • The benefit: if the server’s IP changes, you update one A record and every alias follows.[5]
  • A name with a CNAME can’t hold any other record. Because the zone apex (example.com itself) needs NS and SOA records, a CNAME generally can’t be used there; some providers offer an ALIAS-style record for that case.[5]
  • CNAMEs can point to other CNAMEs, but each hop adds a lookup, so chains are discouraged.[5]
About the primer’s example

The primer’s CNAME example reads “example.com to www.example.com”.[1] Given the apex rule above, the usual set-up is the reverse: www.example.com is the CNAME and points to example.com, which holds the A record, as in DNSimple’s example and the zone file above.[5]

MX priority

Each MX record carries a priority number. Sending servers try the lowest number first and move to higher ones if it fails; equal numbers may be tried in either order. The MX target must be a host name that itself has an A or AAAA record.[5]

7.5Managed DNS and traffic routing

Services such as Cloudflare and Amazon Route 53 provide managed DNS: they run the authoritative servers for you. Some can also choose which answer to give, routing traffic in three ways.[1] This ties back to Unit 6: for public-facing active-active servers, DNS is what knows both IPs.

Weighted round robin

Round robin hands out servers in a fixed rotation. Weighted round robin gives each server a weight, usually in proportion to its capacity, and sends more traffic to higher weights: with weights 5 and 1, five requests go to the first server for every one to the second.[9] The primer lists three uses for it in DNS:[1]

  • Prevent traffic from going to servers under maintenance (give them no weight).
  • Balance between varying cluster sizes (a cluster twice as large gets twice the weight).
  • A/B testing (send a small share of users to a new version).

Latency-based routing

In Route 53, you create one record per region where your application runs. For each query, Route 53 picks the region with the lowest latency for that user and returns that region’s address.[8]

  • Example: with load balancers in Oregon and Singapore, a user in London gets whichever has lower London latency.[8]
  • Latency is measured between users and AWS data centers, not your servers, and collected over time, so the same user might be sent to Oregon one week and Singapore the next.[8]

Geolocation-based routing

Here the answer depends on where the query comes from, by continent, country, or U.S. state. For example, all queries from Europe can go to a load balancer in Frankfurt.[8]

  • When locations overlap, the smallest region wins (a Canada record beats a North America record for Canadian users).[8]
  • Some IPs can’t be placed on a map, so a default record is needed; without one, those users get no answer.[8]
  • Uses: localise content (language), restrict content to regions where you have distribution rights, and keep load predictable.[8]

Weighted round robinLatency-basedGeolocation-based

Keep in mind

A routed answer is cached like any other answer, for its TTL (7.3). Moving users between servers through DNS therefore takes effect only as caches expire, which is one reason low TTLs are used for records that may need to change quickly.[7]

7.6Disadvantages

Disadvantages: DNS

  • Contacting a DNS server adds a slight delay, though caching reduces it.[1]
  • DNS server management can be complex; it is generally handled by governments, ISPs and large companies.[1]
  • DNS services have been hit by DDoS attacks, leaving users unable to reach sites such as Twitter if they don’t know the site’s IP address.[1]

DDoS: the Dyn attack

The primer’s example is the attack on the DNS provider Dyn on 21 October 2016.[1] Three waves of distributed denial-of-service traffic came from Internet-of-Things devices, such as cameras, home routers and baby monitors, infected with the Mirai malware. Dyn reported malicious requests from tens of millions of IP addresses. Sites using Dyn for DNS, including Twitter, Netflix, GitHub, Reddit and PayPal, became unreachable for many users in Europe and North America.[11]

The sites’ own servers were running; what failed was the step that turns their names into addresses. This makes DNS a dependency every service shares, and a provider outage affects all of its customers at once.

Security, briefly

Beyond the primer’s scope, but useful context from Wikipedia:[3]

  • Classic DNS travels unencrypted (UDP port 53, TCP for large answers and zone transfers), exposing it to eavesdropping and cache poisoning, where forged answers are planted in a resolver’s cache.
  • DNSSEC adds cryptographic signatures so answers can be verified.
  • DNS over TLS (TCP port 853) and DNS over HTTPS (port 443) encrypt queries.
In an interview

DNS is the first hop of every request. Mention the TTL trade-off when you plan fail-over or a migration, and that managed DNS can split traffic by weight, latency or location before any load balancer (Unit 9) is involved.
