SYSTEM DESIGN PRIMER · UNIT 5

Consistency patterns

Unit 4 showed that a distributed system must sometimes trade consistency for availability. This unit names the levels of consistency you can choose from: weak, eventual and strong. Each answers one question: after a write, will a read see it?[1] It also covers the synchronous vs asynchronous replication behind each level, the inconsistency window, why transactions need strong consistency, and Barrett’s comparison of backups, master/slave, multi-master, 2PC and Paxos across datacenters.

Primer section · Consistency patternsRyan Barrett · “Transactions Across Datacenters”, Google I/O 2009 (slides + talk)Werner Vogels · “Eventually Consistent” (2009)

5.1The problem: many copies

Once the same data is stored on several machines (replicas), you must decide how to synchronize them so that clients get a consistent view of the data.[1] The primer measures every option against the definition of consistency from the CAP theorem (Unit 4): every read receives the most recent write or an error.[1]

The three patterns differ in how much of that promise they keep. The deciding factor is how a write travels from one replica to the others, which is the job of replication.

Synchronous vs asynchronous replication

The primer ties eventual consistency to asynchronous replication and strong consistency to synchronous replication.[1] The difference is when the writer is told “done”:

  • Synchronous: the write is copied to the other replicas before it is acknowledged. Every replica has it once the client hears “done”, so reads anywhere see it. The client waits longer.
  • Asynchronous: the write is acknowledged as soon as one replica has it, and copied to the others afterwards. The client gets a fast answer, but other replicas lag behind for a while.

5.2Weak consistency

After a write, reads may or may not see it. The system takes a best effort approach: it tries to deliver the data but makes no promise.[1] Barrett’s image for this is a “message in a bottle”.[2]

It is seen in caches such as memcached, and works well for real-time uses such as VoIP, video chat and real-time multiplayer games.[1] The primer’s example: if you lose reception for a few seconds during a phone call, you don’t hear what was said while you were cut off when the connection returns.[1] In real time, old data is useless, so there is no point in recovering it.

Barrett calls weak consistency “what you get from caches”: you put something in, and later it may or may not be there, since a busy cache keeps evicting entries. In a game you care where the other player is now, not 30 seconds ago. It is the right trade-off for those cases, but for persistent data storage it is too weak.[3]

Connection to other units

The same real-time examples appear in the primer’s case for UDP, which suits uses where late data is worse than lost data.[5] A cache such as memcached is a copy of data that may simply not hold the latest value.

5.3Eventual consistency

After a write, reads will eventually see it, typically within milliseconds. Data is replicated asynchronously.[1]

It is seen in DNS and email, and works well in highly available systems.[1] Barrett adds search-engine indexing, SMTP, snail mail, Amazon S3 and SimpleDB, and App Engine’s mail service.[2] As an example of the delay, he estimated that SimpleDB writes became visible after about 400–500 ms on average in 2009, sometimes a few seconds.[3] It is the pattern an AP system falls back on during a partition (Unit 4), and the “E” in BASE, which most NoSQL stores favour (Unit 12).[5]

The inconsistency window

Vogels names the gap between a write and the moment every reader is guaranteed to see it the inconsistency window. Without failures, its maximum size depends on communication delays, system load and the number of replicas. DNS is his standard example: an updated name spreads according to a configured pattern, combined with caches that expire after a time limit, until all clients see it.[4]

A naming difference

The primer lists weak and eventual as separate levels.[1] Vogels treats eventual consistency as a specific form of weak consistency: one that promises all reads return the last value if no new updates are made.[4] Both agree on the key difference: eventual consistency guarantees convergence; plain weak consistency does not.

5.4Strong consistency

After a write, reads will see it. Data is replicated synchronously.[1] This matches the CAP definition of consistency, and is what a CP system protects during a partition (Unit 4).

It is seen in file systems and RDBMSes, and works well in systems that need transactions.[1] Barrett adds the App Engine datastore and Azure tables.[2] Barrett calls it the ideal for read-write data, because it is the simplest model to think about and program against.[3] The cost is the waiting shown in Figure 5.1: every write pays for the slowest replica it must reach.

Why transactions need it

A transaction groups operations that must succeed or fail together. Barrett’s example is a money transfer from A to B: subtract from A, then add to B. If another transaction touches A or B in between, or the thread running it dies halfway (a crash, or hitting a request deadline), money can vanish or appear.[2][3] Transactions exist for correctness: to enforce invariants (rules that must always hold, such as “the total amount of money is unchanged”), the ACID guarantees.[2] ACID is covered under RDBMS in Unit 12: atomicity, consistency, isolation, durability.[5]

Two meanings of “consistency”

The C in CAP (and this unit) is about replicas agreeing: a read sees the latest write. The C in ACID is about a transaction moving the database from one valid state to another.[5] Barrett’s slide lists both under “why transactions”, since a transaction across replicas needs both.[2]

In an interview

Name the level per piece of data, not per system. Ask: what goes wrong if a user reads an old value here? If nothing much (a feed, a view count), eventual is enough and buys availability. If money or invariants are involved, you need strong consistency and should accept the latency.

5.6Across datacenters

The primer’s one source for this section is Ryan Barrett’s Google I/O 2009 talk, based on his work on the App Engine datastore. It starts from the three consistency levels and asks how to keep data consistent when copies live in different datacenters.[2][3] He focuses on structured user data: data that users both write and read, and whose writes they expect to see. He considers it the hardest kind of data to run across datacenters.[3]

CAP is not black and white

Barrett opens with Brewer’s CAP theorem, but adds that you don’t simply get two of three: often you can get a little of one and a little more of another.[3]

Why (and why not)

Why spread data across datacenters: catastrophic failures, expected failures, routine maintenance, and geolocality (serving users from nearby, as CDNs and edge caches do).[2] Why not: the network between datacenters is far worse than the network inside one.

Table 5.2 Network inside vs between datacenters (Barrett, 2009)
Within a datacenterBetween datacenters
BandwidthHigh: 1–100 Gbps interconnectsLow: 10 Mbps–1 Gbps
Latency< 1 ms within a rack, 1–5 ms across50–150 ms
CostLittle to noneExpensive (fibre)

For scale: a round trip between the US west and east coasts takes about 30 ms from the speed of light alone, and busy internet peering points can add another 30–50 ms.[3] That latency is the price of synchronous replication: a strongly consistent write that must reach another datacenter waits for it, often twice.

Accepting writes in more than one place also creates inconsistency. Barrett’s example: Alice sends money to Bob in one datacenter and to Eve in another, but only has enough for one. If both are accepted and reconciled later, money has been created.[3]

Multihoming options

Multihoming means serving from several datacenters. Barrett calls it hard, harder if it must be consistent, and hardest with real-time writes. He gives three options:[2]

Table 5.3 Barrett’s three multihoming options
OptionHowWeaknessExamples (2009)
1. Don’t (“bunkerize”)One datacenter; the most common choiceBad at catastrophic failure (large-scale data loss); no geolocation for servingAzure tables, SimpleDB
2. Primary with hot failover(s)One primary; standbys take over on failureWindow of lost data; failover data may be inconsistent; reads can be geolocated, writes can’tAWS (pick US or EU), banks, brokerages
3. True multihomingSimultaneous writes in different datacentersPaid for in latency; two-way is hard, N-way harder—

From the slides.[2] “Hot failover” is the active-passive fail-over of Unit 6.

  • Bunkerizing means making one site as redundant as possible: several power sources, several network providers, backup cooling. It still fails sometimes. In 2009 the SVColo datacenter lost power for about 2–2.5 hours, taking down Twitter and FriendFeed, which were both hosted only there. Barrett adds that human error, someone pressing the wrong button, causes many outages.[3]
  • Primary with hot failover works like MySQL master-slave replication: one datacenter takes writes and the others can serve reads. Because copying is asynchronous, data still “on the wire” when the primary fails is unavailable, or lost if the failure is destructive.[3]
  • True multihoming is the “holy grail”: every datacenter serves reads and writes, consistently, with working transactions.[3]
Story · NASDAQ’s 27 miles of fibre

Barrett tells a story he says may be an urban myth. NASDAQ ran two datacenters near each other and used two-phase commit across them, so every trade was stored in both or neither. When buying network equipment, its engineers arrived with suitcases of fibre exactly as long as the 27 miles between the sites, and only bought gear that kept round trips within a window of about 2–3 ms.[3] Strong consistency across sites is possible, but distance is the limit.

Techniques and trade-offs

Barrett then compares five ways of keeping copies in sync, from crudest to most rigorous:[2]

  • Backups: make a copy (“sledgehammer”). Weak consistency, usually no transactions.[2] A backup that reads data from start to end over hours sees different moments: if money moves from A to B after A is copied but before B is, the backup breaks the transaction. It runs offline, so it doesn’t slow the live system, but everything since the last backup can be lost, and moving datacenters means backup, restore and downtime.[3]
  • Master/slave (M/S) replication: usually asynchronous, good for throughput and latency; used by most RDBMSes (e.g. MySQL binary logs). Weak/eventual consistency. Detailed in Unit 12.[2] Latency and throughput stay as before, only the small unreplicated window is lost, and on failover replicas serve reads only until a new master is set up. Getting consistent, transaction-safe replicas takes deliberate design.[3]
  • Multi-master (MM) replication: merging concurrent writes made at several places. Asynchronous, eventually consistent. It needs a serialization protocol to order writes, such as a timestamp oracle handing out ever-increasing timestamps, which is either a single point of failure or itself needs a consensus protocol. No global transactions.[2] Barrett explains that there is no usable global clock, so the order must be made up. Besides a timestamp oracle, options are local timestamps with clock-skew detection, per-object version numbers, or a consensus protocol. He likens it to multithreading where the locks are taken after the fact. The upside: on failover every datacenter can keep taking writes.[3]
  • Two-phase commit (2PC): a semi-distributed consensus protocol (a way for nodes to agree) with one coordinator. Heavyweight, synchronous, high latency. 3PC adds a round trip to make it asynchronous.[2] Each transaction’s coordinator is one participant; with only a few datacenters the same ones keep coordinating, and transactions through a coordinator are serialized, which hurts throughput. It is the first true multihoming technique here: a write is stored in all datacenters or none, so nothing acknowledged is lost. For failover you run at least N + 1 datacenters, so one can go down while N keep serving.[3]
  • Paxos: a fully distributed consensus protocol. A write succeeds once a majority accepts it, so it survives a minority of nodes failing. Similar to 2PC/3PC and lighter, but still high latency.[2] There is no master per transaction, so many Paxos rounds can run in parallel, giving better throughput than 2PC. Both still need two round trips between datacenters before confirming a write: around 100–250 ms depending on distance.[3]

From the final version of the table on Barrett’s “Paxos” slide, with its merged cells and colours (green good, yellow middling, red bad).[2] The slides build the table up one column per technique, as the talk does.[3]

Barrett points out that no column is green all the way down. The pattern in the table is the unit’s main lesson: moving right buys stronger consistency and less data loss, and pays in latency and throughput.

Barrett’s conclusions

What App Engine chose. The team wanted Paxos for the datastore, but it would have raised average writes from about 30–50 ms to about 150 ms. Placing datacenters close together, or even two nodes in the same datacenter, did not help enough. Multi-master and 2PC were ruled out early: the first gives up strong consistency, the second write throughput. The datastore uses master-slave replication across datacenters, mainly for latency, with replication done per commit to keep replicas consistent with transactions.[3] Paxos is still used where latency matters less: coordinating moving state, usually through a lock server, plus memcache and offline processing.[2][3]

His closing points:[2][3]

  • No silver bullet. No column of Table 5.4 is good on every row.
  • Still worth doing. A two-hour outage, let alone data loss, is unacceptable.
  • Let the application choose. A bank wants 2PC or Paxos across datacenters; a game just wants fast responses. He hoped to let developers pick per write between strong writes and fast, highly available ones that may occasionally read stale data.

5.7Going further: finer guarantees

This section goes beyond the primer, using Werner Vogels’ article (Amazon’s CTO). Between “eventual” and “strong” sit guarantees about what a particular client sees. They are often enough to make an eventually consistent system feel correct to its users.[4]

Table 5.5 Variations of eventual consistency (Vogels, 2009)
GuaranteeMeaning
CausalIf A tells B it updated an item, B’s later reads see that update. Clients with no such link get plain eventual consistency.
Read-your-writesAfter A updates an item, A always sees the new value, never an older one.
SessionRead-your-writes, kept for as long as a session lasts.
Monotonic readsOnce a client has seen a value, it never later sees an older one.
Monotonic writesWrites from the same client are applied in order.

Quorums: N, W, R

Vogels also shows how a replicated store can choose its level. With N replicas, a write waits for W of them to acknowledge, and a read asks R of them. If W + R > N, every read set overlaps the latest write set, so reads are strongly consistent; smaller W and R give faster but eventually consistent operations.[4] For example, with N = 3, W = 2 and R = 2, any two replicas you read include at least one that took the write.
