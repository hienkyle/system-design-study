SYSTEM DESIGN PRIMER · UNIT 10

Reverse proxy (web server)

A reverse proxy is a web server that centralizes internal services and provides a unified interface to the public. It forwards each client request to a server that can fulfill it, then returns that server’s response to the client.[1] This unit covers what a reverse proxy does on the way through (security, SSL termination, compression, caching and static content), how it differs from the load balancer of Unit 9, and what it costs.

10.0What a reverse proxy is

A proxy is a device or server that sits between two parties and acts on behalf of one of them.[2] A reverse proxy sits in front of web servers. To a client it looks like an ordinary web server, but it only relays the client’s requests to one or more servers behind it.[5] The responses come back looking as if the proxy produced them itself.[2]

F5 calls the reverse proxy a website’s public face: its address is the one advertised for the site, and it sits at the edge of the site’s network to accept requests from browsers and mobile apps.[2] That edge position is why the web servers can stay behind a firewall on the internal network, with only the proxy exposed to the Internet.[5]

The primer’s title says “(web server)” because the two are usually the same software. Reverse proxying is built into popular open-source web servers.[5] NGINX Plus, for example, is described as an all-in-one load balancer, reverse proxy, web server, content cache and API gateway.[16]

Forward vs reverse proxy

The word “reverse” is relative to an ordinary forward proxy. A forward proxy is used when clients are restricted to a private, internal network and ask the proxy to fetch resources from the public Internet for them.[5] A reverse proxy works the other way round (Figure 10.2, Table 10.1).

Table 10.1 Forward and reverse proxies[5]
Forward proxyReverse proxy
Sits in front ofClients on a private networkServers on a private network
Acts forThe clientsThe servers
Typically set up byA network whose clients are restricted to itCompanies that run web servers
Can hide—The existence and characteristics of the origin servers
Who knows it is thereThe clients use it to reach the InternetClients think it is the web server

How a request is forwarded

A reverse proxy can act as a simple forwarding service or take an active part in the exchange. A full proxy keeps two separate network stacks: the client opens a TCP connection to the proxy, and the proxy opens its own, independent connection to the server. The two are never blended.[2] Listing 10.1 is NGINX’s basic form: requests under a path are passed to the server named by proxy_pass.[8]

# NGINX admin guide: pass /some/path/ to an app on port 8000
location /some/path/ {
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;   # tell the app who the client is
    proxy_pass http://localhost:8000;
}

Listing 10.1 A minimal NGINX reverse proxy.[8] NGINX can also pass requests to app servers over non-HTTP protocols such as FastCGI, uwsgi, SCGI and memcached.[8]

Because the server’s connection now comes from the proxy, the server sees the proxy’s address instead of the client’s. The fix is a header carrying the original address: X-Real-IP above, or X-Forwarded-For, which HAProxy adds with option forwardfor. The application must then be configured to log that header instead.[4]

Since it reads each request, a reverse proxy can also decide where to send it. F5 lists parameters such as user device, location, network conditions, application health and even time of day.[2] Wikipedia’s common case is the URL: one public IP address in front of several internal servers, chosen by the path of the request.[5] This is how one proxy centralizes internal services behind a single interface.[1]

10.1Benefits

Everything a reverse proxy offers follows from its position: every request and response passes through it. Table 10.2 summarizes the primer’s list; the subsections below take one benefit each.[1]

Table 10.2 Benefits of a reverse proxy[1]
BenefitWhat the proxy doesWhat the backend servers gain
Increased securityHides backend details, blacklists IPs, limits connections per clientNever exposed directly to the Internet
Scalability and flexibilityIs the only IP clients seeCan be scaled or reconfigured freely
SSL terminationDecrypts requests, encrypts responsesNo TLS work; no X.509 certificate on each server
CompressionCompresses responsesNo compression work
CachingReturns cached responsesFewer requests to answer
Static contentServes HTML/CSS/JS, photos, videos directlyOnly dynamic requests reach them

F5 groups SSL termination, compression and caching under one name, web acceleration: techniques that cut the time to produce a response and return it to the client.[2] The NGINX snippets below show what each benefit looks like in configuration. They are taken from NGINX’s documentation and are illustrations, not a complete setup.

Increased security

The primer lists three security gains: hide information about backend servers, blacklist IPs, and limit the number of connections per client.[1] With nothing about the backend servers visible outside the internal network, malicious clients cannot reach them directly to exploit vulnerabilities. Blacklisting (F5 says denylisting) and per-client connection limits help protect the servers from DDoS attacks.[2] Wikipedia adds that reverse proxies can include application firewall features against common web attacks.[5]

# blacklist IPs: rules are checked in order until the first match
location / {
    deny  192.168.1.1;
    allow 192.168.1.0/24;
    allow 10.1.1.0/16;
    allow 2001:0db8::/32;
    deny  all;
}

# limit connections per client: one key per client IP address
limit_conn_zone $binary_remote_addr zone=addr:10m;
location /download/ {
    limit_conn addr 1;
}

Listing 10.2 IP rules from nginx.org’s access module[14] and a one-connection-per-IP limit from the NGINX admin guide.[13] $binary_remote_addr is the client’s IP in binary form, which is shorter than the text form and so takes less space in the shared memory zone.[13]

Increased scalability and flexibility

Clients only see the reverse proxy’s IP, so you can scale the servers behind it or change their configuration without clients noticing.[1] F5 notes this is particularly useful with load balancing, where the number of servers rises and falls with traffic.[2] Compare Unit 7, where clients keep cached DNS answers until their TTL expires.

SSL termination

With SSL termination, the proxy decrypts incoming requests and encrypts server responses, so the backend servers do not have to perform these potentially expensive operations. It also removes the need to install X.509 certificates on each server.[1] An X.509 certificate binds a public key to an identity such as a hostname; it is signed by a certificate authority and checked by the browser when an HTTPS connection starts.[6] The proxy may also have TLS acceleration hardware for this work.[5]

# NGINX terminates HTTPS; the certificate and key live only here
server {
    listen              443 ssl;
    server_name         www.example.com;
    ssl_certificate     www.example.com.crt;
    ssl_certificate_key www.example.com.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;
    #...
}

Listing 10.3 An HTTPS server in NGINX.[12] The most CPU-intensive step is the TLS handshake. NGINX reduces handshakes with keepalive connections, which carry several requests, and by reusing SSL session parameters from a session cache shared by all workers (about 4,000 sessions per megabyte).[12]

This is the same SSL termination a load balancer offers (Unit 9). It is one feature where the two overlap.

Compression

The proxy can compress server responses,[1] which speeds up loading times.[5] NGINX notes the trade-off: compression often shrinks the data a lot, but it happens at runtime and adds processing overhead that can hurt performance.[10]

server {
    gzip on;
    gzip_types      text/plain application/xml;   # which MIME types to compress
    gzip_proxied    no-cache no-store private expired auth;
    gzip_min_length 1000;                          # skip very small responses
    ...
}

Listing 10.4 gzip compression in NGINX.[10] By default NGINX compresses only text/html; gzip_types adds other types. It does not compress responses that were already compressed on the proxied server. gzip_proxied decides which responses to proxied requests (detected by the Via header) get compressed, for example those marked private, which are unlikely to be cached.[10]

Caching

The proxy can return the response for cached requests without asking a backend.[1] Caches of this kind can often satisfy a considerable number of requests, greatly reducing load on the origin servers. Wikipedia calls this web acceleration, and notes that both static and dynamic content can be cached.[5] Unit 13 lists this as web server caching.

http {
    proxy_cache_path /data/nginx/cache keys_zone=mycache:10m;  # disk path + key zone in memory
    server {
        proxy_cache mycache;
        location / {
            proxy_pass http://localhost:8000;
        }
    }
}

Listing 10.5 Turning on NGINX’s content cache.[9] By default it caches responses to GET and HEAD requests, keyed by the request string. Entries do not expire on their own; they are removed only when the cache passes its maximum size, least recently used first. proxy_cache_valid 200 302 10m; limits how long responses stay valid.[9]

Static content

The proxy can serve static content directly: HTML, CSS and JavaScript files, photos, videos and so on.[1] Only requests that need the application then travel on to it. In NGINX, the root directive names the folder, and NGINX joins it with the request’s URI: a request for /images/photo.jpg is answered from /www/data/images/photo.jpg.[11]

server {
    root /www/data;

    location / {
    }

    location /images/ {
    }

    location ~ \.(mp3|mp4) {
        root /www/media;          # video and audio from another folder
    }
}

Listing 10.6 Serving static files from disk in NGINX.[11]

More uses

Wikipedia lists further jobs a reverse proxy can take on:[5]

Hiding origin serversMakes the real location of a site harder to find, which complicates takedowns and blocking.
Load balancingSpreads requests over several servers, rewriting URLs to match each server’s internal location if needed.
One IP, many serversSeveral web servers on different ports or machines share one public IP; the proxy picks one per request.
Spoon-feedingTakes a whole generated page at once and feeds it to the client at the client’s pace (Section 10.3).
A/B testingServes different versions to different clients without the app deciding.
AuthenticationAdds access authentication in front of a server that has none.

Large websites and CDNs (Unit 8) use reverse proxies together with other techniques to balance load between their internal servers.[5]

Try it: through the proxy

Figure 10.3 puts the benefits together. Each checkbox is one feature configured on the proxy, matching a listing above:

  • SSL termination (Listing 10.3): the proxy holds the certificate and decrypts requests. Off means the encrypted connection passes straight through to a backend.
  • IP deny list (Listing 10.2): requests from 192.0.2.66 are refused at the proxy.
  • Static content (Listing 10.6): the proxy serves files such as /images/logo.png from its own disk.
  • Caching (Listing 10.5): the proxy stores GET responses and answers repeats itself.
  • Compression (Listing 10.4): the proxy gzips responses of the listed types.

Pick a request and a client, tick or untick features, and press Send. Send the product page twice with caching on to see a cache hit, and switch SSL termination off to see which features depend on the proxy reading the request.

Things to notice in Figure 10.3:

  • The client only ever connects to 203.0.113.10. The 10.0.0.x addresses never leave the internal network.
  • With SSL termination on, backends never handle TLS. Switch it off and the proxy can only pass the encrypted connection on: it cannot read the URL, so caching, compression, static files and URL routing all stop working. Wikipedia explains why: to filter, cache or compress encrypted traffic, a proxy must first decrypt it.[5]
  • The deny list still works with SSL termination off, because the client’s IP is in the packet header, not in the encrypted payload.
  • With caching and static content on, repeated GET requests never reach a backend.

10.2Load balancer vs reverse proxy

Both sit between clients and servers and both improve efficiency, so they are easy to confuse. The difference is when each is worth deploying:[1]

  • A load balancer is useful when you have multiple servers. Often it routes traffic to a set of servers that all serve the same function.
  • A reverse proxy can be useful even with just one web server or application server, because the benefits in Section 10.1 apply either way.
  • Solutions such as NGINX and HAProxy support both layer 7 reverse proxying and load balancing.

F5’s glossary, which the primer links for this comparison, gives the reasons. Load balancers are most commonly deployed when the volume of requests is too much for one server to handle efficiently. Adding servers also removes a single point of failure. The load balancer’s job is then to make the best use of each server’s capacity, prevent overload, and return the fastest response. A reverse proxy, by contrast, often makes sense with a single server.[2] Both can be dedicated devices, but in modern architectures both are increasingly software on commodity hardware.[2]

Table 10.3 Load balancer and reverse proxy compared
Load balancerReverse proxy
Main jobDistribute requests among a group of servers[2]Accept requests, forward each to a server that can fulfill it, return the response[2]
Worth it with one server?No: it needs multiple servers[1]Yes[1]
Servers behind itUsually all serve the same function[1]Can be different internal services, chosen by URL[5]
Shared featuresSSL termination, hiding the servers, one public address; a layer 7 load balancer is often called a reverse proxy (Unit 9)
ExamplesNGINX and HAProxy do both[1]

One tool, both roles

In NGINX the step from one role to both is small. A reverse proxy for one server points proxy_pass at that server. A load balancer points proxy_pass at an upstream group of servers instead, and NGINX balances them with round robin unless told otherwise.[15] Switch between one and several servers in Figure 10.4.

Example: SSL proxy in front of HAProxy

The roles can also be split between two programs on one machine. The HAProxy architecture guide’s third example starts with a single HTTPS web server. HAProxy (version 1.2) did not handle SSL, so the old box runs Apache with mod_ssl as an SSL reverse-proxy-cache on port 443, in front of HAProxy on 127.0.0.1:8000, which balances four cheap web servers (Figure 10.5). Taking SSL off the servers frees even more of their resources.[4]

listen 127.0.0.1:8000
   mode http
   balance roundrobin
   cookie SERVERID insert indirect nocache     # nocache: mark cookie pages private
   option httpchk HEAD /index.html HTTP/1.0
   server webA 192.168.1.11:80 cookie A check
   server webB 192.168.1.12:80 cookie B check
   server webC 192.168.1.13:80 cookie C check
   server webD 192.168.1.14:80 cookie D check

Listing 10.7 HAProxy behind the SSL reverse proxy, from the guide.[4]

The cache brings one catch. HAProxy inserts a SERVERID cookie for session persistence (Unit 9), and a page carrying one client’s cookie must not be cached and served to others. The nocache option makes HAProxy add Cache-Control: private to such responses, so Apache does not cache them. Apache is also configured to add X-Forwarded-For itself, so the application still learns the client’s IP.[4]

10.3Inside NGINX as a proxy

The primer’s further reading includes the NGINX architecture article, already covered in Unit 9 (Figure 9.7). Three parts of it matter for a reverse proxy:[3]

  • Event-driven workers. Each worker process is single-threaded and non-blocking, and handles network connections, reads and writes content on disk, and talks to upstream servers. One worker per CPU core (worker_processes auto;) is the recommended setup.
  • Cache processes. The cache loader runs at startup, loads the on-disk cache metadata into memory, then exits. The cache manager runs periodically and prunes the disk cache to its configured size. Workers share cache data through shared memory.
  • Reloads without downtime. On nginx -s reload, the master starts new workers with the new configuration, while the old workers finish their current requests and exit. A proxy that every request passes through can be reconfigured without dropping connections.

NGINX’s caching guide adds detail on the two cache processes. The cache manager removes the least recently accessed data when the cache exceeds max_size, and the cache loader works in small iterations so it does not slow NGINX down right after startup.[9]

Buffering slow clients

NGINX buffers proxied responses by default. It reads the whole response from the backend as fast as the backend can send it, then delivers it to the client at the client’s own speed. Without this, a slow client would tie up the backend for the whole download. Buffering can be switched off (proxy_buffering off;) for fast, interactive clients that should get data as soon as it arrives.[8] Wikipedia calls this spoon-feeding: the program that generated the page does not have to stay open while the client downloads it.[5] Press Play in Figure 10.6 to compare.

A slow client holds the app server more than ten times longer without buffering. With a fast client the difference shrinks, which is why NGINX suggests turning buffering off for fast, interactive clients.[8]

10.4Disadvantages

Disadvantages: reverse proxy

  • Introducing a reverse proxy results in increased complexity.[1]
  • A single reverse proxy is a single point of failure. Configuring multiple reverse proxies (a failover) increases complexity further.[1]

Failover, the primer’s link, means switching to a redundant or standby system when the active one fails. It is automatic, often triggered by a missing heartbeat; a deliberate, manual switch is a switchover, and returning to the original setup afterwards is failback.[7] The active-passive and active-active setups from Units 6 and 9, such as two proxies sharing a virtual IP, apply to reverse proxies just as to load balancers.

Wikipedia shows how large the failure can be. An outage from a misconfiguration, a DoS attack or a software fault makes every service behind the proxy unreachable, even when the services themselves are healthy. Its example is a 2020 Cloudflare outage that briefly took down sites relying on its reverse-proxy edge, including Discord.[5]

Security risks

The same position that makes a reverse proxy useful makes it a target. Wikipedia lists the risks:[5]

  • It sees everything. A proxy can track client IPs and read or modify unencrypted traffic, and so can anyone who compromises it.
  • It holds the keys. To filter, cache or compress encrypted traffic, it must decrypt and re-encrypt it, so it needs the TLS certificate’s private key. That widens access to unencrypted data and makes the proxy a more valuable target.
  • It widens the attack surface. Internal applications exposed through a proxy are often not hardened to public standards.
  • It needs updates. A proxy that does not filter attacks, or whose attack signatures are out of date, can let a zero-day exploit through to the systems behind it.
  • Third parties. Handing private keys to a third party’s reverse proxy puts confidentiality, integrity and availability in that party’s hands.
In an interview

Put a reverse proxy (often NGINX) in front of the web or application tier, even with one server: it terminates SSL, compresses, caches, serves static files and hides the servers. When there are several servers, the same software also load-balances them. Then name its costs: complexity, and a single point of failure that needs a failover pair.
