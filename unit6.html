SYSTEM DESIGN PRIMER · UNIT 6

Availability patterns

Unit 4 defined availability as every request getting a response. This unit covers how systems achieve it: keep a spare ready to take over (fail-over), keep extra copies of the data (replication), and measure the result in nines.[1] It walks through active-passive and active-active fail-over (heartbeats, hot vs cold standby), master-slave, master-master and buddy replication and their costs, and how components in sequence vs in parallel change overall availability.

Primer section · Availability patternsPrimer · Master-slave & master-master replicationJonas Bonér · “Scalability, Availability & Stability Patterns”

6.0Two complementary patterns

The primer names two patterns that together support high availability: fail-over and replication.[1] They solve different halves of the problem:

  • Fail-over keeps the service answering: when a server dies, another one takes its place.
  • Replication keeps the data available: the server that takes over needs a copy of the data to serve.

Bonér’s deck, the source the primer credits for its replication diagrams, groups them the same way under “Availability patterns”: fail-over, then replication in four forms (master-slave, tree, master-master and buddy).[3]

6.1Fail-over

Fail-over is switching work from a failed server to a working one. The primer describes two arrangements, which differ in whether the second server handles traffic before anything goes wrong.[1]

Active-passive

One server is active and handles all traffic; the other is passive, on standby. The two exchange heartbeats, small periodic “I’m alive” messages. If the heartbeat is interrupted, the passive server takes over the active server’s IP address and resumes service. Because the address moves, clients keep using the same IP and don’t need to know a switch happened.[1]

How long the service is down depends on the standby’s state:[1]

  • Hot standby: the passive server is already running, so it can take over almost at once.
  • Cold standby: the passive server must first start up, so downtime is longer.

Active-passive fail-over is also called master-slave fail-over.[1]

Active-active

In active-active, both servers handle traffic and spread the load between them. Since either can be reached, something has to know both addresses:[1]

  • Public-facing servers: DNS must know the public IPs of both (DNS is Unit 7).
  • Internal-facing servers: the application logic must know about both.

Active-active fail-over is also called master-master fail-over.[1] The same two modes come back for load balancers in Unit 9.

Fail-back and other cases

Bonér’s fail-over slides (diagrams credited to Michael Nygard) add two points the primer leaves out.[3]

  • Fail-over is not always this simple. The deck shows more involved set-ups than one active and one passive server.
  • Fail-back is the reverse step: returning service to the original server once it has recovered.

The deck also lists network fail-over as its own topic, as a heading without further detail.[3]

Disadvantages of fail-over

Disadvantages

  • Adds more hardware and additional complexity.[1]
  • Data can be lost if the active system fails before newly written data is replicated to the passive.[1]
Connection to Unit 5

The second point is the cost of asynchronous replication from Unit 5: the active server acknowledges a write before the copy reaches the standby. Barrett called this the “window of lost data” in a primary with hot failover.[5] That is why fail-over needs replication behind it.

6.2Replication

Replication keeps copies of the same data on more than one node. The availability section only names its two main forms, master-slave and master-master, and points to the Database section for details.[1] That is where this part of the unit draws from.[2]

Push vs pull

Bonér first separates replication by who moves the data:[3]

  • Active replication uses a push model: the node holding a change sends it out.
  • Passive replication uses a pull model: when a node doesn’t have some data, it reads it from a peer and stores it locally. Bonér notes this works well with timeout-based caches.

Master-slave replication

The master serves reads and writes and replicates the writes to one or more slaves, which serve only reads. Slaves can also replicate to more slaves in a tree-like fashion (Bonér’s “tree replication”).[2][3]

If the master goes offline, the system keeps working in read-only mode until a slave is promoted to master or a new master is provisioned.[2] Slaves that serve only reads are often called read replicas.[2]

Disadvantage

  • Additional logic is needed to promote a slave to a master.[2]
  • Plus the shared replication disadvantages below.

Master-master replication

Both masters serve reads and writes and coordinate with each other on writes. If either goes down, the system keeps working with both reads and writes.[2]

Disadvantages

  • You need a load balancer, or changes to application logic, to decide where to write.[2]
  • Most such systems are either loosely consistent (violating ACID) or have higher write latency because of synchronization.[2]
  • Conflict resolution matters more as write nodes are added and latency grows.[2]
  • Plus the shared replication disadvantages below.

The Wikipedia article the primer links explains these trade-offs. In multi-master replication, any member of the group can update the data, and the system must propagate changes and resolve conflicts between concurrent updates, often through a consensus algorithm (Unit 5).[4]

  • Why use it: availability (if one master fails, others keep accepting updates), masters at several sites, and faster responses.[4]
  • Lazy vs eager: most systems replicate lazily (asynchronously), which is why they are only loosely consistent. Systems that replicate eagerly (synchronously) are complex and add communication latency.[4] These are the two options in the primer’s second disadvantage.
  • Real examples include Microsoft Active Directory and OpenLDAP among directory servers, and CouchDB, Galera Cluster, MySQL Group Replication and PostgreSQL’s BDR among databases.[4]

Buddy replication

Bonér’s deck lists a fourth form, buddy replication, shown only as diagrams.[3] The JBoss Cache guide, which documents the technique, describes it: instead of copying its data to every node in the cluster, each node copies it to a few chosen buddies, by default just one, picked on a different physical host where possible.[6]

  • Why: replicating to all nodes costs more memory and network traffic with every node added. Buddies keep that cost about constant as the cluster grows.[6]
  • When: it suits data such as HTTP session state, and only pays off with session affinity (sticky sessions, Unit 1), where a client’s requests keep reaching the same node.[6]
  • On failure: a node that receives a request for data it lacks asks the cluster for it, including buddies’ backup copies, and takes ownership. JBoss calls this data gravitation. Data moves only when requested, avoiding a flood of transfers when a node dies.[6]

Disadvantages of replication

These apply to both master-slave and master-master:[2]

Disadvantages

  • Data loss if the master fails before newly written data reaches other nodes.
  • Writes are replayed on the read replicas; with many writes, replicas get bogged down replaying them and can serve fewer reads.
  • More read slaves means more to replicate, so greater replication lag.
  • On some systems the master can write with several threads in parallel, while replicas apply writes sequentially on one thread.
  • Adds more hardware and additional complexity.
In an interview

Pair each pattern with what it costs. Fail-over and replication both add hardware and complexity, and asynchronous copies can lose the last writes.[1][2] Master-slave is simpler but goes read-only on failure; master-master keeps writes going but forces a choice between loose consistency and slower writes.

6.3Availability in numbers

Availability is usually given as uptime (or downtime): the percentage of time the service is available.[1]

Formula

Availability = uptime ÷ total time, so allowed downtime = (1 − availability) × period.

Counting nines

Availability is generally measured in number of 9s: a service with 99.99% availability has “four 9s”.[1] Each extra nine cuts the allowed downtime by a factor of ten.

Availability in sequence vs in parallel

When a service is made of several components that can fail, its overall availability depends on how they are arranged.[1]

  • In sequence (the request needs every component), overall availability decreases:
    Availability (Total) = Availability (Foo) × Availability (Bar)
    Two components at 99.9% give 99.8% in sequence.[1]
  • In parallel (any one component is enough), overall availability increases:
    Availability (Total) = 1 − (1 − Availability (Foo)) × (1 − Availability (Bar))
    Two components at 99.9% give 99.9999% in parallel.[1]

The parallel formula reads: the service is down only if both are down at once, and (1 − A) is each one’s chance of being down. This is why fail-over and replication raise availability: they put components in parallel.

Behind the parallel formula

Multiplying the two “down” chances assumes the components fail independently. Two servers on the same power supply or network switch can go down together, so real gains are smaller. Barrett’s “bunker” example in Unit 5 shows this: one power failure took down every server in a datacenter at once.[5]
