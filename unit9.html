SYSTEM DESIGN PRIMER · UNIT 9

Load balancer

A load balancer distributes incoming client requests to computing resources such as application servers and databases, and returns each resource’s response to the right client.[1] This unit covers what a load balancer protects against, how it picks a server, how to stop the load balancer itself from failing (active-passive and active-active), the difference between layer 4 and layer 7 balancing, and how load balancers make horizontal scaling possible.

9.0What a load balancer does

Clients send requests to one address: the load balancer. It forwards each request to one of several servers, waits for the answer and passes it back to the client (Figure 9.1).[1] Ricky Ho calls this the load balancer pattern: a dispatcher picks a worker by some policy, and works best when the application is stateless, so any worker can handle any request.[12]

The primer says load balancers are effective at:[1]

  • preventing requests from going to unhealthy servers;
  • preventing overloading resources;
  • helping to eliminate a single point of failure (SPOF): one component whose failure stops the whole service.

Because clients only ever talk to the load balancer, the servers behind it stay hidden. Clients cannot reach them directly, which can also help security.[5]

Load balancers come as hardware, which is expensive, or as software such as HAProxy.[1] The first example in the HAProxy architecture guide is typical: a web server saturated by a CPU-heavy application is replaced by HAProxy in front of four cheap servers.[3] Section 9.6 looks inside HAProxy and NGINX.

Health checks

To keep requests away from unhealthy servers, a load balancer health-checks each server: it polls them regularly, takes failed ones out of the pool and puts them back when they recover.[5] Listing 9.1 shows the HAProxy guide’s first example. Each check turns on health checks for that server, and option httpchk makes the check an HTTP request rather than just a TCP connection.[3]

# HAProxy 1.2-era syntax, from the architecture guide’s example 1
listen webfarm 192.168.1.1:80
   mode http
   balance roundrobin                      # routing method (Table 9.1)
   cookie SERVERID insert indirect         # session persistence (below)
   option httpchk HEAD /index.html HTTP/1.0  # health check request
   server webA 192.168.1.11:80 cookie A check
   server webB 192.168.1.12:80 cookie B check
   server webC 192.168.1.13:80 cookie C check
   server webD 192.168.1.14:80 cookie D check

Listing 9.1 HAProxy in front of four web servers.[3] Modern HAProxy splits listen into frontend and backend sections, but the ideas are the same.

SSL termination

With SSL termination, the load balancer decrypts incoming requests and encrypts the servers’ responses, so the backend servers do not have to do this potentially expensive work. It also removes the need to install X.509 certificates on every server.[1] An X.509 certificate binds a public key to an identity such as a hostname. It is signed by a certificate authority, and it is what a browser checks during the TLS handshake of an HTTPS connection.[10]

AWS describes the same thing: to accept HTTPS, you deploy an X.509 certificate on the load balancer, which decrypts requests before sending them on. To avoid terminating TLS there, you pass the traffic through as plain TCP and install the certificates on the servers instead.[8] Wikipedia notes the trade-off: termination saves server CPU, but it can turn the load balancer into a bottleneck, and sometimes adding web servers is cheaper.[5]

Session persistence

If the web apps do not keep track of sessions themselves, the load balancer can issue a cookie and route all of one client’s requests to the same instance. This is session persistence, also called sticky sessions.[1] HAProxy’s cookie insertion (Listing 9.1) works like this:[3]

  1. A request with no cookie is load-balanced as usual.
  2. The response gets a cookie naming the server, e.g. SERVERID=B.
  3. Later requests carrying that cookie go to the same server. HAProxy removes the cookie before forwarding (the indirect option), so the server never sees it.
  4. If that server dies, the client is sent to another server and given a new cookie.

If the application already sets its own session cookie, HAProxy can instead prefix it with the server name (JSESSIONID=A~123) and strip the prefix before forwarding.[3] Figure 9.2 combines SSL termination and cookie insertion.

The catch

Sticky sessions give no automatic fail-over: if the server holding a session fails, that session is lost.[5] Section 9.5 shows the usual fix, which is to keep sessions off the servers altogether.

The primer links an article on round robin versus weighted round robin. Its example has three servers benchmarked at about 100, 300 and 25 requests per second. Plain round robin gives the weakest server as many requests as the strongest, so it would normally be left out of the pool. Try it: routing

Figure 9.3 sends 340 requests per second to the servers in Table 9.2 for two seconds, which is 80% of their combined capacity. Pick a method, take a server down, switch health checks off, then press Play.

Things to notice in Figure 9.3:

  • Round robin: S3 gets a third of the traffic but can handle only a fraction of it, so its queue keeps growing and waits reach seconds. This is the overloading a load balancer should prevent.
  • Weighted round robin: every server runs at the same 80% of its capacity and queues stay short.
  • Least loaded: no weights are configured, yet S2 drains its queue fastest and so receives the most requests.
  • Take a server down with health checks on: the balancer stops using it and the others absorb its share, overloaded if the rest lack capacity. Switch health checks off and its share of requests simply fails.

9.1Active-passive

A single load balancer is itself a single point of failure. To protect against failures, it is common to run multiple load balancers, in either active-passive or active-active mode.[1] These are the two fail-over modes from Unit 6.[11]

In active-passive fail-over, the active server and a passive server on standby send each other heartbeats. If the heartbeat is interrupted, the passive server takes over the active server’s IP address and resumes service. Only the active server handles traffic.[11]

How long the outage lasts depends on the standby:[11]

  • Hot standby: the passive server is already running and can take over at once.
  • Cold standby: it must start up first, so downtime is longer.

Active-passive fail-over is also called master-slave fail-over.[11]

Example: a VRRP pair

The HAProxy guide removes its single load balancer this way. Two load balancers, LB1 (192.168.1.3) and LB2 (192.168.1.4), share a virtual IP (VIP), 192.168.1.1, which is the address clients use. The keepalived tool runs the VRRP protocol between them:[3]

  • LB1 has priority 101 and is the master, so it holds the VIP. LB2 has priority 100 and is the backup.
  • Every 2 seconds a script checks that HAProxy is still running; a passing check adds 2 to the node’s priority. If LB1’s check fails, its priority falls below LB2’s and the VIP moves to LB2.

Clients keep using the same address throughout, which is why the passive server takes over the active one’s IP.

9.2Active-active

In active-active fail-over, both servers manage traffic and spread the load between them. Something must tell clients about both:[11]

  • if the servers are public-facing, DNS needs to know the public IPs of both;
  • if they are internal-facing, the application logic needs to know about both.

Active-active fail-over is also called master-master fail-over.[11] Load balancers deployed as a high-availability pair can also replicate their session persistence data between them.[5]

When one public-facing node fails, DNS has to stop handing out its address. Wikipedia notes that a short TTL helps divert traffic quickly.[5] Until then, clients holding a cached answer keep trying the dead address (Unit 7).

Try it: fail-over

Disadvantages: fail-over

  • Fail-over adds more hardware and additional complexity.[11]
  • Data written to the active system can be lost if it fails before replicating to the passive one.[11]

9.3Layer 4 load balancing

“Layer” refers to the OSI network model. Layer 4 is the transport layer (TCP and UDP, covered in Unit 15), and layer 7 is the application layer (HTTP).[6][7]

Layer 4 load balancers look at transport-layer information to decide where to send a request: generally the source and destination IP addresses and ports in the packet header, but not the contents of the packet. They forward network packets to and from the upstream server, performing Network Address Translation (NAT).[1]

NGINX’s glossary entry (the primer’s link) explains the NAT step:[6]

  1. The load balancer’s own IP address is the one published to clients, for example through DNS.
  2. It decides using address information from the first few packets of the TCP stream.
  3. It rewrites each packet’s destination address from its own to the chosen server’s, and on replies rewrites the source back to its own. Ports are sometimes rewritten too.

Layer 4 balancers are often dedicated hardware with proprietary software, sometimes with special chips for NAT. Strictly, the name should be “layer 3/4”, since IP addresses belong to layer 3 and ports to layer 4.[6]

9.4Layer 7 load balancing

Layer 7 load balancers look at the application layer to decide where to send requests. This can involve the contents of the header, the message and cookies. The balancer terminates the network traffic, reads the message, makes a load-balancing decision, then opens a connection to the selected server.[1] It may instead reuse an existing connection kept open with HTTP keepalives. A device doing this is often called a reverse proxy (Unit 10).[7]

Because it knows what is being requested, a layer 7 balancer can send different traffic to different servers. The primer’s example: video traffic goes to servers that host videos, while more sensitive billing traffic goes to security-hardened servers.[1] Content then does not need to be copied to every server.[6] Reading the whole message also lets it compress or encrypt content and buffer slow clients so the servers are freed sooner.[7]

The cost: layer 4 balancing needs less time and computing resources, at the price of flexibility. The difference can be minimal on modern commodity hardware.[1] The NGINX glossary goes further and calls it negligible in most situations.[6]

9.5Horizontal scaling

Load balancers also help with horizontal scaling, improving performance and availability. Scaling out with commodity machines is more cost efficient and gives higher availability than scaling up a single server on more expensive hardware, which is vertical scaling. It is also easier to hire people who work on commodity hardware than on specialised enterprise systems.[1]

Table 9.5 Vertical and horizontal scaling[1]
Vertical (scale up)Horizontal (scale out)
HowOne server on more expensive hardwareMore commodity machines behind a load balancer
Cost efficiencyLowerHigher
AvailabilityLowerHigher
HiringSpecialised enterprise systemsEasier: commodity hardware
ComplexityLowerHigher: cloning servers, stateless design (below)

Clones

The primer links part 1 of Scalability for Dummies (also covered in Unit 1). Its rules for scaling out:[4]

  • A user may land on a different server with every request, so every server must run the same code and store no user-related data, such as sessions or profile pictures, locally. The author calls this the first golden rule for scalability.
  • Keep sessions in a centralized data store all servers can reach: an external database or an external persistent cache. The author prefers Redis for performance.
  • Deploy code changes to every server, so none keeps serving old code. The article names Capistrano as a tool for this.
  • Once servers hold no state, make an image of one (on AWS, an AMI) and launch new servers from this “super-clone”.

Where sessions go

The primer’s rule is that servers should be stateless, with sessions in a centralized data store such as a database (SQL, NoSQL) or a persistent cache (Redis, Memcached).[1] Table 9.6 compares this with the alternatives Wikipedia describes.

Table 9.6 Where to keep session state
OptionUpsideDownside
On one server, with sticky sessionsServers can keep sessions in memoryNo automatic fail-over: the session dies with the server. Client IPs used for stickiness can change (DHCP, NAT, proxies)[5]
Central databaseAny server can serve any clientExtra load on the database; replicating it helps[5]
Central persistent cacheAny server can serve any client; fast (Redis is the article’s pick)[4]One more shared component the servers depend on
On the client (e.g. an encrypted cookie)Any server can serve any request; generally preferred[5]Unsuitable for large session data[5]

Disadvantages

Disadvantages: horizontal scaling

  • Scaling horizontally introduces complexity and involves cloning servers.[1]
    • Servers should be stateless: no user-related data such as sessions or profile pictures.
    • Sessions go in a centralized data store: a database or a persistent cache.
  • Downstream servers such as caches and databases must handle more simultaneous connections as upstream servers scale out.[1]

9.6Inside software load balancers

The primer’s further reading includes architecture notes for the two best-known software load balancers. They show how one machine can sit in front of many servers without becoming the bottleneck.

NGINX: event-driven workers

NGINX runs a small set of processes:[2]

  • The master process does the privileged work, such as reading the configuration and binding to ports, then starts the others.
  • Worker processes do all the request work: network connections, disk, and talking to upstream servers. The recommended setup is one worker per CPU core.
  • A cache loader loads the disk cache into memory at startup and exits; a cache manager prunes the cache to its size limits.

Many servers dedicate a process or thread to each connection, which then blocks while it waits. Each connection itself costs only a file descriptor and a little memory, but the thread or process tied to it is a heavyweight object. An NGINX worker is single-threaded and non-blocking: it waits for events on its sockets and handles whichever connection has work ready. With tuning, one worker can handle hundreds of thousands of concurrent connections.[2] The article compares it with a chess grandmaster playing hundreds of opponents at once, moving at whichever board is ready.[2]

The same design lets NGINX change without downtime. On nginx -s reload, the master loads the new configuration and starts new workers; the old workers stop taking new connections, finish their current requests and exit. A binary upgrade works the same way, with old and new masters sharing the listening sockets.[2] For a load balancer, which every request passes through, this matters.

HAProxy: queue, don’t overload

The HAProxy guide shows how a load balancer prevents overloading. Each server gets a limit on concurrent connections (maxconn), and HAProxy queues requests above the limit instead of passing them on.[3] The guide lists the benefits:

  • clients are served whatever the volume; only latency goes up;
  • servers can run at full speed without stalling, and response times drop when servers are kept below their congestion point;
  • there is no domino effect when a server fails or starts up;
  • memory-limited servers perform better.
Worked example

Three servers with maxconn 4 each, each handling 4 requests in about 10 ms: with 3000 connections, the guide calculates a maximum delay of 3000 ÷ 3 ÷ 4 × 10 ms = 2.5 s.[3] Clients wait longer, but no server is pushed past what it can handle.

Two related settings: option abortonclose drops queued requests whose client has already gone, and minconn with maxconn lets a server run with lower concurrency under light load, rising towards the maximum as the queue grows.[3]

9.7Disadvantages

Disadvantages: load balancer

  • It can become a performance bottleneck if it lacks resources or is not configured properly.[1]
  • Adding a load balancer to help remove a single point of failure increases complexity.[1]
  • A single load balancer is a single point of failure; configuring multiple load balancers adds still more complexity.[1]

Each point connects to earlier sections: SSL termination is one way to overload the balancer (9.0), the pair of balancers in 9.1 and 9.2 fixes the single point of failure at the cost of complexity, and NGINX’s and HAProxy’s designs (9.6) are aimed at the bottleneck. Wikipedia adds that fail-over through load balancing needs spare capacity, at least one server more than the load requires (N+1).[5]

Beyond the primer

Wikipedia lists features many load balancers offer besides choosing a server:[5]

DDoS and SYN-flood protectionSYN cookies and delayed binding: servers see a client only after its TCP handshake completes.
HTTP compressionShrinks responses with gzip, at the cost of balancer CPU.
TCP bufferingBuffers responses and feeds them to slow clients, freeing servers sooner.
TCP offloadCombines many clients’ HTTP requests into fewer persistent connections to the servers.
Direct server returnReplies take a different path back to the client, bypassing the balancer.

In an interview

Put a load balancer in front of stateless application servers and say where sessions live: a shared cache or database. Then remove the balancer as a single point of failure with an active-passive pair sharing a virtual IP, or active-active behind DNS. Choose layer 7 when you need to route by URL, header or cookie, and mention health checks and SSL termination. Reverse proxies, which overlap heavily with layer 7 balancers, come next in Unit 10.
