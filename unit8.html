SYSTEM DESIGN PRIMER · UNIT 8

Content delivery network

A content delivery network (CDN) is a globally distributed network of proxy servers that serves content from locations closer to the user.[1] This unit covers why CDNs exist, the two ways content gets onto them (push and pull), how users are sent to a nearby server, how cached content is kept fresh, and the costs of using one.

8.0What a CDN is

A CDN stores copies of your content on servers spread around the world. Generally it serves static files such as HTML, CSS, JavaScript, photos and videos, although some CDNs, such as Amazon’s CloudFront, also support dynamic content. The site’s DNS resolution tells each client which CDN server to contact (Unit 7).[1]

The primer names two ways a CDN improves performance:[1]

  • Users receive content from data centers close to them, so requests travel a shorter distance.
  • Your own servers do not have to serve the requests the CDN fulfills, which lowers their load.

Why CDNs exist

The CDN company Akamai grew out of an MIT research effort on the flash crowd problem: a site becomes popular and the request load overwhelms some part of its infrastructure, such as the front-end web server, network equipment or bandwidth. The overload can crash the site or slow it down.[2] Serving everything from one location limits a site’s scalability, reliability and performance.[2] Table 8.1 lists the approaches sites used before CDNs.

Table 8.1 Approaches that existed before CDNs, and their limits
ApproachWhat it isLimit
Local clusteringMany servers in one data centerHard to scale to thousands of servers; if the data center or its ISP fails, the whole cluster is unreachable
MirroringClusters deployed in a few locationsThe site must be kept in sync across mirrors, which can be difficult
MultihomingConnecting through several ISPsInternet routing (BGP) is slow to switch to new routes when a connection fails
Proxy cachesCaches run by ISPs and organisations near their usersLow hit rates, 25–40%, partly because sites use more dynamic content

All rows from Dilley et al.[2]

The first three all need excess capacity. Each cluster must handle the peak load, which can be an order of magnitude above the average, and each ISP link or mirror must be able to carry all the traffic. That can more than double a site’s infrastructure and running costs.[2] Congestion can also occur anywhere along the way: the first mile out of the origin, the backbones, the peering points between network providers, and the last mile to the user.[2] A CDN’s answer is to serve content from the network’s edge, close to the user, past most of those points.

Parts of a CDN

Origin serverYour own web server, which holds the source content.[4]
Edge serverA CDN server that answers client requests; “edge” because it is the CDN’s point closest to the user.[4]
Point of presence (PoP)A location where the CDN runs edge servers. Some CDNs run thousands of nodes; others use a few large PoPs.[4]
FootprintThe geographic area the edge servers can serve well.[4]
Entry pointA CDN server that receives content from the origin, such as a live video stream, and passes it on to edge servers.[2][4]
Origin shieldA CDN service that protects the origin when traffic is heavy.[4]

8.1Push CDNs

A push CDN receives new content whenever changes occur on your server. You take full responsibility for providing content: you upload it directly to the CDN and rewrite URLs to point to the CDN. You can configure when content expires and when it is updated.[1]

  • Content is uploaded only when it is new or changed, which minimises traffic but maximises storage: every file sits on the CDN whether or not anyone requests it.[1]
  • Because content is placed on the CDN in advance, even the first request is served from the edge, with no trip to the origin.[3]
  • The cost is work for you: someone has to update the CDN for changes to appear on the site, and the setup and maintenance effort is higher.[3]

Good fit: sites with little traffic, or content that isn’t updated often. Content is placed on the CDN once, instead of being pulled again at regular intervals.[1] GeeksforGeeks adds large static files such as software downloads and media.[3]

Connection to Unit 1

Unit 1’s “do the work in advance” pattern pre-rendered dynamic pages to static HTML, often with an hourly cron job, and uploaded them to S3, CloudFront or another CDN. Uploading files yourself whenever they change is the push model.

8.2Pull CDNs

A pull CDN grabs new content from your server when the first user requests it. You leave the content on your server and rewrite URLs to point to the CDN.[1] On each request:[3]

  1. The request goes to the nearest edge server.
  2. If the edge server doesn’t have the content (a cache miss), it requests it from the origin.
  3. The edge server stores the content in its cache and returns it to the user.
  4. Later requests are served from that cache (a cache hit), without contacting the origin.

The first request is therefore slower, until the content is cached on the CDN.[1] Setup is simpler, because the CDN manages caching itself.[3]

Time to live

A time-to-live (TTL) determines how long content stays cached.[1] In general, a TTL is a mechanism that limits the lifespan of data in a computer or network. It can be given as a duration or as the date and time when the data expires.[5] This is the same idea as DNS caching in Unit 7. For web content, HTTP sets it with the Cache-Control: max-age header or the Expires header (8.5).[5]

  • Pull CDNs minimise storage on the CDN. Only recently requested content stays there, and anything nobody asks for is never copied.[1]
  • They can create redundant traffic: when a file expires, the next request pulls it again, even if it hasn’t changed.[1]

Good fit: sites with heavy traffic. Traffic is spread out more evenly, and only recently requested content remains on the CDN.[1] GeeksforGeeks also calls pull better for dynamic content, since the CDN handles caching and origin fetches automatically.[3]

8.3Push vs pull

Table 8.2 Push and pull CDNs side by side
Push CDNPull CDN
Who moves contentYou upload it to the CDNThe CDN fetches it from your server on first request
When it movesOnly when new or changedOn a cache miss, including after each TTL expiry
Origin → CDN trafficMinimisedCan be redundant (re-pulling unchanged files)
CDN storageMaximised: everything is storedMinimised: only recently requested content
First requestFast, already at the edgeSlower, goes to the origin
EffortMore setup and maintenance; you manage uploadsSimple; the CDN manages caching
Best forLow traffic, rarely updated content, large static filesHeavy traffic; dynamic content

Rows from the primer,[1] plus “first request”, “effort” and parts of “best for” from GeeksforGeeks.[3] In both models you rewrite URLs to point to the CDN.[1]

Try it

Figure 8.3 follows one file through a day. It changes twice, at 06:00 and 15:00. Pick a model, a traffic level and, for pull, a TTL. Then compare the result with the trade-offs in Table 8.2.

Things to notice in Figure 8.3:

  • Pull, heavy traffic, 1 h TTL: three in four requests hit, but the file is pulled about once an hour even though it changed only twice. This is the primer’s redundant traffic.
  • Pull, 12 h TTL: fewer pulls, but after 06:00 users get the old version until the TTL runs out. This is stale content, a disadvantage in 8.6.
  • Pull, low traffic, 1 h or 4 h TTL: the cached copy expires before the next visitor, so every request misses. Push serves all three from the edge with three uploads, which is why push suits small sites.
  • Push: no stale or slow responses in this model, but the file occupies CDN storage all day.

Choosing

GeeksforGeeks concludes that the choice depends on the kind of content and on how much management effort you can take on. Pull suits dynamic content and teams that want little configuration. Push suits managed delivery of static content that can be placed in advance.[3]

Real CDNs often do both

Akamai’s 2002 paper describes both models in one network. Web objects are fetched from the origin by the edge server when needed, which is pull. On-demand video clips are uploaded by the content provider to Akamai’s storage and replicated to several data centers, which is push. Edge servers then fetch each clip from storage and cache it when a user requests it, which is pull again.[2]

8.4Routing users to the edge

The primer says DNS resolution tells clients which server to contact.[1] Akamai calls the direction of requests to servers mapping. Its mapping system is a dynamic, fault-tolerant DNS system that resolves a host name based on the service requested, the user’s location and network status. It also uses DNS for load balancing.[2]

Nearest, available, likely

The goal is to send each request to the nearest available server that is likely to have the content:[2]

  • Nearest is measured by the network, not the map: a server with a lower round-trip time or less packet loss to the user counts as nearer.
  • Available depends on load and bandwidth: a server that is overloaded, or a data center near its bandwidth limit, takes no more clients.
  • Likely means each customer’s content is placed on only a few servers in each data center. If every server stored every file, as with round-robin DNS, the most popular files would fill every server’s disk and memory.
Table 8.3 What Akamai’s name servers check before returning an edge server
CriterionThe chosen server must…
Service requestedBe able to handle the request; for example, a media stream is not sent to a server that handles only HTTP
Server healthBe up and running without errors
Server loadBe under a load threshold (CPU, disk and network use)
Network conditionBe reachable with little packet loss, in a data center with spare bandwidth
Client locationBe close to the client, for example by round-trip time
Content requestedBe likely to have the content, according to consistent hashing

From Dilley et al.[2] To estimate network distance, the system also combines routing information from BGP with live measurements such as traceroute data.

CDNs route requests in other ways too. Wikipedia lists global server load balancing, DNS-based routing, HTML rewriting and anycast, where one address is served from many locations.[4] DNS-based routing has one weakness. A CDN traditionally locates a user by the IP address of their recursive resolver, which can be far from the user. The EDNS client-subnet extension lets the CDN see the user’s own subnet instead.[4]

DNS in two levels

Edge servers are located by a DNS name such as a7.g.akamai.net, resolved right to left like any name in Unit 7:[2]

  1. A root server refers the resolver to the .net servers, which refer it to Akamai’s top-level name servers.
  2. A top-level server delegates g.akamai.net to low-level name servers located with the available edge servers closest to the user. This answer has a TTL of about one hour.
  3. A low-level server returns the IP addresses of edge servers that can handle the request. This answer has a short TTL, from several seconds to one minute, so resolvers ask again often and Akamai can send users elsewhere as conditions change.

Each content server frequently reports its load. The reports are published to the local DNS server, which decides which IP addresses (two or more) to return. If a server passes one load threshold, part of its content is assigned to more servers as well. Past a second threshold, its address is no longer given out.[2]

Connection to Unit 7

This is the TTL trade-off from Unit 7 in practice. The low-level answer that picks a server has a TTL of seconds, so the choice can change quickly. The delegation changes less often, so it is cached for about an hour.

Handling failure

Akamai’s DNS detects failures quickly and gives out new IP addresses. Some clients still hold a cached answer that points at the failed server, and two mechanisms protect them:[2]

  • DNS can return several IP addresses, so a client can try another one.
  • A live server at the same site can take over the failed server’s IP address.

Monitoring and control are replicated as well, to avoid any single point of failure. Agents that act like users download objects and measure failure rates and download times, so problem servers and data centers are found and suspended automatically.[2]

8.5Freshness and dynamic content

Controlling lifetimes

Content providers need a way to keep cached copies consistent with the origin. Table 8.4 lists the ways described by Akamai.

Table 8.4 Ways to keep cached content consistent
TechniqueHow it worksTrade-off
TTLEach object has a lifetime, from 0 (check with the origin on every request) to infinite (never check)Short: more origin traffic. Long: stale risk
Versioned URLsA version number or unique query string in the URL; a new version is a new URLCan be cached with an infinite TTL; pages must link the new URL
PurgeRemove an object from all edge servers on demand, or on a schedule when content changesNeeds a purge step when you publish

Techniques from Dilley et al.;[2] the trade-off column is a summary building on the primer’s TTL discussion.[1] Purges matter because most web objects change rarely, so heuristic caches keep copies long after they change.[2]

In HTTP, the origin states a lifetime with headers.[5] MDN defines a few that matter for CDNs:[6]

# fresh for 1 hour everywhere; 1 day in shared caches such as a CDN
Cache-Control: max-age=3600, s-maxage=86400

# versioned file: will never change while fresh
Cache-Control: max-age=31536000, immutable

# may be stored, but must be checked with the origin before each reuse
Cache-Control: no-cache
  • max-age=N: fresh for N seconds after the response is generated.[6]
  • s-maxage: freshness for shared caches only (a proxy or CDN). It overrides max-age there and is ignored by the browser’s private cache.[6]
  • A shared cache reuses one response for many users, so personalised content should not be cached there; mark it private.[6]

Header values above are illustrative examples, not recommendations.

Dynamic content

Proxy caches typically can’t cache dynamic content. A mostly static page that contains an advertisement chosen for each user can’t be cached as a whole.[2] Akamai used Edge Side Includes (ESI). The provider splits the page into fragments, each with its own cacheability, and the edge server assembles them for each request. Only uncacheable or expired fragments are fetched from the origin. Across the portals and financial sites Akamai studied, ESI cut bandwidth for dynamic content by 95–99%.[2]

Even uncacheable responses can be faster through a CDN. The edge server splits the user’s TCP connection into two, user ↔ edge and edge ↔ origin. The edge server can react to packet loss more quickly than the origin server. It can also accept the origin’s response quickly and send it on at the user’s pace, which frees the origin for other requests.[2]

8.6Disadvantages

Disadvantages: CDN

  • CDN costs could be significant depending on traffic. Weigh them against the extra costs you would have without a CDN.[1]
  • Content might be stale if it is updated before the TTL expires it.[1]
  • CDNs require changing URLs for static content to point to the CDN.[1]

The cost point cuts both ways. The alternatives in Table 8.1 need excess capacity, which Akamai’s authors say could more than double a site’s infrastructure and running costs (8.0).[2] Stale content is managed with the techniques in Table 8.4.

Beyond the primer

Wikipedia raises a few more concerns:[4]

  • Privacy and tracking. A CDN sees every visitor’s requests, and some providers earn money from tracking data. In 2021 a German court barred a university website from using a CDN, because it sent users’ IP addresses to the provider in breach of the GDPR.
  • Tampered scripts. Shared CDNs serving JavaScript have been targeted to inject malicious code. Subresource Integrity lets the page include a hash of the expected file, so the browser rejects a file that has been changed.
  • Depending on one provider. Some sites use a multi-CDN setup to avoid relying on one CDN, especially during large live events.
In an interview

Put static assets behind a CDN early in a design. Say whether it is push or pull and why, and how you will avoid stale content: a TTL, versioned URLs or purges. CDN caching comes back in Unit 13, alongside the other cache layers.
