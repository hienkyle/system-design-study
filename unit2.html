SYSTEM DESIGN PRIMER · UNIT 2

Performance vs scalability

The first of the primer’s three high-level trade-offs. A fast system and a scalable system are not the same thing: one is about how quickly a single request is served, the other about whether adding resources lets you serve more.[1] This unit covers what “scalable” means (performance proportional to resources added), how to tell a performance problem from a scalability problem, why scaling is hard (redundancy, heterogeneity), designing for scale, and the three high-level trade-offs.

Primer section · Performance vs scalabilityWerner Vogels · “A Word on Scalability” (2006)Jonas Bonér · Scalability patterns deck (2010)

2.1What “scalable” means

Amazon CTO Werner Vogels opens his article by pointing out that “scalability” is often used loosely: saying “that doesn’t scale” can end a design argument, and usually signals that a system’s architecture limits how the service can grow. Used positively, it names a property you want a platform to have. Either way, the word needs a precise meaning.[2]

Proportional to resources added

The primer adopts Vogels’ definition: a service is scalable if it results in increased performance in a manner proportional to resources added.[1][2] Double the servers and, ideally, you serve about double the work. A system whose gains flatten out as you add machines is not scalable, however fast each machine is.

More work vs larger work

“Increased performance” usually means serving more units of work, such as more requests per second. It can also mean handling larger units of work, for example when the dataset each request touches keeps growing.[1][2] A system can scale along one of these axes and fail along the other.

2.2Performance problem or scalability problem?

The primer gives a quick test, taken from Jonas Bonér’s talk Scalability, Availability & Stability Patterns, where it appears as two questions: “How do I know if I have a performance problem?” and “How do I know if I have a scalability problem?”[1][3]

  • If you have a performance problem, your system is slow for a single user.
  • If you have a scalability problem, your system is fast for a single user but slow under heavy load.
Table 2.1 Telling the two problems apart
Performance problemScalability problem
With one userSlowFast
Under heavy loadSlowSlow
What is wrongThe work for a single request costs too muchCost grows faster than load, or added resources don’t help
How to see itProfile a single request, e.g. with a slow query logBenchmark by simulating high load, e.g. with ab

Rows 1–2 restate the primer’s test.[1] Row 3 follows from Vogels’ definition.[2] Row 4 uses the tools the primer names later, in its SQL tuning section.[4]

2.3Why scalability is hard

Vogels names the reasons a system that works today can stop scaling tomorrow.[2]

Redundancy without slowdown

Resources are not only added for capacity. Distributed systems also add them for reliability, and Vogels calls redundancy the first line of defence against failure. For an always-on service, being scalable therefore also means you can add resources for redundancy without losing performance.[2]

Link to Unit 1

The extra load balancer, the second master and the standby server in Unit 1 are all redundant resources. They are only worth adding if they don’t slow the system down.

It can’t be added later

Scalability cannot be bolted on after the fact. Many algorithms behave well at low request rates on small datasets, then become very expensive as request rates rise, datasets grow or the number of nodes increases. A system has to be designed so that added resources really do raise performance.[2]

Heterogeneity

Scaling out means living with heterogeneity. Over time a fleet mixes hardware generations, larger machines become cost-effective and get added, and some resources end up placed farther apart. Nodes then differ in processing speed and storage. Algorithms that assume all nodes are equal either break down or underuse the newer, more powerful machines.[2]

2.4Designing for scale

Vogels concludes that good scalability is possible, but only if the system is architected and engineered for it from the start. He lists what that takes:[2]

  1. Identify the axes of scale: the directions in which the system is expected to grow (requests, data size, nodes).
  2. Decide where redundancy is needed and how it will be handled.
  3. Plan for heterogeneity in the resources the system will run on.
  4. Make sure architects know which tools fit which conditions and what the common pitfalls are.

Bonér’s deck opens its scalability patterns by asking scale up vs scale out? (bigger machine vs more machines, both covered in Unit 1), then gives four general recommendations before turning to the trade-offs.[3] The deck names them without detail, so the short definitions below come from standard references.

Table 2.2 Bonér’s general recommendations for scalable code
RecommendationWhat the term means
Immutability as the defaultAn immutable object cannot change after it is created, so it can be shared without locks or copies.[6]
Referential transparencyAn expression can be replaced by its value without changing the program’s behaviour, a property of pure functions.[7]
LazinessLazy evaluation delays computing a value until it is actually needed, so unneeded work is skipped.[8]
Think about your dataDifferent data needs different guarantees, so don’t give all of it the same treatment.[3]

2.5One of three trade-offs

In both Bonér’s deck and the primer, performance vs scalability is the first of three trade-offs, followed by latency vs throughput and availability vs consistency.[1][3]

Table 2.3 The three high-level trade-offs
Trade-offThe question it asksUnit
Performance vs scalabilityIs it slow for one user, or only under load?2 (this unit)
Latency vs throughputHow long one action takes vs how many actions per unit of time3
Availability vs consistencyWhen the network splits, keep answering or keep data correct? (CAP theorem)4
Keep in mind

Everything is a trade-off.[1] Fixing a performance problem makes each request cheaper; fixing a scalability problem makes extra resources pay off. A system needs both, and they usually call for different fixes.

Key terms · Unit 2
Definitions
Performance
How much work a system gets done, and how quickly.
Scalable
Adding resources raises performance in proportion.
Unit of work
One piece of work, e.g. a request. Growth = more units or larger units.
Axis of scale
A direction the system will grow: requests, data, nodes.
Diagnosis
Performance problem
Slow even for a single user.
Scalability problem
Fast for one user, slow under heavy load.
Profile
Measure where one request spends its time (e.g. slow query log).
Benchmark
Simulate high load to see how the system behaves (e.g. ab).
Why it’s hard
Redundancy
Extra resources for reliability; must not cost performance.
Heterogeneity
Nodes of mixed speed and size; “all equal” algorithms fail or waste capacity.
Scale up / scale out
Bigger machine / more machines.
Bonér’s recommendations
Immutability
Data that never changes after creation; safe to share.
Referential transparency
An expression can be swapped for its value.
Laziness
Compute a value only when it’s needed.
Trade-off
Performance/scalability, latency/throughput, availability/consistency.
