SYSTEM DESIGN PRIMER · UNIT 11

Application layer

The application layer, also called the platform layer, sits between the web servers and the databases. Separating it from the web layer lets you scale and configure both layers independently.[1] This unit covers why that split helps, how the same idea grows into microservices, and how services find each other through service discovery with systems such as Consul, etcd and ZooKeeper.

11.0The application layer

Most applications start with a web application talking straight to its database. Will Larson’s platform layer adds a tier in between: web applications call the platform, and only the platform talks to the databases.[2] Figure 11.1 shows the result: a load balancer spreads requests across web servers, each web server can call any platform server, and the platform servers reach the databases.

Why split the layers

Larson gives three reasons for the platform layer,[2] and the primer leads with the first.[1]

  • Independent scaling. Adding a new API means adding application servers, not necessarily web servers.[1] The API gets platform capacity without paying for web-tier capacity it doesn’t need. Separate roles can also get role-specific tuning: database servers do heavy I/O and benefit from solid-state drives, while application servers rarely read from disk and may gain more from CPU.[2]
  • Reuse across products. One platform can serve several products, such as a web app, an API and an iPhone app, so each one doesn’t repeat the boilerplate for caches and databases.[2]
  • Organizational scale. A good platform exposes a product-agnostic interface that hides implementation details. Several teams can build on it while another team improves the platform itself. Larson calls this the underappreciated benefit.[2]

Stateless web and API tier

Early web services often mixed backend logic and page rendering in one project, as Django and Rails do. As projects grew, they were usually split: a frontend that renders pages and a backend that serves APIs.[3] Both tiers should be stateless, so any instance can be killed or restarted freely. That makes scaling out (adding machines) easy, which Internet companies prefer to scaling up for cost reasons.[3] See Unit 9 · Where sessions go for where that state lives instead.

Single responsibility principle

The single responsibility principle advocates small, autonomous services that work together. Small teams with small services can plan more aggressively for rapid growth.[1] The interview guide in the primer’s further reading puts it plainly: each service should “do one thing and do it well.”[3]

Looking ahead

Workers in the application layer also help enable asynchronism,[1] the message and task queues of Unit 14.

Try it: scale each layer

Add page traffic or a new API and watch which servers you have to buy. With a single combined tier, every server carries both the page-rendering stack and the API logic, so capacity added for the API drags web-tier capacity along with it.

11.1Microservices

Microservices are a suite of independently deployable, small, modular services. Each service runs a unique process and communicates through a well-defined, lightweight mechanism to serve a business goal.[1] There is no single agreed definition, but services are usually organized around a business capability, are loosely coupled, keep their own data and governance, and are free to use different technologies.[4]

Peter Rodgers argued in 2005 that software components could be “Micro-Web-Services”,[4] and the style became popular from about 2014 alongside DevOps and continuous deployment.[6]

Example: Pinterest

Pinterest could have these microservices: user profile, follower, feed, search and photo upload.[1] The interview guide’s own Pinterest design names a follower service, feed service, search service and spam service, with images kept in a blob store behind a CDN.[3] Figure 11.3 draws the primer’s list, giving each service its own data store as the “database per service” pattern (Table 11.2) recommends.[8]

SOA and microservices

The primer’s further reading starts from service-oriented architecture (SOA): a style that organizes a system as discrete, independently accessible services that talk over a network through standard protocols, independent of any vendor or technology.[6] In The Open Group’s definition, a service logically represents a repeatable business activity with a specified outcome, is self-contained, is a black box to its consumers, and may be composed of other services.[6]

SOA building blocks play three roles (Figure 11.4). A provider creates a service and publishes it to a broker (a registry or repository); a consumer finds it there, binds to the provider and invokes it. UDDI was an early discovery standard for this and is no longer actively supported.[6] The broker is the ancestor of the service registry in 11.2.

Wikipedia describes microservices as a modern interpretation of SOA,[6] and Sumit Maingi calls them an evolution of it: SOA focused on integrating separate applications, while microservice architecture (MSA) builds small modular services that belong to a single application.[8] Table 11.1 sets the two side by side.

Table 11.1 SOA and microservices compared
SOAMicroservices
Main goalIntegrate various applications[8]Small, modular services inside one application[8]
Typical plumbingWeb services with WSDL contracts and SOAP; also REST and messaging such as JMS or RabbitMQ[6]Lightweight mechanisms: RESTful HTTP, messaging, GraphQL[4]
TechnologyStandards for interoperability across vendors[6]Each service may pick its own language and storage[4][8]
Finding servicesBroker / registry (e.g. UDDI)[6]Service discovery (11.2)[1]
PeriodSOAP 1.2 became a W3C recommendation in 2003[6]Popular since about 2014, with DevOps[6]

Benefits and costs

Benefits

  • Scale only the constrained service; a monolith must scale as a whole.[4]
  • Deploy one service without touching others, as long as its API contract is unchanged.[8]
  • Small autonomous teams build and ship in parallel; suits continuous delivery.[4]
  • Per-service language choice: rewrite one bloated service instead of the whole system.[8]

Costs

  • Calls between services cost more latency than in-process calls.[4]
  • Testing and deployment get harder.[4]
  • No easy distributed transactions; two-phase commit is seen as an anti-pattern.[4]
  • Reports need data merged from many stores.[4]
  • A monolith uses server resources more efficiently and is easier to script deploys for.[8]

Building microservices: problems and fixes

Maingi’s article, linked from the primer, lists the problems teams hit and how to resolve them:[8]

  • Nano-services. Services split so finely that managing them outweighs the benefit (separate “GetUser” and “GetUserById” services). Split by functional area instead: billing, payments, booking.
  • Service URLs. Addresses change across environments; fixed by a load balancer or service discovery.
  • Discovering APIs and writing clients. Poor documentation leads to inconsistent contracts; OpenAPI (Swagger 2.0) gives standard specs plus tools for docs, SDKs and tests.
  • Too many deployment jobs. Unavoidable; tools such as Jenkins or Beanstalk help.
  • Cascading failures. One failing service can take others down; use retries and circuit breakers.
  • Shared transport and auth code. A shared library couples every service: a fix in it means retesting and redeploying nearly all of them. Use an API gateway instead: a proxy that knows where every service is registered, translates client protocols into a common one (usually HTTP) and handles authentication and authorization, so services can sit inside a closed network.
  • Too many servers. Elastic infrastructure, containers such as Docker, and serverless options (API Gateway with Lambda) for sporadic workloads.
  • Data isolation. See Table 11.2.

Retries and circuit breakers

Retries should use a fixed maximum number of attempts, cap the total timeout across all attempts, and wait with exponential backoff between them. Maingi’s example: try immediately, wait 10 ms, try again, wait 50 ms, try a third time, then fail. Backing off stops clients from flooding a service that is recovering.[8]

Waiting for timeouts on a failing service ties up connections and threads, which slows the caller and can cascade through the system. A circuit breaker counts errors for a service and, at a threshold, opens: later calls fail immediately for a set period. It then goes half-open and lets a little traffic through; healthy responses close it again, failures reopen it. Hystrix (Java, Netflix OSS) and Akka.NET provide this.[8]

Database isolation

Because services are self-contained, their storage should be too.[8]

Table 11.2 Ways to isolate service data, per Maingi[8]
OptionHow it worksVerdict
Database per serviceEach service owns a database and can pick its own technology (e.g. Elasticsearch for search)Recommended default
Schema per serviceServices share a database server; each owns a schema, so ownership is easy to seeWorkable compromise
Tables per serviceEach service has its own tables, but others can still read themOnly pretends to isolate; hard to maintain

Data that spans services is combined by querying the services, and reporting uses published contracts and event queues.[8]

11.2Service discovery

Hard-coding service addresses breaks down quickly: addresses differ between environments and change for infrastructure reasons.[8] Systems such as Consul, etcd and ZooKeeper help services find each other by keeping track of registered names, addresses and ports.[1] The list they keep is called a service registry.

Register, check, look up, call

  1. Register. Each service instance registers itself with the registry, tagged with environment and application name.[8]
  2. Health check. Health checks verify service integrity, often through an HTTP endpoint.[1]
  3. Look up. A caller asks the registry for a service by name and gets back healthy instances; it can round-robin across them.[8]
  4. Call. The caller talks to an instance directly, or through a load balancer (next section).

Client-side vs server-side discovery

Routing every call through a load balancer such as HAProxy is called server-side discovery; querying a registry from the caller is client-side discovery. The discovery agent usually runs on the same machine as the service, and because the data is simple it can use fast protocols, often DNS.[8]

Table 11.3 Client-side vs server-side discovery, per Maingi[8]
Client-side (registry)Server-side (load balancer)
PathClient asks the registry, then calls an instance directlyClient calls the balancer, which forwards to an instance
ForFewer network hops, better performance; no need for a highly available, high-performance balancerOne place that consolidates addresses; a managed cloud balancer such as AWS ELB is generally cheap
AgainstAnother tool to learn (Eureka, Consul); clients coupled to the registry (a proxy such as Zuul avoids that but gives up the speed); registry client code needed for every languageExtra latency; another point of failure; may need DNS management for multi-region deployments

Health checks

A registry is only useful if it stops handing out dead instances. In Consul, client agents act as a distributed health-monitoring platform, and each service registration can carry a check.[10] Consul’s check reference lists the types and how each one decides a status (Table 11.4).[11]

Table 11.4 Common Consul health check types[11]
TypeWhat it doesResult
HTTPRequests a URL on the service2xx → passing · 429 → warning · anything else → critical
TCPTries to open a connection to host and portConnects → passing
ScriptRuns an external programExit 0 → passing · 1 → warning · other → critical
TTLThe service must report in periodicallyNo update in time → critical
gRPCUses the standard gRPC health checking protocolPer protocol response

Statuses are passing, warning and critical. A check starts as critical unless you set an initial status, which keeps a new service out of the pool until its health is verified.[11] Here is the service definition from the tutorial the primer links to: a database registered with its name, tags and port, plus a TCP check every 5 seconds.[10]

# Consul service definition (HCL), abridged from HashiCorp's tutorial
service {
  name = "hashicups-db"
  id   = "hashicups-db-0"
  tags = ["v1", "v2"]
  port = 5432

  check {
    id       = "check-hashicups-db"
    tcp      = "localhost:5432"
    interval = "5s"
    timeout  = "5s"
  }
}

# Look it up through Consul DNS: <service>.service.<datacenter>.consul
dig @consul-server-0 -p 8600 hashicups-db.service.dc1.consul ANY
# Filter by tag: <tag>.<service>.service.<datacenter>.consul
dig @consul-server-0 -p 8600 v2.hashicups-db.service.dc1.consul ANY

Consul, etcd, ZooKeeper

Both Consul and etcd have a built-in key-value store that is useful for config values and other shared data.[1] ZooKeeper keeps data in a tree of nodes and describes itself as a centralized, highly reliable data registry.[7]

Table 11.5 The three systems the primer names
SystemWhat it isData and lookupsNotes
ConsulA networking tool for service discovery and service mesh[9]Key-value store; lookups through DNS or the HTTP API[9][10]Built-in health checks; links datacenters through WAN federation and cluster peering[9]
etcdA distributed, reliable key-value store for the most critical data of a distributed system[12]Keys arranged like folders; clients can watch keys for changes; read and write with plain HTTP tools such as curl[13]Replicates data with the Raft protocol; used by Kubernetes and CoreDNS[13]
ZooKeeperAn open-source, high-performance coordination service for distributed applications[7]Hierarchical namespace of znodes; clients set watches[7]Writes go through a leader with majority consensus;[7] classed as CP[3]

ZooKeeper up close

Saurav Haloi’s slides, linked twice by the primer, start from why such a tool exists: coordination (group membership, locking, publish/subscribe, leader election, synchronization) is very hard to get right. ZooKeeper offers naming, configuration management, locks and group services through a simple interface so developers don’t write them from scratch.[7]

  • Znodes. Every node in the namespace is a znode with data (bytes) and optional children, addressed by absolute slash-separated paths. A znode keeps a stat structure with version numbers and timestamps; data is read and written whole.[7]
  • Node kinds. Persistent nodes live until deleted. Ephemeral nodes live only while the creating session is active and can’t have children. Sequence nodes get a monotonically increasing counter appended to their name.[7]
  • Watches. Clients can watch a znode for creation, deletion, data change or child change. A change sends a notification. Watches are one-time triggers and always ordered, and the client sees the event before the new data.[7]
  • Guarantees. Sequential consistency, atomic updates, a single system image (same view from any server), reliability (applied updates persist) and timeliness (a client’s view is up to date within a time bound).[7]

Service discovery with ZooKeeper. Twitter used ZooKeeper this way: services register themselves, clients query for service “A” in data center “XYZ”, an up-to-date host list is kept per service, new capacity is seen automatically, and calls can be balanced across all servers.[7] Instances register their name, address and port under a service path; callers can cache the answer until a location stops working.[3] Ephemeral nodes make this self-cleaning, as Figure 11.8 shows.

Try it: ephemeral membership

Watch out

CP under failure. ZooKeeper stays consistent, but while its leader is unavailable it can’t accept new service registrations.[3] (See Unit 4 for CP vs AP.)

Herd effect. Many watches on one znode cause bursts of traffic and limit scalability. Because watches are one-time, a znode can change again before the client re-arms its watch; handle that case. Keep session timeouts long enough to ride out garbage-collection pauses.[7]

Other approaches. Uber’s decentralized Hyperbahn, built on a Ringpop consistent-hash ring, is described in the interview guide as a failure. On Kubernetes, that guide’s author prefers Service objects with kube-proxy and the cluster’s internal DNS.[3]

11.3Disadvantages

Disadvantages: application layer

  • Adding an application layer with loosely coupled services needs a different approach to architecture, operations and process than a monolithic system.[1]
  • Microservices can add complexity to deployments and operations.[1] The complexity moves into operations, and the many interface points make the whole ecosystem more complex.[4]

Fallacies of distributed computing

Microservices are exposed to the fallacies of distributed computing,[4] which Haloi lists just before explaining why coordination is hard. Each is a false assumption about the network:[7]

The network is reliableCalls between services can fail or time out.
Latency is zeroEvery hop adds delay over an in-process call.
Bandwidth is infiniteChatty services can saturate links.
The network is secureTraffic between services needs protecting.
Topology doesn’t changeInstances move, hence service discovery.
There is one administratorMany teams own many services.
Transport cost is zeroSerialization and network both cost.
The network is homogeneousMixed protocols and stacks are the norm.

The eight fallacies are from Haloi’s slide 4;[7] the one-line notes link them back to this unit.
