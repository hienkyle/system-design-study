SYSTEM DESIGN PRIMER · UNIT 13

Cache

A cache keeps the result of earlier work so the next identical request can skip it. This unit follows a request inward through the places a cache can sit (client, CDN, web server, database and application), compares caching query results with caching objects, and walks through the four update strategies: cache-aside, write-through, write-behind and refresh-ahead.[1]

13.0Why cache

Caching improves page load times and can reduce the load on your servers and databases.[1] Ricky Ho calls the underlying idea the result cache pattern: before doing any work, a dispatcher checks whether the same request has been made before. If it has, the dispatcher returns the stored result instead of running the work again; if not, it forwards the request to a worker and stores the answer for next time (Figure 13.1). Ho names Memcached as a widely deployed cache server for this.[2]

A cache also smooths out uneven traffic. Databases work best when reads and writes are spread evenly across their partitions. Popular items skew that distribution and turn one partition into a bottleneck. A cache in front of the database can absorb those uneven loads and spikes in traffic.[1] Figure 13.2 shows the effect.

Hits, misses and hit rate

Wikipedia defines a cache as a component that stores data so future requests for it are served faster. Each entry holds the data plus a tag naming the original it copies; in a browser cache the tag is the URL and the data is the page. Finding the entry is a cache hit. Not finding it is a cache miss, which costs a trip to the slower backing store and usually copies the result into the cache. The share of accesses that hit is the hit rate (or hit ratio).[8]

Caches stay small to be cost-effective, and they still work because programs show locality of reference: temporal (recently used data is used again) and spatial (data near recently used data is used next).[8] Matyashovsky lists what software caches buy you: shorter response times, fewer trips to the persistent store, no repeated cost of building the same objects, and objects shared between threads. He adds that they only help I/O-bound applications.[3] Larson widens the idea to precalculated results and pre-generated indexes, and notes that caching usually matters earlier in a product’s life than load balancing.[4]

Cache vs buffer

A buffer holds data temporarily so it can move in fewer, larger transfers, and it helps even when data is written and read only once. A cache pays off through reuse of data read or written repeatedly, and it needs a way to keep copies consistent, which a buffer does not.[8]

Where caches live

Caches can sit on the client side (the OS or the browser), on the server side, or in a distinct cache layer.[1] Sections 13.1 to 13.5 take them in the order a request meets them. Pick a layer in Figure 13.3 to see how much of the trip a hit there saves.

13.1Client caching

The cache closest to the user lives on the client: in the operating system or the browser.[1] Browsers keep earlier responses so they can cut bandwidth, server load and latency. Name lookups are cached too: a DNS cache maps domain names to IP addresses.[8] (Unit 7 covers how DNS caching and its TTLs work; see Unit 7 · Domain name system.)

HTTP caching headers

Bonér’s deck groups browser, proxy and CDN caches together as HTTP caching.[5] The server decides how long a response may be reused by sending a header with it, and any cache on the path obeys it. In Figure 13.4 the backend answers Alice with Cache-Control: max-age=600, allowing the copy to be reused for 600 seconds. When Bob asks for the same page 30 seconds later, the cache answers alone, adding Age: 30 to say how old its copy is; the backend never sees the request.[5][12]

13.2CDN caching

CDNs are considered a type of cache.[1] Larson describes a CDN as a read-through cache: when it holds the requested content it serves it, and otherwise it fetches the content from your servers, keeps a copy, and serves that. HTTP headers configure how long it keeps each item. A CDN takes static media off the application servers and serves it from locations near users, at a price. Before a CDN is worth it, he suggests serving static media from a separate subdomain with a lightweight server such as Nginx, then pointing that subdomain’s DNS at a CDN later.[4] Bonér lists CDNs (with Akamai as the example) alongside reverse proxies as HTTP caching.[5] Push and pull CDNs, and how their TTLs work, are covered in Unit 8 · Content delivery network.

13.3Web server caching

Reverse proxies and caches such as Varnish can serve static and dynamic content directly, and web servers can cache requests and return responses without contacting the application servers.[1] Varnish describes itself as an open-source HTTP accelerator and reverse caching proxy that sits in front of the origin. Its caching policy is written in VCL (Varnish Configuration Language), which is compiled to native code; a cache hit takes only three system calls.[10] Bonér’s list of reverse-proxy HTTP caches also includes Squid, rack-cache, Pound, Nginx, Apache mod_proxy and Traffic Server.[5]

A related approach is to precompute content: generate pages ahead of time (Bonér names cron jobs, Spring Batch, Gearman and Hadoop among the tools) so the web server only serves files.[5] Unit 1 covers the trade-offs of static HTML (Unit 1 · Caching), and Unit 10 shows NGINX’s proxy cache configuration (Unit 10 · Caching).

Name change

The primer’s link, varnish-cache.org, now redirects to varnish.org. The site describes Varnish Cache as a distribution of the open-source Vinyl Cache project.[10]

13.4Database caching

Your database usually ships with some caching in its default configuration, tuned for a generic workload. Adjusting those settings to your own usage patterns can boost performance further.[1] Wikipedia lists what a database cache typically speeds up: indexes, data dictionaries and frequently used subsets of the data.[8]

Larson’s point is that this speed-up needs no change to application code. His example is a colleague who tuned Cassandra’s row caches to the access pattern and cut both I/O load and latency.[4] One database cache to avoid relying on: MySQL’s query cache was deprecated in 5.7.20 and removed in 8.0 (see Unit 12 · SQL tuning).

13.5Application caching

In-memory caches such as Memcached and Redis are key-value stores that sit between your application and your data storage. Because they hold data in RAM, they are much faster than typical databases, which store data on disk.[1] Larson puts the gap at orders of magnitude.[4] Kreutzberger reports that Redis on a standard server can serve several hundred thousand reads per second, and writes, especially increments, are also fast.[6] Unlike database caching, an application cache is explicit: your code decides what goes in and when.[4]

Eviction policies

RAM is more limited than disk, so the cache needs a rule for which entries to drop. The primer points to algorithms such as least recently used (LRU), which evict “cold” entries and keep “hot” data in RAM.[1] Matyashovsky lists the knobs every cache exposes: a maximum size, the algorithm used for eviction (LRU, LFU or FIFO), an eviction percentage, and expiration by TTL or by absolute or relative time.[3] Bonér adds bounded LIFO and explicit invalidation to that list.[5]

Eviction or invalidation?

The primer calls these “cache invalidation algorithms”, and its link leads to Wikipedia’s article on cache replacement policies.[1][9] This guide says eviction for removing an entry to make room, and invalidation for removing an entry because its data changed (13.9).

Wikipedia judges a policy by two numbers, hit ratio and latency: tracking more about usage tends to raise the hit ratio but costs time on every access.[9]

What to cache

There are several levels you can cache at, falling into two general categories, database queries and objects:[1]

Row levelIndividual rows as stored.
Query levelThe result set of one query (13.6).
Serializable objectsFully formed objects assembled by your code (13.7).
Rendered HTMLWhole pages or fragments, ready to send.

Generally, avoid file-based caching: it makes cloning servers and auto-scaling harder.[1] Kreutzberger puts it more bluntly, calling it a pain for both.[6] Unit 1 explains why servers need to stay identical clones (Unit 1 · Clones).

Local to distributed

An application cache can live inside each server or be shared across many. Matyashovsky names five arrangements (Figure 13.6, Table 13.3).[3]

Distributed caches answered a need for availability; data grids answered a need for processing.[3] Bonér’s deck lists data grid products (Coherence, Terracotta, GigaSpaces, GemStone, Tibco Active Matrix, Hazelcast) and places them on the C + P side of CAP; it also notes that a peer-to-peer cache has no special nodes, so nodes can join and leave freely.[5]

13.6Caching at the query level

Whenever you query the database, hash the query to make a key and store the result under it. The approach suffers from expiration problems:[1]

  • A cached result is hard to delete when the query is complex.
  • If one piece of data changes, such as a single table cell, you need to delete every cached query that might include it.

Kreutzberger calls this the older pattern and still the most common one.[6] The difficulty is that the cache only sees a hash; nothing in it says which rows a result came from.

13.7Caching at the object level

Instead, see your data as an object, the way your application code already does. Have the application assemble the dataset from the database into a class instance or a data structure, and cache that:[1]

  • Remove the object from the cache if its underlying data has changed.
  • It allows asynchronous processing: workers assemble objects, and the application consumes the latest cached one.

Kreutzberger’s example is a Product whose prices, texts, pictures and reviews come from several queries that would each be awkward to cache. Assembled once, the whole product is cached and replaced as a unit. He calls this pattern his strong preference.[6] The primer’s suggestions of what to cache:[1]

User sessionsKreutzberger: never keep them in the database.[6]
Fully rendered pagesHis example: fully rendered blog articles.[6]
Activity streamsFeeds assembled from many sources.
User graph dataWho is friends with whom.[6]

13.8When to update the cache

Since you can only store a limited amount of data in the cache, you need to choose the update strategy that suits your use case.[1] AWS makes the same point with examples: a gaming leaderboard and a trending news feed call for different strategies.[7]

Five access patterns

Matyashovsky lists five cache access patterns. The primer covers four of them and mentions the fifth, read-through, when comparing refresh-ahead.[3][1]

Table 13.4 The five patterns by who talks to the database. From Matyashovsky, slides 14–18,[3] and the primer.[1]
PatternWho reads and writes the databaseIn one line
Cache-asideThe applicationThe cache is “kept aside”; the app fills it after a miss
Read-throughThe cacheThe app reads only from the cache, which loads missing entries itself
Write-throughThe cacheThe app writes to the cache, which writes to the database before returning
Write-behindThe cache, laterChanged entries are written to the database asynchronously after a delay
Refresh-aheadThe cache, earlyRecently used entries are reloaded before they expire
Names vary

Larson labels his application-code example a read-through cache, though the app itself checks the cache and queries MySQL on a miss.[4] The primer calls that arrangement cache-aside, and Matyashovsky reserves read-through for a cache that does the loading.[1][3] When reading other material, check who talks to the database.

Cache-aside

The application is responsible for reading from and writing to storage; the cache never talks to storage directly. On a read, the application:[1]

  1. Looks for the entry in the cache and gets a cache miss.
  2. Loads the entry from the database.
  3. Adds the entry to the cache.
  4. Returns the entry.
def get_user(self, user_id):
    user = cache.get("user.{0}", user_id)
    if user is None:
        user = db.query("SELECT * FROM users WHERE user_id = {0}", user_id)
        if user is not None:
            key = "user.{0}".format(user_id)
            cache.set(key, json.dumps(user))
    return user

Listing 13.1 Cache-aside read, from the primer.[1] It is pseudocode: the hit path returns the stored JSON string as-is, while the miss path returns the database row, and the key is built two different ways. Real code would build the key once and deserialize on a hit.

Memcached is generally used this way.[1] Subsequent reads of cached data are fast. Cache-aside is also called lazy loading: only requested data is cached, so the cache doesn’t fill up with data nobody asks for.[1][7]

Advantages

  • Only requested data takes up cache space.[1]
  • A failed cache node isn’t fatal; the app just runs slower while misses refill the new node.[7]
  • May suit setups where several cache servers update the same storage.[3]

Disadvantages

  • Each miss costs three trips (cache, database, cache), which can add noticeable delay.[1]
  • Data goes stale if the database is updated. A TTL forces a refresh, or write-through keeps it current.[1]
  • A failed node is replaced by an empty one, increasing latency until it warms up.[1]

Write-through

The application uses the cache as its main data store, reading and writing data there, while the cache reads from and writes to the database:[1]

  1. The application adds or updates the entry in the cache.
  2. The cache synchronously writes the entry to the data store.
  3. The call returns.

Application code

set_user(12345, {"foo":"bar"})

Cache code

def set_user(user_id, values):
    user = db.query("UPDATE Users WHERE id = {0}", user_id, values)
    cache.set(user_id, user)

Listing 13.2 Write-through, from the primer.[1] Also pseudocode: a real UPDATE needs a SET clause.

Write-through is slow overall because of the write, but reads of just-written data are fast. Users generally tolerate latency on updates better than on reads, and data in the cache is never stale.[1][7] Larson generally prefers it to deleting and repopulating entries, because it makes a stampede of misses onto the database less likely.[4] Matyashovsky adds that read-through and write-through keep application code simpler than cache-aside.[3]

Disadvantages

  • A node created by failure or scaling caches nothing until each entry is next updated in the database. Using cache-aside alongside write-through fixes this.[1] AWS calls it missing data.[7]
  • Most data written may never be read; a TTL limits the waste.[1] AWS calls this cache churn.[7]

Wikipedia’s hardware terms map onto this. A write-through cache updates cache and backing store together, and is usually paired with no-write allocate (also called write-around): a write to an uncached key goes straight to storage without loading it into the cache.[8]

Write-behind (write-back)

In write-behind, the application:[1]

  1. Adds or updates the entry in the cache.
  2. Writes the entry to the data store asynchronously, which improves write performance.

Bonér’s figure shows the mechanism: the write is queued as an event, the user gets an answer at once, and an event processor applies queued events to the database later.[5] Matyashovsky adds that the delay is configurable, and that write-behind can give considerably higher throughput and lower latency than write-through. The database update then happens outside the cache’s transaction, so it can conflict with an update made to the database by someone else.[3] In Hazelcast’s map store, one setting (write-delay-seconds) chooses between the two: 0 means write-through, anything larger means write-behind.[3]

In hardware, a write-back cache writes only to the cache and updates the backing store when the block is about to be replaced. It marks changed entries with a dirty bit so it knows what still needs writing.[8]

Disadvantages

  • Data loss if the cache goes down before its contents reach the data store.[1]
  • More complex to implement than cache-aside or write-through.[1]

Refresh-ahead

You can configure the cache to automatically refresh any recently accessed entry before it expires.[1] Matyashovsky specifies that the reload is asynchronous and goes through the cache’s loader.[3] If the cache predicts well which items will be needed, refresh-ahead gives lower latency than read-through, since readers then rarely wait for a reload.[1] The same idea appears in hardware as prefetching: fetching data early on a guess that it will be needed next.[8]

Disadvantage

  • Predicting badly which items will be needed can make performance worse than not using refresh-ahead at all.[1]

TTL and combining strategies

A time to live (TTL) is the number of seconds until a key expires; reading an expired key counts as a miss. A TTL doesn’t guarantee fresh data, but it limits how stale an entry can get and stops unused entries from piling up. AWS pairs a TTL with each strategy to get the benefits of both: write-through plus a TTL keeps data current without clutter; lazy loading plus a TTL survives empty nodes and refreshes data periodically. Their examples use a 300-second TTL.[7] The same mechanism drives CDN and DNS expiry (Unit 8 · Time to live).

Matyashovsky’s two rules of thumb: read-through/write-through keep application code simple, while cache-aside may block and can fit better when several cache servers update the same store; and write-behind trades write-through’s safety for speed.[3]

13.9Disadvantages of caching

  • You need to keep caches consistent with the source of truth, such as the database, through cache invalidation.[1]
  • Cache invalidation is a difficult problem, and deciding when to update the cache adds complexity.[1]
  • You need application changes, such as adding Redis or Memcached.[1]

Larson explains where invalidation gets hard. In one datacenter it is straightforward, but it becomes error-prone once several code paths write to the database and the cache. The two basic approaches are writing the new value into the cache whenever it changes (write-through) or deleting the cached value and letting the next read repopulate it. Fuzzy queries (such as full-text search) and bulk changes to an unknown set of rows are harder still. For those he suggests relying on database caching, setting aggressive expirations, or reworking the logic: select the matching rows, invalidate their cache entries, then delete them by primary key.[4] He adds that multiple datacenters make it harder again.[4]

Matyashovsky’s list of costs adds limited (or unacceptably large) memory, synchronization complexity, durability and scalability to consistency and invalidation.[3] Wikipedia names the general problem: when anything else changes the backing store, cached copies go stale, and keeping several caches in agreement takes a coherence protocol.[8]
